# UI 셸·반응형 개발 프롬프트 (UI Shell & Responsive Dev Charter)

이 앱은 **사진과 기억이 주인공**이다. UI는 그걸 방해하지 않는 선에서만 존재한다.
여기 규칙과 코드가 어긋나면 **코드가 진실**이고 이 문서를 갱신한다.
편집기·뷰어 전용 규칙은 `.claude/skills/photo-editor-dev`가 정본이다(중복 서술 금지).

## 0. 파일 지도

| 파일 | 역할 | 성격 |
|---|---|---|
| `src/ui/styles/tokens.css` | 색·간격·반경·그림자·시맨틱 토큰(`--sem-*`) | **모든 값의 SSOT** |
| `src/ui/styles/app.css` | 전 화면 스타일 + 반응형 분기 | 하드코딩 색 금지 — 토큰만 |
| `src/ui/styles/fonts.css` | 제목 웹폰트 `@font-face` 조각(unicode-range) | **GENERATED — 손편집 금지.** `python3 scripts/gen-font-subsets.py` |
| `src/ui/theme.ts` | 라이트/다크 + 계절 테마(localStorage) | 표시 선호만(기억 데이터 아님) |
| `src/ui/dom.ts` | `el()` 생성 헬퍼 + `setNote()` 상태 위계 | **자유 텍스트는 textContent만**(innerHTML 금지) |
| `src/ui/screens/*.ts` | 화면 셸 | DOM. 순수 로직이 생기면 `domain/`으로 내려보낼 것 |

## 1. 불변 계약

1. **토큰만 쓴다**: 색·간격·반경을 하드코딩하지 않는다. 새 값이 필요하면 토큰을 추가한다(하드코딩은 테마·다크모드에서 조용히 깨진다).
2. **`innerHTML` 금지**: 자유 텍스트(사용자 입력·외부 API 결과)는 `textContent`로만. CSP·XSS 게이트가 이를 전제한다.
3. **DOM 순서 = 논리 순서**: 시각 배치는 **CSS로만** 바꾼다. 2단 레이아웃을 만들 때도 DOM은 논리 순서(입력 → 목록)를 유지해 화면읽기·키보드 탐색이 흔들리지 않게 한다.
4. **한 줄을 무한정 늘리지 않는다**: 넓은 화면에서 `max-width`만 키우면 입력·본문이 읽기 나빠진다. **남는 폭은 구조로 쓴다**(2단·다열). 현재 상한: `≥1100px`에서 1200px, `≥1600px`에서 1360px.
5. **상태 표시는 위계를 가진다**(`setNote`): `ok`=정상은 거의 안 보이게 · `info`=알아둘 것은 옅게 · `error`=놓치면 안 되는 것만 뚜렷하게. **성질이 다른 상태에 균일한 시각 무게를 주지 않는다.**
6. **어포던스는 모바일에서 성립해야 한다**: `title`(hover 툴팁)에만 담긴 정보는 휴대폰에서 **없는 것과 같다**. 근거·상세는 탭으로 펼치는 실제 요소로 준다.
7. **터치 영역·초점**: 버튼은 충분한 높이, `:focus-visible` 윤곽 유지. 모달은 초점 이동 + Esc 닫기 + 리스너 정리.
   🔴 **정리 규율은 모달만의 것이 아니다** — 화면(screen)도 **정리 함수를 돌려주고**, 비동기 뒤에
   그리기 전에 **`isCurrent()`를 묻는다**(§3-K · M-0158). 예전엔 이 항목이 모달만 말해서
   **문서 자체가 비대칭**이었고 코드가 그 모양을 따랐다.
8. **오버레이·모달은 `.overlay-base` / `.modal-base`를 쓴다** — 자기 배치 규칙을 갖지 않는다(§9 참조).
9. **선택할 수 있으면 해제할 수 있다**: 사용자가 고른 것(사진·좌표·감정·필터)은 **되돌릴 어포던스를 같은 자리에** 둔다. 해제 기호는 늘 `✕`, 늘 우상단. 저장 전과 저장 후가 다른 어휘를 쓰면 안 된다(§3 v0.73).
10. **시맨틱 틴트 위 텍스트는 `--sem-*-ink`**: 원색(`--sem-teal` 등)을 같은 색 틴트 배경 위에 쓰면 라이트 테마에서 대비가 무너진다. 다크에서만 확인하면 안 보인다.

### 목록 순서와 반복 카드 색상 (2026-08-04 · 홈 여행 목록)

- **저장소 순서·입력 순서는 화면 정렬 계약이 아니다.** 사용자가 무엇을 먼저 찾는지에 맞는 기준을 순수 함수로 만들고, 화면은 그 결과만 그린다. 날짜 목록의 기본은 최신순이며 날짜 미정은 뒤로 보낸다. 같은 날짜의 안정 정렬처럼 의도한 동률 규칙도 테스트에 적는다.
- **필터마다 정렬 규칙을 손으로 다시 쓰지 않는다.** 전체·연도·월·보관처럼 같은 성격의 목록은 필터 뒤 공용 정렬 함수를 통과해 사용자 대면 대칭을 지킨다. 의도적으로 다른 목록만 이유를 코드에 남긴다.
- **정렬 회귀 픽스처는 입력순서와 기대순서를 반대로 만든다.** 이미 최신순으로 들어온 자료를 검사하면 정렬 코드가 없어도 초록이다. 예: 7월을 먼저 넣고 8월을 나중에 넣은 뒤 DOM에서는 8월이 앞인지 잰다.
- **반복 카드는 색으로 서로 경쟁하지 않는다.** 공통 저채도 바탕을 토큰으로 두고 카드마다 계절색·범주색 하나만 낮은 비율로 섞는다. 한 카드 안에서 고채도 강조색 여러 개를 교차시키지 않으며, 제목·상태·기간이 배경보다 먼저 읽혀야 한다.
- **색상 조정은 대표 카드 하나만 보지 않는다.** 모든 변형을 한 화면에 놓고 라이트·다크 테마의 대비, 카드 간 편차, 텍스트 가독성을 실제 Chromium 캡처로 확인한다. 색값은 `tokens.css`가 SSOT다.

## 1-A. 오버레이/모달 계약 (실제 사고에서 역산 — 2026-07-26)

> **이 절은 "읽었어도 못 막았을 구멍"이었다.** 사용자 실기기(가로 태블릿)에서 사진 편집 모달의
> **상하가 잘리고 여백이 없었는데**, 그때 이 문서에는 `vh`·오버레이 스크롤 얘기가 한 줄도 없었다.
> 문서를 정독하는 단계의 진짜 일은 이런 구멍을 발견해 **그 자리에서 메우는 것**이다.

원인이 둘이고, 둘 다 세로 화면에서는 안 드러난다:

| 함정 | 왜 위험한가 |
|---|---|
| `vh` 단위 | 모바일 브라우저의 `vh`는 **주소창을 포함한 레이아웃 뷰포트**라 실제 보이는 높이보다 크다. `max-height: 96vh`가 화면 밖으로 넘친다. |
| `place-items: center` + 넘침 | 위아래로 **똑같이** 삐져나가 **스크롤로도 닿지 못한다.** 잘린 부분에 영영 접근 불가. |

**계약(규칙은 `app.css`의 `.overlay-base`/`.modal-base` 한 곳에만 있다):**

- 오버레이: `align-items: flex-start` + `overflow-y: auto` + safe-area 여백. 중앙정렬 금지.
- 모달: `margin: auto`(들어가면 가운데, 넘치면 위에서부터) + `max-height: calc(100dvh - N)` — **`dvh`만**.
- 새 오버레이는 `el('div', 'overlay-base my-overlay')` 처럼 **두 클래스를 붙인다.** 자기 파일에
  `position/padding/max-height`를 다시 쓰면 그 순간 형제와 갈라진다(세 오버레이가 실제로 갈라졌다).

### 🔴 모달은 **불투명 표면**을 갖는다 — 그리고 그 표면은 한 곳에만 산다 (2026-08-15 · M-0172)

> 사용자 실기기 화면에서 「여행 편집」 모달의 **뒤 카드 글자가 모달 글자를 뚫고 나왔다.**
> 라이트 테마에서는 「새 여행」 제목과 빈 상태 문장이 **겹쳐 읽혔다.**

실측: `.trip-editor-modal`의 배경이 `rgba(0,0,0,0)` · 테두리 0 · 모서리 0 · 그림자 none · 여백 0.
그런데 형제 다섯(`guide`·`map`·`pe-sheet`·`pr-records`·`single-photo-moment`)은 **글자 단위로 같은
네 줄**을 갖고 있었다. **손으로 다섯 벌 복사돼 있었고 여섯 번째에서 빠졌다** — §2 「손편집 중복
자체가 결함」과 §7 「형제 중 하나만 조용히 빠졌다」가 같은 자리에서 만난 형태다.

- **표면 네 줄(`background`·`border`·`border-radius`·`box-shadow`)은 `.modal-base`에만 쓴다.**
  새 모달은 `modal-base`를 붙이는 것만으로 **물려받는다**(다음 사람이 몰라도 지켜진다).
- 🔴 **`padding`은 올리지 않는다.** 헤더/바디 구조를 가진 모달은 자식이 여백을 갖고
  `overflow: hidden`으로 자르므로, 바깥 여백을 주면 그 구조가 어긋난다. **여백은 내용 구조를
  가진 쪽이 정한다**(`.pe-sheet`·`.trip-editor-modal`처럼 단순 세로 폼만 자기 여백을 갖는다).
- **다른 값으로의 재정의는 정당하다**(전면 사진 모달의 검은 배경 등). 잡는 것은 **같은 값의 재선언**뿐이다.
- 🔴 **폭이 글자 수로 정해지면 안 된다**: 취소 버튼이 「취소」 두 글자 폭(52px)이라 저장과
  **8.08:1**이 됐다. 3-E ②(*"높이는 못 박는다"*)가 **폭에도** 걸린다. 하한을 주고 비를 4:1 이하로.

**검증 층(헤드리스만으로는 부족하다):**

- 정적 — `check-verdict-symmetry`의 `overlayContract()`가 `vh` 사용·중앙정렬·스크롤 누락을 막는다. **이게 본 방어선이다.**
- 라이브 — `verify-editor-live`가 짧은 뷰포트 3종에서 상단 잘림·여백·스크롤 도달을 잰다.
- **헤드리스는 원인을 재현하지 못한다**: 브라우저 주소창이 없어 `vh == 실제 높이`가 되기 때문이다.
  그래서 라이브 검사는 기하가 아니라 **계약**(`overflow-y`, `align-items`)을 본다.


## 2. 반응형 측정 규율 (이 절이 이 문서의 핵심)

> **반응형 회귀는 "보는 것"이 아니라 "재는 것"으로 잡는다. 그리고 한 방향만 재면 절반을 놓친다.**

- **세로·가로 둘 다 측정한다.** 세로 화면은 폭이 제약이고 가로 화면은 높이가 제약이라, 높이 제약 결함은 세로에서 안 드러난다(§3 v0.41이 그 사례).
- **경계값을 재라**: 분기점 직전/직후(예: 1099/1100/1101)와 흔한 기기 폭(412·768·1024·1280·1480·1920).
- **가로 넘침은 0이어야 한다**: `documentElement.scrollWidth - clientWidth <= 0`을 모든 폭에서 확인.
- **측정은 수치로 남긴다**: "괜찮아 보임"이 아니라 렌더 rect·본문 폭·넘침 px를 표로 기록한다.
- 새 레이아웃 분기를 넣으면 `scripts/verify-editor-live.mjs`에 **영구 회귀 검사**를 추가한다.

### 🔴 글꼴 배율 축 — **폭만 재면 절반이다** (T-051 · 2026-08-16 신설)

> 이 저장소는 폭(344·375·412·768)과 방향(세로·가로)은 촘촘히 쟀는데 **글꼴 배율은 규칙도
> 검사도 0건**이었다. 그래서 「344px 통과」는 **「기본 글꼴에서만 봤다」**였다.

**기준(고른 숫자가 아니라 근거)** — `live-browser-lib.mjs`의 `SCALE_STEPS`가 정본:

| 배율 | 근거 |
|---|---|
| `130%` | 안드로이드 One UI 「글자 크기」 **최대 단계**(실사용 상한) |
| `200%` | **WCAG 1.4.4 Resize Text** — *"내용·기능 손실 없이 200%까지"* |

🔴 **이 앱이 이 축에 노출된 이유(실측)**: `font-size` 선언 **238개가 전부 `rem`, `px` 0개**이고
`html { font-size }` 선언이 없다 — 브라우저·OS 기본 글꼴을 **그대로 따라간다.** 반면
`--touch-target-min`은 `44px`이라 **글자만 커지고 상자는 안 커진다.** 그 어긋남이 깨지는 자리다.
그러므로 루트 `font-size` 조정이 이 앱에서는 **충실한 시뮬레이션**이다.
(**정직한 한계**: px 글꼴을 쓰는 앱에는 충실하지 않다 — 안드로이드 textZoom은 px도 곱한다.)

**규칙 셋.**

- **`white-space: nowrap`은 배율에서 폭탄이다.** 평상시엔 옳지만 글자가 두 배가 되면
  **접힐 수가 없어** 화면 밖으로 나간다. 넘치면 **자르지 말고 접는다**
  (`white-space: normal` + `max-width: 100%` + `overflow-wrap: anywhere`).
- 🔴 **부모를 `flex-wrap: wrap`으로 바꿔서 접지 마라 — 자식의 정렬 계약이 조용히 바뀐다.**
  `wrap`은 **줄마다 교차축 크기를 따로** 계산해서 자식의 `align-self: stretch`를 무력화한다.
  실측(M-0176): T-049에서 30px로 올려놓은 히트 높이가 **17px로 되돌아갔고** 이웃 터치까지 훔쳤다.
  **접는 일은 자식이 자기 안에서** 한다.
- **44px 표적은 배율을 걸지 않고 100%에서만 잰다.** 글자가 커지면 상자도 커져 그 축은
  **쉬워진다** — 쉬워진 검사로 통과를 사는 것은 §4가 말하는 공허함이다.
- 🔴 **겹치는 표면에 자를 댈 때는 「몇 개에 맞았는가」를 증거에 남겨라**(2026-08-16 · M-0179).
  이 앱의 오버레이는 **겹친다** — 「개발자 정보」 위에 「설계 개요도」가 열리면 `.guide-overlay`가
  **2개**가 되고, `querySelector`는 **밑에 깔린 것**을 준다. 그러면 검사는 사용자가 보는 화면이
  아니라 **가려진 화면**을 재고, 초록의 뜻은 「괜찮다」가 아니라 **「엉뚱한 걸 쟀다」**가 된다.
  - `coverSweep`은 이제 **마지막(맨 위)**을 쓰고 `roots`를 판정 증거에 싣는다.
  - 🔴 **「모집단 0이 아니다」는 「올바른 모집단이다」가 아니다.** 모집단 가드는 *안 본 것*을
    막지 *엉뚱한 것을 본 것*은 못 막는다.
  - 🔴 **서로 다른 화면이 같은 숫자를 내면 멈춰서 물어라.** 두 개발자 화면이 똑같이
    `controls: 5`를 낸 것이 이번의 **유일한 단서**였다.

### 🔴 움직임 줄이기 축 — **배려가 기능을 뺏으면 그건 결함이다** (T-052 · 2026-08-16 신설)

> `prefers-reduced-motion: reduce`는 「애니메이션을 끄면 된다」로 읽히기 쉽다. 그런데 이 앱에서
> 그 설정이 걸리는 자리는 **끌어서 순서 바꾸기**와 **소리 재생 중 표시**다 — 둘 다 움직임이
> *장식이 아니라 정보*를 나르고 있었다. 끄기만 하면 **정보가 같이 사라진다.**

**기준(이 축에서 「정상」이 무엇인가)** — 두 갈래로 나눠서 판정한다:

| 갈래 | 켰을 때 옳은 것 | 켰을 때 결함인 것 |
|---|---|---|
| **장식** — 확대·튀는 전환·움직이는 그래픽 | 사라진다 | 남아 있다 |
| 🔴 **정보** — 「지금 들려 있다」·「지금 재생 중이다」·「여기로 간다」 | **다른 수단으로 여전히 보인다**(색·테두리·글자·`aria-*`) | 같이 사라진다 |

🔴 **그래서 이 축의 검사는 「없어졌는가」가 아니라 「여전히 아는가」를 잰다.** 「애니메이션이
`none`이다」만 재는 검사는 **정확히 결함인 쪽을 통과시킨다** — 기능이 사라진 화면도 애니메이션은
`none`이기 때문이다. 전제(`none`)와 결과(**여전히 보인다·여전히 된다**)를 **한 검사에서 함께** 읽는다.

**규칙 셋.**

- **끄는 것은 `transform`/`animation`이고, 남기는 것은 `color`/`border`/`글자`/`aria`다.**
  실측: 들어올린 사진은 배율이 `none`이 되지만 **테두리 색**으로 계속 구분된다
  (`R⑨-1`이 그 두 값을 나란히 찍는다). 소리는 🔊가 **이퀄라이저 글리프**로 바뀌고
  `aria-pressed=true`가 남는다 — 움직이지 않아도 상태를 읽을 수 있다.
- 🔴 **기능은 절대 빼지 않는다.** 「움직임을 줄여 달라」는 「덜 움직이게 해 달라」이지
  **「못 하게 해 달라」가 아니다.** 끌어서 재배열은 켠 상태에서도 **끝까지 돼야 한다**(`R⑨-2`).
- **재고 나서 되돌린다.** `page.emulateMedia({ reducedMotion })`는 페이지 상태를 보존하므로
  같은 탭에서 켜고 끈다 — `browser.newContext()`는 **IndexedDB가 빈 채로 시작**해 픽스처가
  통째로 날아간다. 되돌림 자체도 검사한다(`R⑨-3`) — 안 되돌리면 뒤 검사가 조용히 오염된다.

**어디에 있나**: `live-browser-lib.mjs`의 `underReducedMotion(page, fn)`이 켜고·되돌리는 일을
한 곳에서 맡고, 화면은 *무엇을 재는지*만 쓴다(§7 2층). `verify-editor-live.mjs`의 `R⑨` 블록과
오디오 2건이 **런타임** 층이다.

### 🔴 그리고 CSS에도 층을 놓았다 — `no-preference`는 **덫**이다 (`check-reduced-motion-scope`)

라이브는 **내가 짝지어 준 두 자리**만 본다. CSS에서 규율이 깨지는 것은 아무도 안 보고 있었다.

> `@media (prefers-reduced-motion: no-preference) { … }` 안에 넣은 선언은
> **reduce 사용자에게 통째로 사라진다.** 지금은 장식만 들어 있지만, 누가 거기에
> *정보*(색·글자·표시 여부)를 넣는 순간 그 사용자만 조용히 못 보게 된다 —
> 그리고 **자료구조는 옳으므로 유닛은 영원히 초록이다**(§10 ③의 CSS판).

**규칙**: 두 방향의 `prefers-reduced-motion` 블록 안에는 **움직임 속성만** 온다
(`transition*`·`animation*`·`transform`·`translate`·`rotate`·`scale`·`scroll-behavior`·`will-change`).
그 밖의 속성은 **이유와 함께 등록**해야 통과한다(`NON_MOTION_ALLOWED` — 이유 없는 제외는 결함, §7).

- **반대 방향도 같은 규칙이다.** `reduce` 블록에서 끄는 것도 움직임이어야 한다.
  거기 `display: none`을 쓰면 배려가 아니라 **기능을 뺏는 것**이다(M-0177).
- **모집단을 먼저 판정한다.** 블록을 하나도 못 찾으면 초록이 「위반 없음」이 아니라
  **「안 봤음」**이므로 **실패로 닫는다**(§4 · §2-J ①).
- 🔴 **정직한 한계 — 속성 이름만 본다.** 「이 선언이 장식인가」는 못 본다.
  `transform`으로 정보를 나르면 이 게이트는 **조용하다.** 판단은 예외 등록의 *이유*가 지고,
  그건 사람이 읽는다. 하는 일은 「장식만 들었다」의 보증이 아니라
  **「움직임이 아닌 것이 조용히 섞이는 것의 차단」**이다.

**현재 등록된 예외는 1건**: `.trip-card:hover { box-shadow }` — 떠오르는 그림자는 hover 장식이고,
「누를 수 있다」는 `cursor: pointer`가, 「지금 여기 있다」는 `:focus-visible` 외곽선이 진다.
**둘 다 블록 밖에 있어 reduce에서도 살아 있다**(2026-08-16 실측).

**주입증명(§4)** — 두 방향으로 RED를 봤다:
① 헬퍼를 `reducedMotion: null`로 바꾸니 **전제 2건**이 빨간불(`애니메이션: "eqp"`).
② 드롭에서 `onReorder`를 건너뛰게 하니 `R⑨-2`만 빨간불(순서가 그대로)이고 `R⑨-1`·`R⑨-3`은
초록 유지 — **검사가 죽지 않고 판정했다**(§18-G).

### 🔴 아직 안 재는 축 — 「없다」가 아니라 **「안 봤다」**이다 (2026-08-15 흡수)

외부 UI/UX 규칙집(`ui-ux-pro-max`)을 우리 규율과 대조했더니, 그쪽이 말하는 것 대부분은 우리가
**이미 더 촘촘하게** 갖고 있었다(터치 44px·safe-area·대비 4.5:1·다크 토큰·4/8 간격·경계 폭).
**우리에게 없던 것은 딱 둘**이고, 둘 다 규칙도 검사도 0건이었다. 적어 두지 않으면 다음 사람은
「이미 다 재고 있다」고 믿는다 — 그게 §8이 말하는 가장 나쁜 반올림이다.

🔴 **둘 다 2026-08-16에 축이 생겨 이 표는 지금 비어 있다**(글꼴 배율 `T-051` · 움직임 줄이기
`T-052` — 각각 위 두 절). **비어 있다는 것이 「다 잰다」는 뜻은 아니다** — 그때 대조한 것은
`ui-ux-pro-max` 한 권이고, 그 목록 밖은 애초에 묻지 않았다.

| 축 | 지금 상태 | 왜 우리에게 중요한가 |
|---|---|---|
| *(비어 있음)* | — | — |

**표를 지우지 말고 비워 둔다.** 지우면 다음 사람은 이 규율이 있었다는 것도 모른다.
새 축을 발견하면 **여기 먼저 적고**(「반쪽」인지 「0건」인지 상태와 함께), 기준을 정하기 전에는
게이트를 만들지 않는다 — 기준 없는 초록의 뜻은 「지켰다」가 아니라 **「안 봤다」**이다
(§19가 게이트를 두지 않은 것과 같은 자세). 두 축 모두 **과제로 올려 두고 기준을 먼저 세워서**
닫았고, `T-051`은 그 과정에서 결함 5건을, `T-052`는 규율의 방향 자체(「끄기」가 아니라
「다른 수단으로 남기기」)를 잡아냈다.

## 3-A. 웹폰트 규칙 (2026-07-26 건강검진에서 신설)

- **사용자 글자를 서브셋으로 잘라내지 않는다.** `.trip-title`·`.detail-title`은 사용자가 쓴 여행
  제목이다. "앱이 쓰는 글자만" 남기면 사용자 글이 폴백으로 갈라진다 — 폰트를 번들한 이유가
  그 갈라짐을 없애는 것이었으므로, 자르는 순간 목적을 잃는다. 자르려면 **`unicode-range`로**
  자른다(안 쓰면 안 받을 뿐, 쓰면 받는다).
- **CSS는 렌더 차단이고 폰트는 아니다**(`font-display: swap`). 그래서 조각을 잘게 쪼갤수록
  좋은 게 아니다 — `unicode-range` 문자열이 길어지면 **첫 페인트를 늦춘다.** 실측으로 정한다:
  정밀 구간을 다 적으면 CSS gzip +19.4KB, 희귀 조각만 성기게 두면 +9.9KB였다.
- **겹치는 `unicode-range`는 뒤 선언이 이긴다.** 이 성질에 기대는 배치는 **추측하지 말고**
  헤드리스에서 실제 네트워크 요청으로 확인한다(`verify-editor-live`의 「폰트 조각」 검사).
- `font-display: swap`을 빼지 않는다. 빠지면 폰트 도착 전 글자가 **투명**해진다(빈 화면).

## 3-C. 라이브 검사는 **흐름을 깨지 않는 자리**에 넣는다 (오늘 두 번 어겼다)

## 3-C-2. 🔴 **`settle()`은 「프레임 두 장」이지 「끝났다」가 아니다** (2026-08-15 · T-042)

라이브가 **같은 코드에서 흔들렸다** — 세 번 관측했고 매번 다른 검사였다(「휴지통 일괄삭제」에서
30초 timeout 사망 · 「홈 트리 ✕ 해제」 · 「R⑧ 재배열 직후 사진 뷰어」). 재실행하면 통과했다.

**근본형은 하나다: 행동 직후 「즉시」 재는 것.**

| 쓰는 것 | 실제로 기다리는 것 | 언제 이른가 |
|---|---|---|
| `await settle(page)` | **rAF 두 번**(프레임 두 장) | 저장소 조회·이미지 로드·네트워크가 끼면 |
| `await locator.isVisible()` | **아무것도** — 즉시 판정 | 펼침·애니메이션이 끝나기 전 |
| `await locator.count()` | **아무것도** — 즉시 판정 | 위와 같음 |

🔴 **`isVisible()`·`count()`에는 자동 대기가 없다.** `click()`·`waitFor()`와 달라서, 「곧 나타날
것」을 물으면 **false를 사실로 받아 적는다.** 그리고 그 뒤 클릭이 timeout으로 죽으면 **뒤따르는
검사가 통째로 사라진다** — FAIL 하나가 아니라 시나리오 절단이다(실제로 그렇게 죽었다).

**처방**: 시간이 아니라 **내용**을 기다린다(M-0119가 이미 적은 규율의 재확인).

```js
// ✗ 프레임만 기다리고 즉시 판정
await settle(page);
check('뷰어가 열린다', await page.locator('.photo-viewer').count() === 1);

// ✓ 「열렸다」는 사실을 기다린 뒤 그 결과로 판정
const opened = await waitUntil(async () => await page.locator('.photo-viewer').count() === 1, 5000);
check('뷰어가 열린다', opened);

// ✓ locator라면 waitFor가 더 싸다(자동 대기를 쓴다)
await confirmBtn.waitFor({ state: 'visible', timeout: 10_000 }).catch(() => {});
```

**`settle()`을 다 없애라는 뜻은 아니다.** 동기 렌더(클래스 토글·텍스트 교체)에는 그것으로 충분하고
실제로 100곳 가까이 그렇게 쓰고 있다. 갈림은 **「이 결과가 비동기를 거치는가」** 하나다 —
저장소 조회 · 이미지/영상 로드 · 네트워크 · 애니메이션이 끼면 `settle`은 이르다.

**정직한 한계**: 흔들림은 정의상 **가끔** 난다. 고친 뒤 통과했다고 「없어졌다」고 말할 수 없다 —
말할 수 있는 것은 「이 세 자리에서 이르게 재던 것을 내용 기다림으로 바꿨다」까지다.

## 3-F. 🔴 **한 자리에 그리는 손이 둘이 되면 「주인」을 정하라** (2026-08-05 · M-0105)

같은 DOM 자리에 그리는 경로가 **둘 이상**이고 둘 다 `await` 뒤에 그리면, **늦게 시작한 쪽이
먼저 끝날 수 있다.** 그러면 사용자가 방금 띄운 것을 **직전 요청의 답이 지나가며 지운다.**

실제: 장소 칸 결과 상자에 「치는 동안의 대장 조회」(120ms 뒤)와 「[🔍 검색]」(네트워크)이
함께 그리게 됐다. 전체 하네스가 **기존 라이브 검사에서** 잡았다(`element was detached from the DOM`).

- 🔴 **「나중에 그린 쪽이 이긴다」는 시간에 기댄 규칙이고, 시간은 계약이 아니다.**
  지금까지 안 깨졌다면 그건 계약이 아니라 **운**이다(M-0034의 *"표기에 의존하면 판정이 아니라
  우연"*과 같은 부류).
- **구조로 바꾼다**: 그리려면 `claim()`으로 주인이 되고, `await`에서 돌아온 뒤 `holds()`로
  **아직 내가 주인인지** 확인한다. 새 주인이 나섰으면 조용히 물러난다. 세 번째 손이 붙어도
  같은 문을 지나므로 **자동으로 따라온다**(§7 2층). `placeResultsOwner()`가 그 형태다.
- **자문**: *"이 자리에 그리는 코드가 몇 개인가? 그중 `await` 뒤에 그리는 것은?"*
  둘 이상이면 주인을 정해야 한다.

### 곁가지 — **뜻이 둘이면 이름도 둘이다**

같은 상자에 「검색이 못 찾음」과 「대장에 없음」이 같은 클래스(`.place-none`)로 들어가자
**화면에서도 검사에서도 구별되지 않았다**(라이브가 엉뚱한 줄에 걸렸다). 이름을 나누고
(`.place-live-none`) **모양은 CSS가 공유한다** — `zone-suggest` vs `zone-notice`와 같은 규율이다.

### ① 컨테이너가 배치를 선언하지 않으면 자식은 조용히 줄바꿈한다

`.chip`은 `display`를 안 정해 인라인이었다. 그래서 안의 두 버튼이 인라인으로 흐르다
폭이 좁으면 **줄바꿈했다.** 그리고 `.chip-clear`의 `margin-left: auto`는 **flex가 아니면
아무 일도 하지 않는다** — 코드에는 "오른쪽 끝으로"라고 적혀 있는데 실제로는 아무 뜻이 없었다.

> **자식을 넣을 자리에는 배치를 선언한다.** `margin-left:auto`·`align-self`·`gap`은
> 부모가 flex/grid일 때만 뜻이 있다. 부모를 안 보고 자식에만 쓰면 **죽은 선언**이 된다.

### ② 높이는 못 박는다 — 우연히 같기를 바라지 않는다

flex로 고친 뒤에도 27.3 vs 29.3으로 **2px 어긋났다.** 글자만 든 칩과 버튼이 든 칩의
line-height가 달라서다. 칩 줄이 미묘하게 들쭉날쭉해 보이는 게 「조잡함」의 나머지 절반이었다.

> 같은 성격의 것이 나란히 서는 자리는 **`min-height`로 못 박는다.** 내용에 따라 높이가
> 달라지면 그건 "자연스러운 것"이 아니라 **어긋난 것**이다(§7 사용자 대면 대칭).

### ③ 🔴 부품을 **떼어내 재면** 맥락이 만드는 결함을 못 본다

✕의 터치 목표를 `::after { inset: -11px }`로 40px까지 넓혔다. **격리해서 재니 네 방향이
전부 통과**했다. 그런데 실제 카드 안에서는 **아래쪽이 사진 격자에 가려져 실패**했다.

그리고 그건 단순 미달이 아니라 **위험**이었다:

> 보이지 않는 **삭제** 목표가 사진 위에 얹히면, 사진을 누르려던 손이 소리를 지운다.

`z-index`로 올려서 "고칠" 수도 있었지만 그건 위험을 키운다. **칩 밖으로 넘치지 않는**
방식으로 바꿨다 — ✕를 칩 높이만큼 세로로 늘려 24×30=**720px²**(예전 18×18=324px²의 두 배)를
칩 **안에서** 확보했다.

**규칙 셋:**
- 넓힌 히트영역은 **자기 컨테이너를 넘지 않는다.** 넘으면 이웃의 터치를 훔친다.
- **파괴적 동작(삭제)의 히트영역은 특히** 넘치면 안 된다. 실수의 대가가 비대칭이다.
- 히트영역은 **실제 화면에서 `elementFromPoint`로 재라.** 격리 픽스처는 이 부류를 못 본다.

### 측정할 때 두 번 헛디딘 것 (둘 다 "검사가 딴 것을 재고 있었다")

| 헛디딤 | 증상 | 교훈 |
|---|---|---|
| 픽스처가 0바이트 더미 | 재생이 실패해 **「재생 불가」 경로만** 재고 있었다 | 픽스처가 틀리면 검사는 **조용히 딴 것을 잰다.** 실제로 디코드되는 것을 만들어라(무음 WAV 44바이트 헤더면 된다) |
| 칩이 뷰포트 밖 | `elementFromPoint`가 **null**을 돌려준 것을 "안 눌린다"로 읽었다 | **멀쩡한 것을 결함이라 부르는 것도 결함이다.** 재기 전에 `scrollIntoView({block:'center'})` |

### 라이브 검사는 **앱이 스스로 그리게** 한다

칩 마크업을 검사 안에서 손으로 세우면 **내가 쓴 마크업을 재는 것**이지 앱을 재는 것이 아니다
(M-0038의 「이름이 있는 것과 불리는 것은 다르다」의 CSS판). Dexie에 행을 넣고 앱이 렌더하게
하면, 클래스 이름이 바뀌는 순간 검사가 빨개진다.

**비공허 확인**: 배포됐던 상태(비-flex + `.chip-clear`)를 그대로 주입해 **5건 RED**(h=51.3 재현).

## 3-F. **뒷정리가 만드는 신호를 실패로 읽지 마라** (2026-07-28 · M-0043)

사용자 실기기: *"재생불가가 아닌데 재생불가라고 안내하네요."* 녹음을 **끝까지 들으면**
칩이 「🔇 재생 불가」로 바뀌었다. 재생은 멀쩡히 됐다.

정리 함수가 **스스로 오류를 만들고** 있었다. 미디어 요소의 `src`를 비우고 `load()`를 부르면
브라우저는 "실을 것이 없다"를 `error`로 알린다 — 그런데 그 리스너가 아직 붙어 있었다:

```
①ended → ②정리(src=''+load()) → ③라벨 정상 복귀 → ④뒤늦게 error → ⑤「재생 불가」로 덮음
```

**정상 경로에서만** 나는 거짓말이라 더 나빴다 — 실패했을 때가 아니라 **성공했을 때** 실패라 했다.

### 규칙

- **리스너를 정리보다 먼저 뗀다.** `AbortController`로 묶고 teardown 첫 줄에서 `abort()`.
- **이중 방어**: 실패 처리기는 *자기가 아직 현재 것인지* 확인하고 아니면 즉시 반환한다.
- **`src = ''` 대신 `removeAttribute('src')`.** 빈 문자열은 **문서 URL을 미디어로 실으려 드는**
  또 다른 오류원이다.

### 같은 형태가 날 수 있는 자리

WebSocket `close` · `AbortController`로 취소한 fetch(**`AbortError`를 네트워크 실패로 세는 것**) ·
`IntersectionObserver.disconnect` · `MediaRecorder.stop` — **자원을 놓는 행위는 그 자체로
이벤트를 만든다.**

### 🔴 검사는 **끝난 뒤**를 봐야 한다

기존 라이브 검사는 재생 **중** 상태만 쟀다(폭·`aria-pressed`). 상태 전이의 **마지막 칸**을
아무도 안 봤고, 그래서 이 부류는 원리적으로 안 잡혔다. §10 ③(전달 결함)의 **시간축 버전**이다:

> *"상태가 A→B→C로 가면 C도 재라. B만 재는 검사는 C에서 나는 결함에 대해 영원히 침묵한다."*

## 3-K. 🔴 **화면은 자기 생명주기를 스스로 말한다 — 「떠남」과 「늦게 도착함」 둘 다** (2026-08-13 · M-0158)

> 외부 리뷰가 두 가지를 짚었는데 **원인이 하나**였다: 라우터가 「지금 어느 화면인가」를
> **아무 데도 안 적고 있었다.**

- ① **늦게 온 Promise가 새 화면을 덮는다.** 여행 상세는 인증 확인을 `await`한 뒤 그리는데,
  그 사이 사용자가 뒤로 가면 먼저 시작한 확인이 나중에 끝나 **떠난 화면을 다시 그렸다.**
- ② **떠난 화면의 구독이 살아남는다.** 홈의 구독은 `renderHome()`이 **다시 불릴 때만** 해지됐다.
  홈 → 상세로 가면 그대로 남아 떼어낸 DOM을 참조했다.

🔴 **이 문서가 이미 반쪽을 알고 있었다.** §1 불변 계약 7항이 *"모달은 초점 이동 + Esc 닫기 +
**리스너 정리**"*라고 적고 있다. 그런데 **형제인 화면(screen)에는 같은 말이 없었다** — 오버레이는
정리 규율을 갖고 화면은 안 갖는 비대칭이 문서에 그대로 있었고, 코드가 그 모양을 따랐다(§7).

🔴 **왜 게이트 71종·유닛이 전부 초록이었나**: 그 규율이 `main.ts`에 살았고 **진입점은 유닛이
부를 수 없다.** 기존 `router.test.ts`는 **경로 파싱만** 봤다. §10 ③이 처방을 이미 적어 뒀다 —
*"사용자에게 가는 로직은 순수 함수로 뽑아라. 그래야 검사할 수 있다."*

### 규칙

1. **화면 진입 함수는 정리 함수를 돌려준다** — `(...): () => void`. 정리할 것이 없어도
   `() => undefined`를 돌려주고 **왜 비었는지 머리말에 적는다.** 반환형이 계약이라
   **다음 화면은 기억하지 않아도 따라온다**(§7 2층 — 가장 싼 구조층이다).
2. **비동기 뒤에 그리기 전에 「아직 여기인가」를 묻는다.** `await`·`.then()` 뒤의 렌더는
   전부 `if (!screen.isCurrent()) return;`을 앞에 둔다.
3. **늦게 도착한 것은 현재 화면의 정리 함수를 덮지 않는다.** 덮으면 진짜 현재 화면이 영영
   정리되지 않아 **고치려던 누수를 다시 만든다**(`screenSession.mount()`가 그 자리에서 막는다).
4. **판단은 `src/app/screenSession.ts`에만 있다.** 화면이 자기 세대 카운터를 새로 만들지 않는다.

### 이 규칙이 기대는 세 층 (§7)

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 조항 | 이 절 | 이 문서 |
| ② 구조 | 세대·정리를 한 곳에 + **반환형이 계약** | `src/app/screenSession.ts` |
| ③ 기계 | 라우터의 화면 호출 **전부**가 `screen.mount()`를 거치고, 비동기 갈래가 `isCurrent()`를 갖는가 | `check-screen-lifecycle` |

**정직한 한계**: 게이트는 **라우터**만 본다. 화면이 스스로 건 구독·타이머가 정리되는지,
`isCurrent()`가 *그리기 직전*에 있는지는 못 본다 — 존재만 본다. 그 자리는 유닛과 실기기다.

### 같은 형태가 날 수 있는 자리

`await` 뒤에 DOM을 만지는 모든 곳 — 목록 새로고침(홈이 `refreshGeneration`으로 이미 막고 있다 ·
M-0131) · 검색 결과 · 썸네일 지연 로드 · 진단 재판정. **비동기가 끝난 세계는 시작한 세계와
다르다**는 것이 공통 전제다.

## 3-G. **화면 문구는 로그인 상태를 읽는데, 화면이 그리는 데이터는 안 읽을 수 있다** (2026-08-05 · M-0102)

사용자 실사용: *"로그아웃하면 사진 데이터가 보이지 않아야 하는데 데이터가 보입니다."*

`home.ts`는 `user`(로그인 상태)를 동기화 안내 문구(`renderSyncNote`)엔 넘겼지만, 목록을 그리는
`listTrips()`/`listArchivedTrips()` 호출에는 전혀 넘기지 않았다 — 문구는 "로그인하면 동기화돼요"라고
말하면서 그 아래 목록엔 **로그인 여부와 무관하게** 이 기기에 남은 데이터가 그대로 보였다. 딥링크
라우트(`/trip/<id>`)는 인증 확인 자체가 없어 더 심했다.

### 규칙
- **"저장은 로그인과 무관"과 "표시는 로그인과 무관"은 다른 규칙이다.** 오프라인 우선은 전자만
  약속한다 — 클라우드 모드에서 로그아웃은 "이 계정의 기록을 볼 자격"의 경계이지, 로컬 데이터를
  지우거나 못 쓰게 만드는 것이 아니다(비타협 원칙 #1 — 가리는 것과 지우는 것은 다른 일).
- **같은 신호(`user`)를 문구와 데이터 양쪽에 넣어라.** 한쪽만 반영하면 화면이 스스로 모순된 말을
  한다 — 안내는 "로그인하세요"인데 바로 아래 목록엔 이미 남의(또는 이전 세션의) 기록이 있다.
- **목록 화면과 딥링크 라우트는 같은 경계를 공유해야 한다.** 목록만 가리고 상세 라우트(직접 URL·
  뒤로가기)를 그대로 두면 그 라우트가 우회로가 된다 — 잠금은 화면 하나가 아니라 **그 데이터로
  가는 모든 문**에 걸어야 한다.

이 화면들에 딸린 인증 신호가 있다면 §7대로 형제도 같은 경계를 지키는지 확인한다(다른 화면에도
사용자별 로컬 캐시가 있다면 같은 결함이 날 수 있다).

## 3-H. **한글은 `word-break: keep-all`** · 장식은 그것이 받쳐줄 내용이 생긴 뒤에 (2026-08-05)

사용자 실기기: *"제목이 일관되지 않는 거 같아요. 그리고 제목 글자크기도 좀 줄여야 될 거 같고
목록카드 색상은 요란한 거 같아요."* 셋이 다 여행 목록 카드 하나에서 나왔고, 원인은 셋이었다.

### ① 한글 줄바꿈 — 기본값은 낱말을 두 동강 낸다
`word-break` 설정이 없으면 브라우저가 한글을 **글자 단위로** 끊는다. 실제 화면:
`26년 전 한화에어 / 로 동료들과 만남`, `우즈베키스탄 의 / 대 유학생활` — 「한화에어로」와
「의대」가 쪼개졌다. **한글 제목·본문에는 `word-break: keep-all`이 기본값이어야 한다**
(낱말 경계에서만 끊는다). 끊을 데가 정말 없는 초장문 낱말 대비로 `overflow-wrap: anywhere`를
함께 둔다. `text-wrap: balance`는 카드처럼 **여러 개가 나란히 서는** 자리에서는 빼라 —
줄바꿈 지점이 카드마다 달라져 제목 모양이 들쭉날쭉해진다.

### ② 아래 붙인 내용은 위 요소를 밀어 올린다
`.cover-info`가 `position:absolute; bottom:14px`이었다. 제목이 두 줄이 되는 순간 그 위의
배지가 위로 밀렸고, **같은 줄 카드끼리 배지 높이가 달라졌다.** 이게 "일관되지 않는다"의 정체다.
→ **여러 개가 나란히 서는 카드의 내부는 위에서부터 흐르게 한다**(static). 그러면 첫 요소는
늘 같은 자리다. 실측으로 확인하라: 카드별 배지 top 편차가 0인가.

### ③ 장식은 **그것이 받쳐줄 내용**이 생긴 뒤에 만든다 🔴
카드에 그라데이션 배경 + 어두운 베일 + 노이즈 세 겹이 깔려 있었다. 그 세 겹은 원래
*사진 위에 흰 글자를 읽히게* 하려고 있는 층인데 — **이 앱엔 아직 대표사진이 없다.** 받쳐줄
내용 없이 장식만 남으면 그건 그냥 소음이고, 북극성("사진이 주인공")과 정반대다.

곁들여: 색을 `index % 3`으로 돌리고 있었다. **순번 기반 색은 뜻이 없다** — 기간 필터를 걸면
같은 여행의 색이 바뀐다. 색을 쓸 거면 **뜻**(상태·분류)을 따르게 하고, 색만으로 인코딩하지
말고 글자를 함께 둔다. (같은 `cover--*`를 쓰는 상세 히어로는 `coverIndex(trip.id)` 해시라
여행마다 색이 고정 — 그건 정당하므로 그대로 뒀고, **왜 다른지를 CSS에 적었다**(§7).)

### 규칙
- 한글 제목/본문: `word-break: keep-all` + `overflow-wrap: anywhere`. 나란히 서는 카드면 `text-wrap: balance` 금지.
- 나란히 서는 카드 내부는 **위에서부터 흐르게**. 아래 붙이면 첫 요소 자리가 내용 길이에 흔들린다.
- 사진 자리를 확보하려는 **고정 높이**는 사진이 있을 때만. 글자만 있으면 `min-height` + 격자 stretch에 맡긴다.
- 장식 층(veil·grain·gradient)을 만들 때 *"이게 무엇을 읽히게 하려는 층인가"*를 답하라. 답이 없으면 만들지 않는다.
- **어두운 배경을 전제한 부품**(흰 반투명 버튼·`backdrop-filter`)은 배경이 밝아지면 함께 따라와야 한다(§3-E).

## 3-I. 🔴 **새 제스처를 만들면 「플랫폼이 이미 이 동작을 쓰고 있지 않은가」를 먼저 물어라** (2026-08-06 · M-0115)

「사진을 꾹 눌러 순서 바꾸기」를 만들었다. 길게 누르면 칸이 **들리는데**(시작은 됨) **끌어도
아무 일이 없었다.** 저장소에는 아무것도 안 써졌다.

**원인**: 썸네일이 `<img>`다. 크롬은 이미지 위에서 누르고 움직이면 **네이티브 이미지 드래그**를
시작하며 **포인터를 가로채 `pointercancel`을 낸다.** 우리 상태가 초기화돼 `pointerup` 때
옮길 것이 없었다. 계측해 보니 `pointermove`가 **딱 1회** 돌고 끝나 있었다.

```ts
// 컨테이너 한 곳에서 막는다 — 다음에 순서를 바꿀 목록이 생겨도 자동으로 따라온다(§7 2층)
container.addEventListener('dragstart', (e) => e.preventDefault());
```
```css
.photo-thumb { -webkit-user-drag: none; user-select: none; }
```

- 🔴 **유닛으로는 원리적으로 못 잡는다.** `dropIndex`·`moveItem`·`orderPhotos` 유닛 19건이
  전부 초록이었고 타입도 옳았다. **틀린 것은 자료구조가 아니라 브라우저와의 계약**이었다
  (§10 ③의 확장형).
- **브라우저가 먼저 손대는 자리 목록**(제스처를 만들기 전에 훑는다): 이미지·링크의 네이티브
  드래그 · 텍스트 선택(길게 누르기) · 스크롤/줌(`touch-action`) · 컨텍스트 메뉴(길게 누르기) ·
  풀투리프레시. **길게 누르기는 특히 붐비는 자리다.**
- **재는 법은 하나뿐이다 — 실제로 눌러 본다**(§13 4항). 「라벨이 있다」와 「돈다」는 다른 말이다.

### 🔴 그리고 **막는 이벤트는 하나가 아니다** (2026-08-06 · M-0116 — 배포 뒤 사용자 실기기)

위 `dragstart` 차단으로 **마우스에서는 됐다.** 그리고 배포했다. 사용자 태블릿에서 **손가락으로는
안 됐다.**

| 플랫폼이 가져가는 것 | 막는 곳 |
|---|---|
| 이미지 네이티브 드래그 | `dragstart` + `-webkit-user-drag: none` |
| **터치 스크롤** | 🔴 **비수동 `touchmove`의 `preventDefault()`** — `pointermove`로는 **안 막힌다** |
| 롱프레스 컨텍스트 메뉴(안드로이드) | `contextmenu` |
| 텍스트 선택 | `user-select: none` |

```ts
// pointermove의 preventDefault는 터치 스크롤을 못 막는다 — 이게 그날의 결함이었다
window.addEventListener('touchmove', (e) => { if (dragging) e.preventDefault(); }, { passive: false });
```

### 🔴 **입력 장치도 「표면」이다 — 마우스로 재고 「된다」고 하지 마라**

라이브가 `page.mouse`로 재고 있었다. **터치에만 있는 갈래(브라우저의 스크롤 판정)를 원리적으로
볼 수 없는 입력**으로 돌면서 345/345 초록을 찍었다. 헌법 §17의 *"그 검사가 「문제가 날 수 있는
자리」에서 도는지 물어라"* 위반이고 — **그 조항을 같은 세션에 쓰고 같은 세션에 어겼다.**

- **재는 법**: 컨텍스트에 `hasTouch: true`, 입력은 **CDP `Input.dispatchTouchEvent`**.
  `page.touchscreen`은 탭만 되고, JS로 만든 `TouchEvent`는 **브라우저의 스크롤 판정을 재현하지
  못한다**(내가 만든 이벤트를 내가 재는 셈 · §3-E).
- **시작만 재지 마라.** 이 결함은 **들리기는 하고 중간에 죽는** 형태였다 — 「끄는 도중에도
  살아 있는가」를 따로 재야 잡힌다.

### 곁가지 둘 (같은 검사에서 잡혔다)

1. 🔴 **좌표계를 섞지 마라.** 미리보기를 `style.order`로 칸을 밀어 구현했는데, `order`는
   *화면 순서*를 바꾸고 `querySelectorAll`은 *DOM 순서*를 준다 — 한 번 밀고 나면 「몇 번째 칸
   위인가」와 「몇 번째로 옮기는가」가 **다른 것을 가리켰다**(M-0060의 형태). 미리보기를
   **자리 표시(클래스)**로 바꿔 좌표계를 하나로 만들었다. **끌 때는 아무것도 밀지 않는다** —
   실제 배열은 손을 뗄 때 한 번 바뀐다(취소해도 자료가 안 움직이는 이점이 덤이다).
2. **라이브 검사가 자기 픽스처를 소유해야 한다.** 드래그 대상을 인덱스(`boxes[0]`)로 집었는데
   같은 순간에 다른 블록이 남긴 사진이 쌓여 **첫 칸이 내 것이 아니었다.** 칸에
   `data-media-id`를 달아 **id로 집는다** — 그러면 형제가 늘어도 검사가 흔들리지 않는다.
   (썸네일 `src`는 objectURL이라 정체를 말해 주지 않는다. **검사가 대상을 지목할 손잡이가
   없으면 그 검사는 「개수 세기」로 약해진다.**)

## 3-J. **터치 표적과 반복 색인의 시각 밀도는 같은 값이 아니다** (2026-08-07 · M-0125)

홈 기간 트리는 모든 버튼에 44px 최소 높이를 주고 2px gap까지 반복해, 데스크톱에서 연·월 몇 줄이
내용보다 큰 패널을 만들었다. 44px는 터치 안전 계약이지 모든 입력 장치에서 행간을 고정하는 계약이
아니다. 다만 화면이 넓다는 이유만으로 줄이면 대형 터치 화면의 표적도 작아진다.

- 반복 색인을 압축할 때는 **화면 폭과 입력 장치**를 함께 가른다. 정밀 포인터만 조밀하게 하고
  터치는 기존 최소 표적을 유지한다.
- 주 선택(「전체」)과 반복 날짜 행을 같은 무게로 다루지 않는다. 주 선택은 표적을 유지하고 반복 행만
  줄이면 계층과 행동 우선순위를 함께 보존할 수 있다.
- 라이브 페이지가 터치로 열렸다면 정밀 포인터 CSS가 안 보이는 것이 정상이다. 한쪽 분기를 억지로
  공용 CSS로 바꾸지 않는다. 🔴 **같은 페이지에서 CDP로 touch만 껐다 켜지 마라** — Windows는
  `pointer:fine`으로 돌아오지만 Linux Chromium은 `pointer:none`에 머물 수 있다(M-0126).
  터치/정밀 포인터를 **별도 browser context**로 열고 같은 최소 픽스처를 각각 앱에 심어 계측한다.
- 수치는 행 높이와 gap을 재고, 캡처에서는 계층·개수 열·겹침을 본다. 둘 중 하나만으로 완료하지 않는다.

## 4. 검증 레시피

작업층: 관련 유닛·`npm run typecheck`·개별 게이트(`check-csp` 포함 — 새 외부 호스트를 쓰면
`index.html`과 게이트의 `REQUIRED`를 같은 커밋에 갱신)·아래 화면 실측. **전체 harness는
머지·배포할 릴리스 후보에서만**, `npm run build` 다음에 실행한다(헌법 §15).

라이브 측정(`node scripts/verify-editor-live.mjs` 확장):
```js
await page.setViewportSize({ width: W, height: H });
const m = await page.evaluate(() => ({
  overflow: document.documentElement.scrollWidth - document.documentElement.clientWidth,
  rect: document.querySelector('.타깃').getBoundingClientRect(),
}));
```
- 여러 폭을 훑고 **넘침 0**·의도한 배치(2단 여부)·요소 겹침 없음을 단언
- **콘솔 에러 0**까지 확인

시각 확인(수치로 못 잡는 것) — **이건 선택이 아니라 의무다**(CLAUDE.md §13):

- **화면을 바꿨으면 그 화면을 연다.** Playwright·Chromium이 이 환경에 있다. 사용자에게
  *"확인해 주세요"*라고 묻기 전에, **내가 열어서 스크린샷을 찍는 것이 질문보다 싸다** —
  질문은 왕복 수 분이고 캡처는 수십 초다. 사용자가 직접 지적했다(2026-07-28):
  *"니가 의심되는 부분에서 스크린샷 찍어서 확인하면 되는거 아냐?"*
- 스크린샷을 실제로 열어 본다(비율·여백·겹침). 다만 "확인함"은 **수치 단언과 함께** 적는다.
- **앱에서 만들 수 없는 상태**(서버가 특정 모양일 때만 나오는 화면 등)는 포기하지 말고
  **판정 함수에 직접 먹여 실제 렌더러로 그린다.** `verify-diagnostics-live`의 B층이 그 형태다 —
  픽스처를 `.diaglive/`에 세우고 진짜 `renderTool()`을 부른다(손으로 마크업을 세우면 §3-E대로
  *내가 쓴 마크업을 재는 것*이 된다).
- 🔴 **버튼을 만들었으면 눌러 본다**(헌법 §13 4항). 「그려진다」와 「돈다」는 다른 층이다 —
  누르면 ①결과 문장이 화면에 나오는가 ②재판정이 도는가 ③실패 사유가 보이는가 ④버튼이 잠기지
  않는가. **파괴적 버튼은 누르지 않는다**(§0): 「행동이 만들어지는가」로 재고 실행은 픽스처로.
- **못 열었으면 「라이브 렌더 미실행 / 사용자 확인 권장」이라고 적는다.** 안 본 것을 봤다고
  하지 않는다(비타협 원칙 #4). 색 대비·미세 정렬·실기기 촉감은 원래 이쪽이다(자동층이 아님).
