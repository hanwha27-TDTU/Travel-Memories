# 진단 도구 개발 프롬프트 (Diagnostics Dev Charter)

원칙의 정본은 `CLAUDE.md` **§7 수평전개와 대칭성** · **§8 진단 도구의 제1 규율**이다.
이 문서는 **작업 헌장** — 그 원칙을 실제 코드로 옮기는 법이다.

---

## 0. 이 도구들이 존재하는 이유

2026-07-25, "지운 것이 되살아난다"를 **네 번 진단해서 네 번 틀렸다.** 매번 진짜 결함을 찾긴 했지만
신고된 증상의 원인은 아니었다. 근본 원인은 결함이 아니라 **관측 불가**였다 — 서버는 볼 수 있어도
사용자 기기 안(대기열·tombstone·표식)은 볼 수단이 없어 매번 가설을 세우고 틀렸다.

진단 화면을 만들자 **한 번에** 풀렸다: `permanent_failed 1 / moment 1`이 박혀 있었다.

> 진단 도구는 편의 기능이 아니라 **CLAUDE.md §3("의도가 아니라 현실로 검증")을 지킬 수 있게 하는 전제조건**이다.
> 현실을 볼 창이 없으면 그 규율은 지킬 수 없다.

그리고 2026-07-26, 사용자가 그 화면을 실기기에서 보고 말했다:

> "뭐가 문제인지도 잘 모르겠고 **너무 나열되어** 있기도 하구요.
>  우리가 이런 도구를 만드는 건 **정상은 어떤 상태이고 문제가 발생한 게 뭔지 차이를 아는 것** 아닐까요?"

옳았다. 그때까지 화면은 *관측*을 했다 — 사실을 전부 같은 무게로 나열했다. 정상 항목 11개가 화면
대부분을 먹고 진짜 이상은 그 더미에 파묻혔다. **관측은 개발자용으로는 옳고 사용자용으로는 틀렸다.**

## 2. 판정 4단 — 왜 3단이 아닌가

| 판정 | 글리프 | 뜻 | 사용자가 할 일 |
|---|---|---|---|
| `ok` | ✓ | 기대값과 같다 | 없음 (화면에서 접힌다) |
| `todo` | ● | 지금 해두면 좋다 | 버튼 하나 |
| `problem` | ! | 지금 확인해야 한다 | 버튼 하나 |
| `unknown` | ? | **이 정보만으로는 판정 불가** | 대조 경로 안내 |

**`unknown`이 있는 이유가 이 설계의 핵심이다.** 진단에는 현재 증거로 판정할 수 없는 지표가 실제로
있다. op 없는 tombstone은 **로컬만으로는** "이미 서버에 갔다"와 "못 갔다"를 구분하지 못한다
(M-0008). 그래서 M-0095부터는 서버 행의 삭제 상태·version·operation id와 영구삭제 원장을
읽어 판정한다. 서버 tombstone이면 정상으로 숨기고, 서버 active면 `mergeDecision`으로 더 최신
복원을 보호한다. **서버 행도 원장도 없거나 조회가 불완전할 때만** `unknown`이며 자동 수정하지
않는다. 모르는 것을 정상이나 문제 어느 쪽으로 밀어도 거짓말이 된다(비타협 원칙 #4 정직한 완료).

색만으로 인코딩하지 않는다 — **글리프와 이름이 항상 함께** 간다(색각·흑백·계절 테마 대응).

## 3. 새 진단 도구를 추가하는 절차

### ① `probe()`를 쓴다 — 그리는 코드는 쓰지 않는다

```ts
export async function xxxProbe(): Promise<Verdict> {
  const metrics: Metric[] = [
    {
      label: '대상만 말한다',          // 상태를 라벨에 넣지 마라(옛 결함: "지움 + 보낼목록 없음  없음")
      actual: '지금 값',
      expected: '정상이면 이 값',       // ← 필수. 못 쓰면 지표가 아니다(§4 참조)
      level: cond ? 'problem' : 'ok',
      ...(cond ? { meaning: '무슨 뜻이고 무엇을 하면 되는지 한 줄' } : {}),
    },
  ];
  const level = levelFromMetrics(metrics);   // ← 손으로 적지 마라(자기모순 방지)
  return { level, headline: /* 결론 한 문장 */, metrics, actions: [], evidence: [], context: [] };
}
```

### ② 등록부에 넣는다

`CORE_TOOLS`에 `{id, icon, label, hint, lead, probe}` — **여섯 필드 전부**. 하나만 빠지는 게 최빈
결함군이라 게이트가 이걸 검사한다. 허브·롤업·요약이 자동으로 따라온다(손으로 세 곳을 고치지 않는다).

### ③ 검사 두 층을 붙인다

- `node scripts/check-verdict-symmetry.mjs` — 계약 이탈
- `tests/unit/` — 실제 실행으로 정상/이상이 구분되는가

### ④ 게이트에 알려진 실패를 주입해 RED를 확인한다 (§4)

```bash
# 예: 기대값을 지우고 게이트가 잡는지
```
잡히지 않으면 게이트가 공허한 것이다. 실제로 이 게이트도 처음엔 공허했다 —
`guide-card-icon`이 `guide-card-ic`를 부분문자열로 포함해 원래 결함을 그대로 통과시켰다.

## 4. 지표 감사 — 무엇을 최상위에 둘지 임의로 고르지 않는다

각 후보에 **"정상이면 이 값이다"를 쓸 수 있는가**를 묻는다. 답이 안 나오면 최상위가 아니다.

| 자격 | 위치 |
|---|---|
| 기대값을 쓸 수 있다 | **최상위 지표** (`metrics`) |
| 판정 불가 / 목록 / 기술코드 / 원문 | **접힌 출처** (`evidence`) |
| 상태가 아닌 환경 사실(앱 버전·시간대·저장소 종류) | **맥락** (`context`) |

옛 동기화 진단 5줄을 이 기준으로 감사한 결과:

| 옛 최상위 지표 | 기대값 | 판정 가능? | 옮긴 곳 |
|---|---|---|---|
| 대기 중인 작업 | — | 가능하나 **두 가지가 섞여 있었다** | 쪼개서 최상위 2개(막힌 작업 / 보낼 대기) |
| 지움 + 보낼목록 없음 | 정의 불가 | **불가**(소스가 자인) | 최상위에 남기되 `unknown` + 해소 경로 명시 |
| 지운 항목(이 기기) | 사용자 행동의 결과 | 불가 | 접힌 출처 |
| 영구삭제 표식 | 임의 | 불가 | 접힌 출처 |
| 사진 저장소 | 상태 아님 | 해당 없음 | 맥락 |

**"대기 중인 작업 3건"이 최악이었다** — *아직 안 보낸 것*(누르면 풀림)과 *보내다 막힌 것*(눌러도
안 풀림)을 한 숫자에 섞었다. 사용자가 해야 할 행동이 정반대인데 같은 줄에 있었다.

## 5. 화면 규율 (렌더러가 이미 강제하지만, 알고 써라)

1. **침묵이 정상이다.** `level: 'ok'`인 지표는 카드가 아니라 접힌 한 줄로 집계된다. 스크롤이 짧아지는
   게 목적이 아니라 **"남아 있는 것이 곧 문제"라는 규칙**이 생기는 게 목적이다.
2. **목록에 상한을 둔다.** 이 앱은 여행 사진 앱이다 — 수백 장이 정상이다. 상한이 없으면 수리 버튼이
   목록 뒤로 밀려 **진단 도구가 스스로 수리 경로를 막는다**(`ITEM_CAP`).
3. **조용히 자르지 않는다.** 잘랐으면 `외 N건 생략`이라고 라벨에 적는다. 조용한 절단은 "전부 봤다"로 읽힌다.
4. **주행동은 하나.** `primary: true`는 화면당 하나. 여러 버튼을 늘어놓으면 무엇을 누를지가 다시 사용자 몫이 된다.
4-B. **값을 받아야 하면 `Action.input`을 쓴다 — 도구가 입력 UI를 그리지 않는다.** 렌더러가 버튼 앞에
   입력칸을 붙이고 그 값을 `run(input)`에 넘긴다(`aria-label`·Enter 제출·`{hook}-input` 훅까지 한 곳에서).
   도구가 자기 입력칸을 그리기 시작하면 도구마다 다른 모양이 생기고, 그게 이 저장소에서 세 번 반복된
   결함군이다(§7). 쓰는 곳이 하나뿐일 때 렌더러에 넣어 둬야 **다음 도구가 자동으로 따라온다.**
5. **계산 전에 정상을 칠하지 않는다.** 빈 화면에 초록을 먼저 깔면 거짓말이다 — `확인 중…`으로 시작한다.
6. **액션 후 재판정한다.** 고쳤다고 말만 하고 옛 값을 들고 있으면 사용자는 고쳐졌는지 알 수 없다.
7. **화면 문자열에 마크다운을 쓰지 마라.** `textContent`로 그리므로 `**`가 그대로 찍힌다(실제 발생).
   강조가 필요하면 문자열이 아니라 `level`로 표현한다.
8. **hex·기술코드·UA는 출처 층에만.** 개인 여행 기억 앱에서 사용자가 자기 사진을 hex로 만나면 안 된다.
9. **라벨이 말할 수 있는 것만 말하게 한다.** 「저장 상태」의 기기 목록은 `updated_by_device`에서
   나오므로 **올린 기록만** 있다 — 받아만 간 기기는 흔적이 없다. 그래서 "마지막 동기화"가 아니라
   **"마지막으로 올림"**이라고 쓴다. 한 글자 차이가 거짓말과 사실을 가른다(2026-07-26).
10. **차이 ≠ 결함.** 클라우드와 개수가 다른 건 대개 "아직 안 올렸다/안 받았다"이고 동기화로 풀린다.
   → `todo`(할 일)이지 `problem`이 아니다. 진짜 실패는 동기화 도구가 따로 말한다. 겁주지 않는다.

## 6. 개인정보 규율

진단이 모으는 것은 **기기·브라우저 성질과 개수**뿐이다.

- 담는다: 앱 버전 · 화면 · 시간대 · 저장 용량 · 기능 지원 · 개수 집계 · 오류 메시지 · id **앞 8자리**
- 담지 않는다: 여행 제목 · 메모 · 사진 · 좌표 · 이메일

오류 로그는 **메모리 전용 링버퍼**다. Dexie에 쓰면 오류가 저장소를 오염시키고 백업 대상 판단도
흐려진다 — 새로고침하면 사라지는 게 맞다.

## 7. 자주 하는 실수 (전부 실제로 했다)

| 실수 | 왜 나쁜가 | 대신 |
|---|---|---|
| 정상 항목을 전부 나열 | 이상이 그 더미에 파묻힌다 | 접힌 한 줄 집계 |
| 값만 있고 기대값 없음 | 불안해질 수는 있어도 행동할 수는 없다 | `expected` 필수 |
| 판정 불가를 '문제'로 단정 | 거짓 경보는 결함만큼 해롭다(M-0008) | `unknown` + 해소 경로 |
| 도구마다 자기 렌더 코드 | 여섯 벌이 각자 흘러간다 | `renderTool()` 하나 |
| 심각도를 계절 강조색(`--a3`)으로 | 겨울엔 두 등급이 같은 파랑이 된다 | 시맨틱 토큰만 |
| 틴트 배경 위에 시맨틱 원색 텍스트 | 라이트에서 2.5:1로 무너진다 | `--sem-*-ink` |
| 상한 없는 목록 | 실사용자에게 수리 버튼 도달 불가 | `ITEM_CAP` + 생략 개수 |
| "1회 실행" 최적화 | 나중에 생긴 문제를 영영 못 잡는다 | 매번 대조 |

## 7-B. 진단 도구는 **상태 의존 결함의 게이트다** (CLAUDE.md §10)

2026-07-26에 결함 6건을 겪고 분류한 결과: **정적 게이트가 잡은 것은 0건**이었고, 그중 **둘은 원리적으로 정적 게이트가 잡을 수 없는** 부류였다.

| 부류 | 왜 정적 게이트가 못 잡나 | 어디서 잡나 |
|---|---|---|
| 상태 의존 — 저장소 혼재(M-0019), 옛 방식 잔재(M-0023) | **코드에 답이 없다.** 지금 데이터가 어떤 모양인지에 달렸다 | **진단 지표**(런타임) |
| 전달 — 판정 문장이 엉뚱함(M-0021), 확인해놓고 화면에 안 알림(M-0022) | **자료구조는 옳다** | 순수 함수 + `check-report-fields` + 실기기 |

**그래서 이 규율이 생긴다**: **과거 데이터가 어긋날 수 있는 변경을 하면, 그 어긋남을 진단 지표로 만든다.** 정적 게이트는 빌드 시점이고 진단은 런타임이다 — 그 층이 없으면 아무도 못 본다.

이미 그렇게 만든 것들: 「지웠는데 서버에 남은 항목」(M-0023) · 「파일이 없는 사진 기록」 · 「옛 저장소에 남은 사진」(M-0019) · **「복원했는데 서버가 막은 항목」(M-0032)**. 넷 다 *"코드는 맞는데 데이터가 옛 모양"*을 잡는다.

> **넷째가 이 규율을 가장 잘 보여준다.** 복원이 서버 원장에 막히던 결함은 코드를 고쳐 배포하면 *새로* 복원하는 사람에게는 안 난다. 그런데 **옛 판으로 이미 복원해 둔 사람은 여전히 그 상태**이고, 그를 데려올 층은 정적 게이트가 아니라 이 지표뿐이다. 그래서 **결함을 고칠 때 묻는다 — "이미 그 상태에 빠진 사람은 누가 데려오나?"** 답이 없으면 지표를 하나 만들어야 한다.

**지표는 정상이 되면 스스로 사라진다**(침묵이 정상). 실제로 복원이 성공하자 「복원했는데 서버가 막은 항목」과 「설명할 수 없는 사진 파일 10개」가 화면에서 함께 사라졌다 — 그게 이 계약이 제대로 도는 모습이다.

**그리고 지표를 만들었으면 고칠 곳도 만든다.** 2026-07-26에 「파일이 없는 사진 기록 2건」을 가리키는데 사용자가 **손댈 곳이 없었다** — 개별 삭제한 사진의 복구 UI가 없었기 때문이다(F5). 판정만 하고 행동을 못 주면 그건 관측으로 되돌아간 것이다.

## 7-D. **지표 자신이 틀릴 수 있다** — 오탐은 "빡빡한 진단"이 아니라 **틀린 진단**이다 (2026-07-27 · M-0034)

진단이 사진 9건을 「만든 시각이 고친 시각보다 늦음」으로 띄웠다. 실서버를 떠 보니 그 9행은
`created_at = updated_at`으로 **완전히 같았다.** 데이터는 처음부터 멀쩡했고, 틀린 것은 **판정식**이었다:

```ts
r.createdAt > r.updatedAt          // ← 문자열 대소. 표기가 다르면 같은 순간도 다르게 읽힌다
```

서버는 `…48.34+00:00`, 로컬은 `…48.340Z`로 **같은 순간을 다르게 적는다.** `'0'`(0x30) > `'+'`(0x2B).

- **판정식이 값의 *표기*에 의존하면 그건 판정이 아니라 우연이다.** 시각은 `compareInstants()`처럼
  **의미 단위로** 비교한다. 문자열 비교는 "정렬 키"일 때만 쓰고, 그때도 표기가 하나임이 보장돼야 한다.
- **하나의 발견에 두 원인이 섞이면 나눈다.** 「순간이 앞뒤가 안 맞는가」(`TIME_INVERSION`)와
  「표기가 우리 표준인가」(`BAD_TIME_FORMAT`)는 사용자가 할 일이 다르다 — 하나로 묶으면 둘 다 못 고친다.
- **오탐의 진짜 비용은 그 지표의 죽음이다.** 사용자가 무시하기 시작하면 진짜 시간 역전이 왔을 때
  아무도 안 본다(§11 ③과 같은 조항 — 게이트든 지표든 같다).
- **자문**: *"이 지표가 지금 켜져 있다면, 나는 그게 진짜 문제라고 서버에서 확인할 수 있는가?"*
  못 하면 켜기 전에 확인 경로부터 만든다. 이번엔 SQL 한 줄이 유닛 9건보다 먼저 답을 줬다(§9 4단계).

## 7-E. **과도한 `unknown`도 결함이다** — 판정 규칙이 지표의 질문과 어긋날 때 (2026-07-27 · M-0035)

총괄 판정이 `unknown`인데 하위 지표는 **전부 `ok`**였다. 끄는 것은 하나였다:

```
unknown  자동 동기화: 지금 마지막 성공 19:45:03 / 정상 최근에 성공   ← 보고서는 19:46:15
```

**72초 전에 성공했는데 판정 불가.** 판정이 `phase === 'ok'`일 때만 `ok`였고, 그 순간 동기화가
**한 번 더 돌고 있었다**(`running`). 그런데 문구는 그 사실을 말하지 않아 사용자는 이유를 알 수 없었다.

- **지표가 묻는 질문을 한 문장으로 쓰고, 판정을 그 질문에 맞춘다.** 이 지표의 질문은
  「자동 동기화가 **조용히 실패**하고 있는가」였는데, 판정은 「지금 상태가 정확히 `ok`인가」를
  재고 있었다. 둘은 다른 질문이다.
- **§8의 "모르는 것을 정상으로 반올림하지 않는다"는 *아는 것을 모른다고 하라*는 뜻이 아니다.**
  마지막 결과가 성공이면 "조용한 실패"의 답은 아니오다 — 그건 아는 것이다.
- **과도한 `unknown`의 비용**: 총괄 판정을 끌어내려 **정상 화면을 이상하게 보이게** 만들고,
  사용자는 매번 안을 열어 하나씩 확인해야 한다. §11 ③의 오탐과 같은 부류 — 지표가 틀리면
  사람이 그 지표를 안 본다.
- **`unknown`을 낼 거면 문장이 왜 모르는지 말해야 한다.** 「지금 동기화 중 — 이번 세션의 첫
  회차」처럼. `unknown` + 이유 없음은 사용자에게 **아무 정보도 주지 않는다.**
- **판정과 문장을 순수 함수로 뽑아라.** DOM 클로저 안에 있으면 갈래를 검사할 수 없다.
  `domain/syncStatusVerdict.ts`가 그 예이고, 유닛은 **level만이 아니라 문장도 잰다**(§10 ③).

## 7-C. 판정 문장의 세 가지 거짓말 (2026-07-26 · 근본형 B)

문장은 자료구조가 옳아도 틀릴 수 있다. 세 형태를 다 겪었다.

| 형태 | 실제 사례 | 처방 |
|---|---|---|
| **엉뚱한 곳을 가리킴** | 사진 파일이 문제인데 「클라우드와 다른 항목이 1가지」(M-0021) | 문장을 손으로 쓰지 말고 **무리별 개수에서 만든다** |
| **한정을 생략** | 「이 기기는 클라우드와 같습니다」 — 실제로 비교한 건 *살아 있는 항목 개수*뿐이었다(M-0028) | 문장에 **비교 대상**을 넣는다: 「살아 있는 기록 N건이 클라우드와 같아요」 |
| **시야의 경계를 안 밝힘** | 「사진 파일 0개」 — 실제로는 *내 폴더 기준*이지 저장소 전체가 아니었다 | 앱이 **자기가 못 보는 자리**를 지표로 말한다(「앱이 관리하지 않는 항목」) |

**쓰기 전에 자문할 한 문장:**

> **"이 문장이 다루지 *않는* 것은 무엇인가?"**

답이 있으면 그걸 문장에 넣거나, 옆에 지표로 세워라. 없다고 답하기 전에 두 번 생각하라 —
「같습니다」는 거의 항상 *무엇이* 같은지를 빠뜨린다.

### 빈 상태를 초록으로 칠하지 마라

활성이 **양쪽 다 0**일 때 `0 === 0`을 '같음'으로 판정했다. 그건 대조라기보다 **"비교할 것이
없다"**에 가깝다. 자료를 전부 휴지통으로 옮긴 사용자는 초록 「정상」을 보고 **자기 자료가 어디
있는지 모른 채** 화면을 떠난다.

```
alive > 0   → `살아 있는 기록 N건이 클라우드와 같아요`
alive === 0 && trashed > 0 → `살아 있는 기록이 없어요 — N건이 휴지통에 있습니다`
alive === 0 && trashed === 0 → `아직 기록이 없어요`
```

## 7-D. 지표를 만들었으면 **고칠 곳도 만든다** — 이걸 두 번 어겼다

§7-B에 이미 적혀 있는 규칙인데 2026-07-26에 **또** 어겼다. 「기록 없는 사진 파일 3개」를
정확히 잡아 놓고 앱 안에 손댈 곳이 없어, 사용자가 Cloudflare 콘솔을 직접 열었다.

같은 날 다른 자리에서도: [저장소 보호 요청]이 브라우저에 거절당하자 화면이
*"받아들이지 않았어요"*로 끝났다 — **그럼 어떻게 하면 되는지**를 안 알려줬다.

> 거절·실패도 **상태**다. "안 됐다"에서 멈추지 말고 **"그래서 무엇을 하면 되는가"**까지 말하라.
> 우리가 못 고치는 것이면(브라우저 정책 등) **사용자가 할 수 있는 행동**을 찾아 적어라.

## 7-E. 진단 요약은 **지표 숫자까지** 담는다 — 아니면 사용자가 사진을 찍는다

「진단 요약 복사」가 판정 한 줄씩만 담고 있었다. 복사해 봐야 숫자가 없으니 결국 화면을
사진으로 찍게 된다. 2026-07-26에 사용자가 그 이유로 스크린샷을 **수백 장** 찍었다.

지금은 `rollup()`이 지표까지 들고 오고 요약이 `지금 3개 / 정상 0개`까지 적는다.
**도구를 새로 만들면 자동으로 따라온다**(§7 2층) — 손으로 요약에 추가하지 않는다.

> 기능을 하나 더 만들기 전에 물어라: **지금 이 앱은 사람에게 무엇을 대신 시키고 있는가?**
> 답이 "화면을 사진으로 찍어 나르는 일"이면 그걸 먼저 없애라.

**해소 동작은 같은 판정을 실제로 해소해야 한다**(v1.64 · M-0095). `로컬 tombstone + 큐 없음`은
성공한 전송 뒤의 정상 모양이므로, [다시 확인]이 로컬 스냅샷만 다시 읽으면 영원히 같은 경고다.
서버 read-back이 필요한 판정은 그 해소 경로가 서버 증거를 가져와 판정 함수에 넣어야 한다.
증거 없이 op을 다시 만드는 [정리]는 해소가 아니라 새 쓰기이며, 최신 서버 복원을 덮거나 바이트를
다시 올릴 수 있으므로 금지한다. 서버 조회가 불완전하면 `unknown` 그대로 두고 자동 수정하지 않는다.
여러 표를 읽는 판정은 `canonical_version`을 전후로 읽어 같은 세대 snapshot인지 확인한다. 중간에
세대가 바뀌면 일부 옛 행+일부 새 행을 한 판정으로 섞지 말고 전체를 `unknown`으로 버린다.

## 7-F. **안 보는 것을 「0건」이라 말하지 마라** — 스냅샷에 빠진 도메인 (2026-07-27 · M-0040 ⑤)

`checkIntegrity(s)`는 `IntegritySnapshot`을 받는데, 오디오가 태어날 때 **그 타입에 안 들어갔다.**
결과: 부모 없는 소리도, 지운 순간에 살아남은 소리도, 옛 표기로 박힌 `recordedAt`도 전부
**「0건」**으로 보고했다. 0건은 *"정상이다"*로 읽힌다. 실제 뜻은 *"안 봤다"*였다.

§8이 금지하는 세 번째 거짓말(**모르는 것을 정상으로 반올림**)의 가장 조용한 형태다 — 지표가
자기 시야의 경계를 밝히지 않으면 그 숫자는 거짓이다.

### 처방 ① — 스냅샷 필드를 **선택이 아니라 필수**로

```ts
export interface IntegritySnapshot {
  trips: TripRowLike[]; moments: MomentRowLike[];
  media: MediaRowLike[]; expenses: ExpenseRowLike[];
  audio: AudioRowLike[];   // ← optional로 두면 다음 도메인이 또 조용히 빠진다
}
```
필수로 두니 **모든 호출부가 컴파일 오류로 끌려 나왔다**(화면 2곳 + 검사 3곳). 그게 목적이다.

### 처방 ② — 스냅샷 조립을 **한 곳**으로

`diagnostics.ts` 안에 같은 `Promise.all([...])`이 **두 벌** 손으로 적혀 있었다(진단 카드용·요약
텍스트용). 도메인을 더할 때 둘 다 고쳐야 하는 구조는 **반드시 한쪽을 빠뜨린다.**
→ `loadIntegritySnapshot()` 하나로 모으니 다음 형제는 여기만 고치면 전부 따라온다.

### 처방 ③ — 자식 검사는 **배열 한 곳**에서 돈다

`ORPHAN_PARENT`·`ALIVE_UNDER_DELETED`가 도메인마다 `...aliveX.filter(…)`를 손으로 나열하고
있었다. `parentChecks()`로 뽑아 **자식 종류를 배열 한 곳**에 모았다 — 새 자식은 한 줄이다.
(래칫이 이 추출을 밀어줬다: `checkIntegrity` 133 → 109줄. §2-C의 실례.)

### 안내문이 도메인마다 안 맞을 때 — **쪼개지 말고 묶어라**

`ALIVE_UNDER_DELETED`의 문구는 *"서버·저장소에는 남습니다"*인데 소리는 (당시) 서버에 안 갔다.
그래도 **같은 발견으로 묶었다**: 사용자가 고쳐야 할 상태가 동일하고, 소리만 별도 코드를 만들면
**같은 성격의 줄이 화면에 둘로 늘어난다**(§7 화면 대칭 위반). 문구의 미세한 부정확은 주석에
적고, 화면은 하나로 둔다.

## 7-C. 「없다」는 찾아보고 나서 하는 말이다 (M-0046, 2026-07-28)

배포 **30분 만에** 사용자 실기기가 잡았다. 그때 통과하던 것: 게이트 31종·유닛 686건·라이브 165건.

화면이 말한 것: *「지운 소리의 남은 기록 3개 · **소리 자체는 없습니다** — [정리]로 치울 수 있어요」*
사실: **로컬 휴지통에 그대로 있었다.** 그 버튼은 로컬 행까지 지운다 — 눌렀으면 녹음 20초가 사라졌다.

**어긋남을 세고 분류한 것까지는 옳았다.** 틀린 것은 그 다음 문장과 버튼뿐이다 — §10 ③(전달 결함).

규율 두 개가 여기서 나왔다:

1. **파괴적 행동을 권하기 전에 "이 기기에 사본이 있는가"를 묻는다.** 원칙 #4는 *모르는 것을
   반올림하지 마라*인데, 이건 한 걸음 더 나간 형태였다 — **묻지 않은 것을 안다고 말했다.**
   판정 함수(`classifyMissingFiles`)가 그 질문을 **구조적으로 강제**한다: `localBytes`를
   인자로 받으므로 안 묻고는 호출할 수 없다.
2. **정리를 권할 때는 찾아봤다는 사실을 함께 말한다** — 「이 기기에도 사본이 없습니다(찾아봤어요)」.
   근거 없는 삭제 권유는 §8의 「고쳤다고 말하지 말고 다시 읽어라」와 같은 부류의 위반이다.

그리고 **베낀 조건에는 베끼지 않은 전제가 붙어 있다**(같은 사고의 다른 겹): 사진의
`if (deletedAt === null)`은 "지운 건 안 올린다"가 아니라 "이미 올라가 있다"를 뜻했다.
형제 코드를 옮길 때 **조건이 아니라 그 조건이 참인 이유**를 옮겨라.

## 7-G. 🔴 「이 기기에 없다」는 「없다」가 아니다 (2026-07-28 · M-0048)

7-C를 고친 **다음 날**, 같은 근본형이 **기기 축**에서 다시 났다. 사용자가 두 기기의 스크린샷을
나란히 보냈다 — **같은 3건, 같은 서버 상태, 정반대 안내**:

| 기기 | 화면이 한 말 | 주버튼 |
|---|---|---|
| 태블릿(사본 있음) | 「서버에 파일이 없지만 **이 기기에는 그대로 있어요.** 자료는 안전합니다」 | [서버에 없는 자료 다시 올리기] |
| 폴드5(사본 없음) | 「**이 기기에도 사본이 없습니다**(찾아봤어요) — 치울 수 있어요」 | 🔴 **[지운 소리 기록 정리]** |

두 문장 다 *자기 기기에 대해서는* 참이었다. 틀린 것은 **폴드5의 결론**이다. 그 버튼은 서버
원장에 id를 올리고 트리거가 재등록을 영구히 거부하므로 **태블릿의 사본까지 못 되살리게** 된다.

> **한 기기에서 확인한 사실로 계정 전체를 판정하지 마라.** 「이 기기에 없다」와 「없다」 사이에는
> *다른 기기 N대*가 있다. 그리고 앱은 그 N을 **화면에 띄우면서도**(「내 기기들 2대」) 판정에는
> 쓰지 않고 있었다 — §12의 형태다: **앱이 아는 것을 판정에 안 썼다.**

### 규칙

- **파괴적 행동의 전제는 「어디에도 없다」이지 「여기 없다」가 아니다.** 다른 기기가 하나라도
  있으면 「확인 불가」로 내리고 **그 버튼을 만들지 않는다**(비활성이 아니라 **없음**).
- **막다른 문장으로 끝내지 않는다.** *"다른 기기에서 「앱 상태 확인」을 열어 [서버에 없는 자료
  다시 올리기]가 보이는지 확인해 주세요"* — 사용자가 **다음에 할 일**을 안다.
- **범위를 판정 함수의 인자로 받고, 기본값을 두지 마라.** 기본값이 있으면 새 호출부가 안 넘겨도
  컴파일된다 — 그게 이 규율이 조용히 빠지는 길이다(§7 2층: 누락이 컴파일 오류가 되게).
  실제로 인자를 필수로 만들자 컴파일러가 호출부 2곳과 유닛 9곳을 끌고 왔다.

### 같은 커밋에서 곁가지 하나 더 — **판정 문장이 종류 이름을 못 부르고 있었다**

배너가 「**사진** 파일에 확인할 것이 1가지 있어요」인데 사진은 9:9로 멀쩡했고 어긋난 것은
**소리**였다. `fileBad`가 소리까지 세게 됐는데 문장만 「사진」으로 못 박혀 있었다(§7 최빈형).
**바로 그 함수 위 주석이 같은 사고를 이미 적어 두고 있었다.**

> **숫자를 합치면 이름이 사라진다.** 종류별 집계는 **각 감사가 자기 이름을 들고 다니게** 한다
> (`fileAuditMetrics`가 `noun`을 반환) — 그러면 다음 형제(영상 등)가 자동으로 따라온다.

### 라이브 픽스처도 거짓말을 한다

이 수정을 재려고 `verify-diagnostics-live`에 판을 하나 더 넣었더니 **FAIL**이 났다. 그런데
앱은 옳았다 — **픽스처가** 버튼을 `recoverable` 하나로 손수 고르고 `else`로 「정리」를 붙이고
있었다. 앱의 계약은 *"목록이 비면 그 행동은 아예 없다"*인데.

> **주입 픽스처의 행동 목록도 판정에서 파생시켜라.** 손으로 고르면 §3-E의
> *「내가 쓴 마크업을 재는 것」*이 되고, 그때 초록/빨강은 앱이 아니라 **픽스처**를 가리킨다.

## 7-H. 🔴 **버튼은 눌러 봐야 확인한 것이다** (2026-07-28 · 헌법 §13 4항)

M-0046도 M-0048도 **버튼이 결함**이었다 — 「정리」를 권하면 안 되는 자리에서 권했다.
그런데 `verify-diagnostics-live`는 버튼의 **라벨만 읽고 한 번도 안 눌러 봤다.**

누른 뒤의 계약은 §8에 이미 있다 — *"고쳤다고 말하지 말고 **다시 읽어라**"*. 그 재판정이
실제로 도는지 아무도 재고 있지 않았다. **행동 하나에 네 가지를 잰다**(`renderTool`의 배선):

| 재는 것 | 안 재면 나는 결함 |
|---|---|
| 결과 문장이 **화면에 나오는가** | 계산해놓고 화면에 안 알림 — **M-0022의 행동판** |
| 누른 뒤 **재판정이 도는가**(probe 호출 수로 관측) | 「고쳤어요」라고 말만 하고 화면은 옛 판정 그대로 |
| 실패하면 **사유가 보이는가** | 조용히 삼킴 — 사용자는 성공한 줄 안다 |
| 버튼이 **다시 눌리는가** | 비활성으로 잠겨 재시도 불가 |

### 🔴 파괴적 버튼은 누르지 않는다

이 검사는 **사용자의 실제 기억을 담은 기기에서도** 돌 수 있다(§0 — 원본 자료를 임의로
지우지 않는다). 그래서:

- **파괴적 경로는 「행동 목록이 만들어지는가」로 잰다** — 있어야 할 때 있는가, **없어야 할 때
  없는가**(M-0048의 B③-2가 그 형태다: 다른 기기가 있으면 그 버튼이 **아예 없어야** 한다).
- **실행은 주입 픽스처의 가짜 `run()`으로만** 한다. 그러면 배선(§8 재판정·실패 표시)은 실제
  렌더러로 재면서 자료는 건드리지 않는다.
- 실제 앱에서 누르는 것은 **[다시 확인]처럼 읽기 전용인 행동**뿐이다.

### 픽스처의 행동 목록도 **판정에서 파생**시켜라

앱의 계약은 *"그 목록이 비면 그 행동은 아예 없다"*이다. 픽스처가 버튼을 손으로 고르면
§3-E의 **「내가 쓴 마크업을 재는 것」**이 되고, 그때 빨강/초록은 앱이 아니라 픽스처를
가리킨다 — 실제로 그렇게 한 번 헛디뎠다.

## 7-I. 🔴 **원인을 모를 때는 추측을 쌓지 말고, 아는 것을 화면에 내놓아라** (2026-08-01 · M-0066)

> 나흘 동안 *"왜 위치가 안 들어오나"*를 추측으로 좁혔고 **네 번 틀렸다.** 그 사이 사용자는
> 스크린샷을 **스무 장 넘게** 찍어 날랐다. **그런데 앱은 그 바이트를 손에 쥐고 있었다.**

§12는 *"지금 이 앱은 사람에게 무엇을 대신 시키고 있는가?"*라고 묻는다. 그 답이
**「앱 안의 사실을 사진으로 찍어 나에게 설명하는 일」**이면, 만들 것은 기능이 아니라 **관측 창**이다.

### 진단 도구의 두 종류 — 섞지 마라

| | **판정 도구**(§8) | **관측 창**(이 절) |
|---|---|---|
| 언제 | 정상 상태를 **안다** | 원인을 **모른다** |
| 무엇 | 기대값과 대조해 판정 | **사실만** 적는다 |
| 예 | 「서버에 없는 사진 3개 / 정상 0개」 | 「위치 칸은 있는데 값이 비어 있음 (N 0/0,0/0,0/0)」 |

§8은 *"관측이 아니라 판정을 하라"*고 말한다. **그건 정상을 아는 자리의 규율이다.**
원인을 모르는 자리에서 판정하면 **네 번 틀린 단정**이 화면에 나가고, 사용자는 엉뚱한 곳을 뒤진다.

### 관측 창의 계약

1. **판정어를 쓰지 마라.** 「~때문입니다」·「~가 지웠어요」 금지. **유닛이 RED로 잡게 하라** —
   조항만으로는 다음에 또 쓴다(실제로 M-0054에서 썼고 M-0056에서 철회했다).
2. **원자료를 가공하지 말고 그대로 보여라.** `N 36/1,36/1,32809680/1000000` — 십진수로 바꾸면
   **대조할 수 없다.** 사용자가 눈으로 맞춰 볼 수 있어야 한다.
3. **정상은 침묵한다.** 좌표를 얻었으면 상자 자체가 안 나온다(§8의 그 규율은 여기서도 산다).
4. **관측이 갈라지는 지점마다 행동을 하나씩** 준다. 관측만 던지면 사용자는 "그래서?"에 남는다.
5. 🔴 **사용자가 나를 검증할 수 있게 하라.** 해시를 적는 이유가 그것이다 — 폰의 원본과 직접
   대조하면 *"앱이 바꾸는 듯?"*이 추측이 아니라 **사용자가 확인한 사실**이 된다.
   **판단이 아니라 관측 수단을 준다.**

### 언제 만드는가

**사용자에게 같은 것을 두 번 물었으면 그때다.** 두 번째 요청은 *"내가 앱을 못 만들어서 사람이
대신 재고 있다"*는 신호다. 그리고 그 창은 **버그가 아니라 기능으로** 남는다 — 다음에 비슷한
증상이 오면 첫 질문이 *"그 줄 보내 주세요"* 하나로 끝난다.
