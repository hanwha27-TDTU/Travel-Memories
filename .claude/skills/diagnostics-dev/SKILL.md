# 진단 도구 개발 프롬프트 (Diagnostics Dev Charter)

원칙의 정본은 `CLAUDE.md` **§7 수평전개와 대칭성** · **§8 진단 도구의 제1 규율**이다.
이 문서는 **작업 헌장** — 그 원칙을 실제 코드로 옮기는 법이다.

---

## 0. 이 도구들이 존재하는 이유

2026-07-25, "지운 것이 되살아난다"를 **네 번 진단해서 네 번 틀렸다.** 매번 진짜 결함을 찾긴 했지만
신고된 증상의 원인은 아니었다. 근본 원인은 결함이 아니라 **관측 불가**였다 — 서버는 볼 수 있어도
사용자 기기 안(대기열·tombstone·표식)은 볼 수단이 없어 매번 가설을 세우고 틀렸다.

진단 화면을 만들자 **한 번에** 풀렸다: `permanent_failed 1 / moment 1`이 박혀 있었다.

> 진단 도구는 편의 기능이 아니라 **CLAUDE.md §3("의도가 아니라 현실로 검증")을 지킬 수 있게 하는 전제조건**이다.
> 현실을 볼 창이 없으면 그 규율은 지킬 수 없다.

그리고 2026-07-26, 사용자가 그 화면을 실기기에서 보고 말했다:

> "뭐가 문제인지도 잘 모르겠고 **너무 나열되어** 있기도 하구요.
>  우리가 이런 도구를 만드는 건 **정상은 어떤 상태이고 문제가 발생한 게 뭔지 차이를 아는 것** 아닐까요?"

옳았다. 그때까지 화면은 *관측*을 했다 — 사실을 전부 같은 무게로 나열했다. 정상 항목 11개가 화면
대부분을 먹고 진짜 이상은 그 더미에 파묻혔다. **관측은 개발자용으로는 옳고 사용자용으로는 틀렸다.**

## 2. 판정 4단 — 왜 3단이 아닌가

| 판정 | 글리프 | 뜻 | 사용자가 할 일 |
|---|---|---|---|
| `ok` | ✓ | 기대값과 같다 | 없음 (화면에서 접힌다) |
| `todo` | ● | 지금 해두면 좋다 | 버튼 하나 |
| `problem` | ! | 지금 확인해야 한다 | 버튼 하나 |
| `unknown` | ? | **이 정보만으로는 판정 불가** | 대조 경로 안내 |

**`unknown`이 있는 이유가 이 설계의 핵심이다.** 진단에는 로컬 정보만으로 판정할 수 없는 지표가 실제로
있다 — op 없는 tombstone은 "이미 서버에 갔다"와 "못 갔다"를 구분하지 못한다. M-0008에서 이걸
"서버로 못 간 삭제"라고 단정해 **거짓 경보**를 냈다. 모르는 것을 정상이나 문제 어느 쪽으로 밀어도
거짓말이 되므로 자기 칸을 준다(비타협 원칙 #4 정직한 완료).

색만으로 인코딩하지 않는다 — **글리프와 이름이 항상 함께** 간다(색각·흑백·계절 테마 대응).

## 3. 새 진단 도구를 추가하는 절차

### ① `probe()`를 쓴다 — 그리는 코드는 쓰지 않는다

```ts
export async function xxxProbe(): Promise<Verdict> {
  const metrics: Metric[] = [
    {
      label: '대상만 말한다',          // 상태를 라벨에 넣지 마라(옛 결함: "지움 + 보낼목록 없음  없음")
      actual: '지금 값',
      expected: '정상이면 이 값',       // ← 필수. 못 쓰면 지표가 아니다(§4 참조)
      level: cond ? 'problem' : 'ok',
      ...(cond ? { meaning: '무슨 뜻이고 무엇을 하면 되는지 한 줄' } : {}),
    },
  ];
  const level = levelFromMetrics(metrics);   // ← 손으로 적지 마라(자기모순 방지)
  return { level, headline: /* 결론 한 문장 */, metrics, actions: [], evidence: [], context: [] };
}
```

### ② 등록부에 넣는다

`CORE_TOOLS`에 `{id, icon, label, hint, lead, probe}` — **여섯 필드 전부**. 하나만 빠지는 게 최빈
결함군이라 게이트가 이걸 검사한다. 허브·롤업·요약이 자동으로 따라온다(손으로 세 곳을 고치지 않는다).

### ③ 검사 두 층을 붙인다

- `node scripts/check-verdict-symmetry.mjs` — 계약 이탈
- `tests/unit/` — 실제 실행으로 정상/이상이 구분되는가

### ④ 게이트에 알려진 실패를 주입해 RED를 확인한다 (§4)

```bash
# 예: 기대값을 지우고 게이트가 잡는지
```
잡히지 않으면 게이트가 공허한 것이다. 실제로 이 게이트도 처음엔 공허했다 —
`guide-card-icon`이 `guide-card-ic`를 부분문자열로 포함해 원래 결함을 그대로 통과시켰다.

## 4. 지표 감사 — 무엇을 최상위에 둘지 임의로 고르지 않는다

각 후보에 **"정상이면 이 값이다"를 쓸 수 있는가**를 묻는다. 답이 안 나오면 최상위가 아니다.

| 자격 | 위치 |
|---|---|
| 기대값을 쓸 수 있다 | **최상위 지표** (`metrics`) |
| 판정 불가 / 목록 / 기술코드 / 원문 | **접힌 출처** (`evidence`) |
| 상태가 아닌 환경 사실(앱 버전·시간대·저장소 종류) | **맥락** (`context`) |

옛 동기화 진단 5줄을 이 기준으로 감사한 결과:

| 옛 최상위 지표 | 기대값 | 판정 가능? | 옮긴 곳 |
|---|---|---|---|
| 대기 중인 작업 | — | 가능하나 **두 가지가 섞여 있었다** | 쪼개서 최상위 2개(막힌 작업 / 보낼 대기) |
| 지움 + 보낼목록 없음 | 정의 불가 | **불가**(소스가 자인) | 최상위에 남기되 `unknown` + 해소 경로 명시 |
| 지운 항목(이 기기) | 사용자 행동의 결과 | 불가 | 접힌 출처 |
| 영구삭제 표식 | 임의 | 불가 | 접힌 출처 |
| 사진 저장소 | 상태 아님 | 해당 없음 | 맥락 |

**"대기 중인 작업 3건"이 최악이었다** — *아직 안 보낸 것*(누르면 풀림)과 *보내다 막힌 것*(눌러도
안 풀림)을 한 숫자에 섞었다. 사용자가 해야 할 행동이 정반대인데 같은 줄에 있었다.

## 5. 화면 규율 (렌더러가 이미 강제하지만, 알고 써라)

1. **침묵이 정상이다.** `level: 'ok'`인 지표는 카드가 아니라 접힌 한 줄로 집계된다. 스크롤이 짧아지는
   게 목적이 아니라 **"남아 있는 것이 곧 문제"라는 규칙**이 생기는 게 목적이다.
2. **목록에 상한을 둔다.** 이 앱은 여행 사진 앱이다 — 수백 장이 정상이다. 상한이 없으면 수리 버튼이
   목록 뒤로 밀려 **진단 도구가 스스로 수리 경로를 막는다**(`ITEM_CAP`).
3. **조용히 자르지 않는다.** 잘랐으면 `외 N건 생략`이라고 라벨에 적는다. 조용한 절단은 "전부 봤다"로 읽힌다.
4. **주행동은 하나.** `primary: true`는 화면당 하나. 여러 버튼을 늘어놓으면 무엇을 누를지가 다시 사용자 몫이 된다.
4-B. **값을 받아야 하면 `Action.input`을 쓴다 — 도구가 입력 UI를 그리지 않는다.** 렌더러가 버튼 앞에
   입력칸을 붙이고 그 값을 `run(input)`에 넘긴다(`aria-label`·Enter 제출·`{hook}-input` 훅까지 한 곳에서).
   도구가 자기 입력칸을 그리기 시작하면 도구마다 다른 모양이 생기고, 그게 이 저장소에서 세 번 반복된
   결함군이다(§7). 쓰는 곳이 하나뿐일 때 렌더러에 넣어 둬야 **다음 도구가 자동으로 따라온다.**
5. **계산 전에 정상을 칠하지 않는다.** 빈 화면에 초록을 먼저 깔면 거짓말이다 — `확인 중…`으로 시작한다.
6. **액션 후 재판정한다.** 고쳤다고 말만 하고 옛 값을 들고 있으면 사용자는 고쳐졌는지 알 수 없다.
7. **화면 문자열에 마크다운을 쓰지 마라.** `textContent`로 그리므로 `**`가 그대로 찍힌다(실제 발생).
   강조가 필요하면 문자열이 아니라 `level`로 표현한다.
8. **hex·기술코드·UA는 출처 층에만.** 개인 여행 기억 앱에서 사용자가 자기 사진을 hex로 만나면 안 된다.
9. **라벨이 말할 수 있는 것만 말하게 한다.** 「저장 상태」의 기기 목록은 `updated_by_device`에서
   나오므로 **올린 기록만** 있다 — 받아만 간 기기는 흔적이 없다. 그래서 "마지막 동기화"가 아니라
   **"마지막으로 올림"**이라고 쓴다. 한 글자 차이가 거짓말과 사실을 가른다(2026-07-26).
10. **차이 ≠ 결함.** 클라우드와 개수가 다른 건 대개 "아직 안 올렸다/안 받았다"이고 동기화로 풀린다.
   → `todo`(할 일)이지 `problem`이 아니다. 진짜 실패는 동기화 도구가 따로 말한다. 겁주지 않는다.

## 6. 개인정보 규율

진단이 모으는 것은 **기기·브라우저 성질과 개수**뿐이다.

- 담는다: 앱 버전 · 화면 · 시간대 · 저장 용량 · 기능 지원 · 개수 집계 · 오류 메시지 · id **앞 8자리**
- 담지 않는다: 여행 제목 · 메모 · 사진 · 좌표 · 이메일

오류 로그는 **메모리 전용 링버퍼**다. Dexie에 쓰면 오류가 저장소를 오염시키고 백업 대상 판단도
흐려진다 — 새로고침하면 사라지는 게 맞다.

## 7. 자주 하는 실수 (전부 실제로 했다)

| 실수 | 왜 나쁜가 | 대신 |
|---|---|---|
| 정상 항목을 전부 나열 | 이상이 그 더미에 파묻힌다 | 접힌 한 줄 집계 |
| 값만 있고 기대값 없음 | 불안해질 수는 있어도 행동할 수는 없다 | `expected` 필수 |
| 판정 불가를 '문제'로 단정 | 거짓 경보는 결함만큼 해롭다(M-0008) | `unknown` + 해소 경로 |
| 도구마다 자기 렌더 코드 | 여섯 벌이 각자 흘러간다 | `renderTool()` 하나 |
| 심각도를 계절 강조색(`--a3`)으로 | 겨울엔 두 등급이 같은 파랑이 된다 | 시맨틱 토큰만 |
| 틴트 배경 위에 시맨틱 원색 텍스트 | 라이트에서 2.5:1로 무너진다 | `--sem-*-ink` |
| 상한 없는 목록 | 실사용자에게 수리 버튼 도달 불가 | `ITEM_CAP` + 생략 개수 |
| "1회 실행" 최적화 | 나중에 생긴 문제를 영영 못 잡는다 | 매번 대조 |

## 7-B. 진단 도구는 **상태 의존 결함의 게이트다** (CLAUDE.md §10)

2026-07-26에 결함 6건을 겪고 분류한 결과: **정적 게이트가 잡은 것은 0건**이었고, 그중 **둘은 원리적으로 정적 게이트가 잡을 수 없는** 부류였다.

| 부류 | 왜 정적 게이트가 못 잡나 | 어디서 잡나 |
|---|---|---|
| 상태 의존 — 저장소 혼재(M-0019), 옛 방식 잔재(M-0023) | **코드에 답이 없다.** 지금 데이터가 어떤 모양인지에 달렸다 | **진단 지표**(런타임) |
| 전달 — 판정 문장이 엉뚱함(M-0021), 확인해놓고 화면에 안 알림(M-0022) | **자료구조는 옳다** | 순수 함수 + `check-report-fields` + 실기기 |

**그래서 이 규율이 생긴다**: **과거 데이터가 어긋날 수 있는 변경을 하면, 그 어긋남을 진단 지표로 만든다.** 정적 게이트는 빌드 시점이고 진단은 런타임이다 — 그 층이 없으면 아무도 못 본다.

이미 그렇게 만든 것들: 「지웠는데 서버에 남은 항목」(M-0023) · 「파일이 없는 사진 기록」 · 「옛 저장소에 남은 사진」(M-0019). 셋 다 *"코드는 맞는데 데이터가 옛 모양"*을 잡는다.

**그리고 지표를 만들었으면 고칠 곳도 만든다.** 2026-07-26에 「파일이 없는 사진 기록 2건」을 가리키는데 사용자가 **손댈 곳이 없었다** — 개별 삭제한 사진의 복구 UI가 없었기 때문이다(F5). 판정만 하고 행동을 못 주면 그건 관측으로 되돌아간 것이다.

## 7-C. 판정 문장의 세 가지 거짓말 (2026-07-26 · 근본형 B)

문장은 자료구조가 옳아도 틀릴 수 있다. 세 형태를 다 겪었다.

| 형태 | 실제 사례 | 처방 |
|---|---|---|
| **엉뚱한 곳을 가리킴** | 사진 파일이 문제인데 「클라우드와 다른 항목이 1가지」(M-0021) | 문장을 손으로 쓰지 말고 **무리별 개수에서 만든다** |
| **한정을 생략** | 「이 기기는 클라우드와 같습니다」 — 실제로 비교한 건 *살아 있는 항목 개수*뿐이었다(M-0028) | 문장에 **비교 대상**을 넣는다: 「살아 있는 기록 N건이 클라우드와 같아요」 |
| **시야의 경계를 안 밝힘** | 「사진 파일 0개」 — 실제로는 *내 폴더 기준*이지 저장소 전체가 아니었다 | 앱이 **자기가 못 보는 자리**를 지표로 말한다(「앱이 관리하지 않는 항목」) |

**쓰기 전에 자문할 한 문장:**

> **"이 문장이 다루지 *않는* 것은 무엇인가?"**

답이 있으면 그걸 문장에 넣거나, 옆에 지표로 세워라. 없다고 답하기 전에 두 번 생각하라 —
「같습니다」는 거의 항상 *무엇이* 같은지를 빠뜨린다.

### 빈 상태를 초록으로 칠하지 마라

활성이 **양쪽 다 0**일 때 `0 === 0`을 '같음'으로 판정했다. 그건 대조라기보다 **"비교할 것이
없다"**에 가깝다. 자료를 전부 휴지통으로 옮긴 사용자는 초록 「정상」을 보고 **자기 자료가 어디
있는지 모른 채** 화면을 떠난다.

```
alive > 0   → `살아 있는 기록 N건이 클라우드와 같아요`
alive === 0 && trashed > 0 → `살아 있는 기록이 없어요 — N건이 휴지통에 있습니다`
alive === 0 && trashed === 0 → `아직 기록이 없어요`
```

## 7-D. 지표를 만들었으면 **고칠 곳도 만든다** — 이걸 두 번 어겼다

§7-B에 이미 적혀 있는 규칙인데 2026-07-26에 **또** 어겼다. 「기록 없는 사진 파일 3개」를
정확히 잡아 놓고 앱 안에 손댈 곳이 없어, 사용자가 Cloudflare 콘솔을 직접 열었다.

같은 날 다른 자리에서도: [저장소 보호 요청]이 브라우저에 거절당하자 화면이
*"받아들이지 않았어요"*로 끝났다 — **그럼 어떻게 하면 되는지**를 안 알려줬다.

> 거절·실패도 **상태**다. "안 됐다"에서 멈추지 말고 **"그래서 무엇을 하면 되는가"**까지 말하라.
> 우리가 못 고치는 것이면(브라우저 정책 등) **사용자가 할 수 있는 행동**을 찾아 적어라.

## 7-E. 진단 요약은 **지표 숫자까지** 담는다 — 아니면 사용자가 사진을 찍는다

「진단 요약 복사」가 판정 한 줄씩만 담고 있었다. 복사해 봐야 숫자가 없으니 결국 화면을
사진으로 찍게 된다. 2026-07-26에 사용자가 그 이유로 스크린샷을 **수백 장** 찍었다.

지금은 `rollup()`이 지표까지 들고 오고 요약이 `지금 3개 / 정상 0개`까지 적는다.
**도구를 새로 만들면 자동으로 따라온다**(§7 2층) — 손으로 요약에 추가하지 않는다.

> 기능을 하나 더 만들기 전에 물어라: **지금 이 앱은 사람에게 무엇을 대신 시키고 있는가?**
> 답이 "화면을 사진으로 찍어 나르는 일"이면 그걸 먼저 없애라.
