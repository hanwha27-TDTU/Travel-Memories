> 🔴 **이 파일은 생성물이다. 여기를 고치지 마라.**
> 정본은 `docs/CONSTITUTION.md`이고, 이 문서는 거기서 **릴리스에 관한 절만 모아** 심은 것이다.
> 고치려면 `docs/CONSTITUTION.md`를 고치고 `node scripts/gen-harness-law.mjs`를 돌린다.
> `check-adapter-parity`가 「커밋본 == 재생성본」을 강제한다(CLAUDE.md·AGENTS.md와 같은 계약).
>

> 스스로 주워 모아야 했다. 그리고 이 규율들은 **다른 앱에 이식하는 것이 실제 용도**인데
> 그때 건네줄 파일이 없었다 — 이 파일 하나면 된다.
>

## 하네스·릴리스 법 (§18 — 사용자 지시 2026-08-06 · 외부 문서 「Harness and Release Law」 검토 도입)

> 사용자가 외부 프롬프트(HRL v1.1 · 모델 무관)를 가져와 *"우리 앱에도 적극 도입 검토하자"*고 했다.
> 조문별로 대조해 보니 **절반 이상은 이 헌법에 이미 있었다.** 그래서 **복사하지 않는다** —
> §2가 말하듯 **손편집 중복 자체가 결함**이고, 복사하면 정본이 둘이 되어 갈라진다.
>
> **여기에는 우리에게 비어 있던 것만** 적고, 이미 있는 것은 **가리키기만** 한다.

### §18-A. 🔴 검증 명령을 파이프에 넣지 않는다 — 판정은 **종료코드**로

```bash
npm run harness 2>&1 | grep -E "FAIL"        # ✗ 종료코드는 grep의 것이다
npm run harness > /tmp/r.log 2>&1; echo "EXIT=$?"; tail -20 /tmp/r.log   # ✓
npm run harness && echo OK || echo FAILED                                 # ✓ 종료코드를 본다
```

**왜 이 조문이 첫 번째인가**: 이 저장소가 **실제로 가장 많이 어긴 것**이기 때문이다.
2026-08-06 세션에서 이 형태를 수십 번 썼다 — 출력 문자열을 눈으로 읽어서 살았지,
**종료코드로 판정한 적이 없다.** 초록을 보고 싶은 사람과 초록을 만들어 주는 파이프가 만나면
그 검사는 정보가 없다.

**기계 층**: 게이트로는 원리적으로 못 잡는다(파일이 아니라 **내가 치는 명령**에서 깨진다) →
**PreToolUse(Bash) 훅**이 차단한다(`scripts/hook-verify-exit.mjs` · S-09). 자체검사 양성 5·음성 6.

**대리 지표 금지도 같은 조문이다.** *"X가 끝나면 Y가 생긴다"*가 참이어도 **"Y가 생기면 X가 끝났다"**는
거짓일 수 있다. 역이 성립하지 않는 신호로 완료를 판정하지 마라 — **결론을 직접 물어라**
(워크플로면 run conclusion, 스크립트면 종료코드).

### §18-B. 재실행 범위 — 실패한 그룹만, 그리고 **그 검사가 이번 변경을 보는가**

- 검사 하나가 빨간불이면 **그 검사가 속한 그룹만** 다시 돈다. 멀쩡히 통과한 그룹을
  「불안해서」 다시 돌리지 않는다.
- 🔴 **재실행 전에 물어라**: *이 검사가 이번 변경을 볼 수 있는가?* 바꾼 심볼·파일로 검사 소스를
  `grep`해서 **0건이면 모집단이 0**이고, 나올 초록은 「위반 없음」이 아니라 **「아무것도 안 봄」**이다.
  이건 §17의 *"그 검사가 「문제가 날 수 있는 자리」에서 도는지 물어라"*와 같은 질문이다.
- 우리 가장 비싼 그룹은 `verify-*-live`(브라우저)다. **그 층이 빨간불일 때만** 다시 돈다.

### §18-C. 병렬이 기본 — 직렬은 **의존이 있을 때만**

낭비되는 시간의 대부분은 대기가 아니라 **병렬로 할 수 있는 것을 줄 세운 것**이다.

이 원칙은 조사·검사·배포뿐 아니라 **앱 런타임 오케스트레이션과 동기화 도메인**에도 그대로
적용한다. 같은 단계의 작업이 서로의 결과를 입력으로 쓰지 않으면 병렬이 기본이다.

**직렬 판정 기준(이것만)**: 앞의 결과가 뒤의 입력인가? 순서가 바뀌면 뒤의 증거가 무효가 되는가?

```
소스·버전 확정 → build        번들이 그 소스를 품는다
build → harness·live          증거는 그 번들을 포함한 트리에서 나와야 한다
CI 초록 → 머지 → 배포
```

**그 밖에서 「앞의 것이 끝나야 안심된다」로 줄 세우는 것은 의존이 아니라 습관이다.**
병렬로 해야 하는 것: 조사·탐색 · 리뷰 렌즈 · 서로 다른 파일을 보는 검사 · 독립 배포 표면.

🔴 **직렬 경계에는 구체적 사유가 필수다.** `안전을 위해`·`기존 순서라서`·`한 번에 하나씩`은
사유가 아니다. 다음 둘 중 하나를 **정확한 값·자원·증거 이름으로** 적는다.

1. 앞 단계의 어떤 출력이 뒤 단계의 어떤 입력이 되는가.
2. 어떤 공유 자원이나 read-back 증거가 겹쳐, 순서를 바꾸면 무엇이 무효가 되는가.

코드 오케스트레이션은 가능하면 병렬 그룹과 직렬 간선을 **타입 있는 실행 계획 데이터**로 둔다.
첫 단계 이후의 각 간선은 `reason` 같은 필수 필드를 가져야 하며, 새 형제가 들어올 때 병렬 그룹과
의존성을 선택하지 않으면 컴파일·게이트가 실패해야 한다. 산문 주석만으로 줄 세우지 않는다.

🔴 **병렬 실패도 합류(join) 뒤에 보고한다.** 부수효과가 있는 형제 중 하나가 실패했다고 즉시
반환하면 나머지 쓰기는 뒤에서 계속되어 다음 단계·다음 실행과 겹친다. 같은 단계의 모든 형제를
성공/실패로 정산한 뒤 실패를 반환한다. 조기 reject를 완료 경계로 쓰지 않는다.

병렬 전 확인 셋: ①**같은 자원을 쓰는가**(겹치면 병렬이 아니라 직렬이거나 격리)
②**결과를 합칠 자리와 실패 처리를 먼저 정했는가** ③**침묵을 관측할 수 있는가**
(못 하면 대리 지표에 속는다 — §18-A).

PR과 완료 보고에는 **병렬 그룹**과 **직렬 간선+각 사유**를 적고, 요약은
**「직렬 N구간 + 병렬 M구간」**으로 쓴다. 「28분 걸렸다」는 정보가 없다.

### §18-D. 자동화도 하나의 표면이다

러너·크론·백그라운드 잡은 **사람과 같은 권한으로 같은 브랜치·파일**을 쓴다.
맡긴 동안 그 자원을 건드리지 마라 — 급하면 끝난 뒤에 한다.

이 저장소에 걸리는 자리: **APK 워크플로가 도는 동안 같은 브랜치에 푸시하지 않는다**
(러너가 `[rejected] fetch first`로 죽으면 정상적으로 만들어진 산출물이 통째로 버려진다).

🔴 **규칙의 범위를 예시로만 적지 마라 — 예시 밖은 지켜지지 않는다.**

### §18-E. 산출물이 품는 소스가 바뀌면 산출물을 다시 만든다

**패키징 산출물은 소스 확정이 끝난 뒤에 만든다.** 만든 뒤 소스를 또 바꾸면 해시·버전이 낡는다.

```
소스·생성물·버전·이력 확정 → 좁은 검사 → 커밋 → 산출물 빌드 → 전체 검사 한 번 → 머지 → 배포
```

⚠️ **문서만 고쳐도 소스가 바뀔 수 있다** — 생성물(문서 목록·버전·레지스트리)이 소스 안에 박혀
있기 때문이다. 판정 기준은 「거동이 바뀌었나」가 아니라 **「그 파일이 실제로 바뀌었나」**이고,
**기계에게 묻는다.**

**우리 형태**: 이 저장소는 APK를 **커밋하지 않고** 고정 릴리스에 올리므로, 원문의
`check-release-order.mjs`(산출물 커밋 뒤 소스 커밋 검출)를 그대로 쓸 대상이 없다.
같은 근본형은 이미 세 곳이 지킨다 — `verify-*-live`의 **dist 낡음 차단(exit 2)** ·
`gen-registry` · `check-adapter-parity`. **비어 있는 것은 APK 쪽**이고, 그건
`android-apk-dev` 헌장이 다룬다.

### §18-F. 🔴 앱과 서버가 따로 배포되면 **제공자를 하위 호환으로 먼저 배포하고 정확한 실물을 되읽는다**

앱이 기대하는 Edge Function·DB capability·외부 저장소 계약이 바뀌면, 앱과 서버를 같은
릴리스라고 불러도 **실제로는 서로 다른 시각에 배포되는 두 표면**이다. `FN_VERSION=6` 같은
프로토콜 번호는 *무엇을 할 줄 아는가*를 말할 뿐, **오늘 고친 소스가 운영에 올라갔는가**를
증명하지 않는다. 같은 버전 안의 수정·재시도·timeout·CORS·진단 필드도 배포 누락될 수 있다.

그래서 소비자 앱보다 제공자 표면을 먼저 배포하는 릴리스는 다음 순서를 지킨다.

1. **정본과 생성물을 먼저 고정한다.** 프로토콜·필수 연산·논리 소스 해시의 정본을 하나만 두고,
   Edge 상수와 앱 계약은 거기서 생성한다. 생성 뒤 Edge 본문이 바뀌면 해시부터 다시 만든다.
2. **새 제공자는 구형 앱을 계속 받아야 한다.** Edge 선배포 창에서 현재 운영 앱의 요청이 깨지면
   선배포가 아니라 즉시 장애다. 하위 호환이 불가능한 변경은 capability 세대나 단계적 migration을
   별도로 설계하고 같은 릴리스에 숨기지 않는다.
3. **제공자를 먼저 배포한 뒤 운영 응답을 직접 읽는다.** 배포 명령 성공이나 함수 revision 증가는
   대리 지표다(§18-A). 운영 `capabilities`의 **정확한 소스 해시**, 프로토콜, 필수 연산, 필요한
   시크릿 준비 상태를 릴리스 계약과 대조한다.
4. **운영 대조가 통과한 뒤에만 Ready PR·앱 배포를 연다.** 불일치·조회 실패·환경변수 부재는
   `unknown` 또는 실패이지 통과가 아니다. 앱을 먼저 올려 사용자 기기에서 시험하거나 사용자
   자료를 고쳐서 확인하지 않는다.
5. **앱 배포 뒤 두 표면을 다시 되읽는다.** Pages/APK 버전과 서버 계약이 모두 기대값이어야
   완료다. 하나만 초록이면 §15가 말하는 배포 완료가 아니다.

**현재 적용 표면 — `media-sign`.** `schemas/sync-release-contract.json`이 protocol·필수 op·
LF 정규화 논리 소스 SHA-256의 정본이다. `check-sync-release-contract`는 정본↔Edge↔앱 생성물을,
`verify-sync-release-live`는 운영 `capabilities`를 대조한다. Ready PR의 Required harness와 Pages
배포가 같은 운영 대조를 통과해야 한다. 기기의 「동기화 출고 점검」은 같은 계약을 읽기 전용으로
판정하며, 사용자 자료를 수정·삭제하는 복구 버튼을 갖지 않는다.

새 독립 서버 표면이 생기면 `schemas/release-profile.json`에 영향 조건·배포 주체·권위 있는
read-back을 등록하고, 위와 동등한 **정적 동일성 검사 + 운영 실물 검사**를 갖추기 전에는
앱 릴리스의 전제라고 부르지 않는다.

### §18-G. 🔴 게이트는 **자기가 사는 세계**를 가정하지 않는다 — 없는 세계에서 한 번 돌려 본다

> **실측(2026-08-09 · M-0135)**: 로컬 하네스가 **전부 초록**인 커밋이 CI에서 죽었다.
> 범인은 그날 내가 만든 게이트였고, 하는 일은 한 줄이었다 — `git diff origin/main...HEAD`.
> 로컬에는 `origin/main`이 있다. `actions/checkout`의 얕은 체크아웃에는 **없다.**

**왜 조항이어야 하나**: 🔴 **로컬 하네스는 이 부류를 원리적으로 못 잡는다 — 자기가 사는
세계에서 도니까.** 그래서 「조심하자」로는 절대 안 지켜지고, 검출은 언제나 CI가 한다.
그런데 CI에서 잡히면 이미 릴리스 묶음 한복판이라 §18-H의 값까지 함께 치른다.

**정확히 무엇이 결함이었나 — 죽음을 위반으로 보고했다.** 이 저장소의 계약은 이미 셋이다:

```
exit 0 = 통과      exit 1 = 재보고 위반을 찾음      exit 2 = 전제 미충족(SKIP)
```

전제가 없을 때 게이트가 **예외를 스택째 뱉으면** 종료코드는 1이 되고, 하네스는 그것을
「위반을 찾았다」로 적는다. 그 문장은 거짓이다 — 게이트는 판정한 게 아니라 **죽었다**.
`unknown`을 통과로 반올림하지 않는 규율(§8)의 **거울상**이다: 모르는 것을 *위반*으로도
반올림하지 않는다.

**규칙.**

1. **전제가 없으면 판정하지 말고 말한다.** 없는 세계를 만나면 `exit 2`(SKIP)로 나가거나,
   그 창만 빼고 판정하고 「확인 불가: …는 재지 못했습니다」를 화면에 적는다.
2. **게이트마다 가정하는 세계를 원장에 적는다.** 어휘는 동결이고(`baseRef`·`dist`·
   `globalSkills`·`network`·`browser`·`runtimeEnv`), **아무것도 가정하지 않으면 빈 문자열을
   적는다** — 빈칸과 「아직 안 봤다」는 다른 말이므로 누락은 RED다.
3. 🔴 **선언은 산문이므로 믿지 않는다 — 벗겨서 돌려 본다.** 얕은 체크아웃과 같은 모양의
   **빈 세계 사본**(작업트리·색인·HEAD는 있고 `origin/*`·`dist/`는 없음)을 만들어 싼 게이트를
   전부 한 번 돌린다. 집에서는 초록인데 거기서 빨간불이면, 그 게이트는 세계를 가정한 것이다.
4. **새 게이트도 예외가 아니다.** 사본은 **추적 파일 + 아직 커밋 안 한 파일**을 함께 옮긴다 —
   이 검사가 가장 필요한 순간이 *방금 만든 게이트*이기 때문이다(M-0135가 그랬다).

**이 조항이 기대는 세 층 (§7)**

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 조항 | 이 절 | `docs/CONSTITUTION.md` → 두 어댑터 |
| ② 구조 | `GATE_WORLD` 원장 — 없는 게이트는 RED이므로 **다음 형제가 자동으로 따라온다** | `src/app/gates.ts` |
| ③ 기계 | **빈 세계 시연** — 매 실행마다 카나리아(`rev-parse origin/main`)로 *세계가 실제로 벗겨졌는지* 먼저 증명하고, 그 위에서 게이트를 돌린다 | `check-env-assumption` |

**정직한 한계**: 벗길 수 있는 세계는 둘(`baseRef`·`dist`)뿐이다. 나머지 넷은
**재지 않았고**, 원장 선언으로만 안다 — 판정문이 그렇게 말한다. 그리고 빈 세계는 게이트가
**죽지 않는지**까지만 본다. 판정 *내용*이 옳은지는 여전히 보지 못한다.

### §18-H. 🔴 릴리스 검증이 시작되면 저장소를 **얼린다** — 다시 여는 것은 결정이고, 결정은 세어진다

> **실측(2026-08-09 · v2.07)**: CI가 네 번 돌았다. 필요한 것은 **한 번**이었다.
>
> | run | 결과 | 커밋 | 시각 |
> |---|---|---|---|
> | #552 | **failure** | 04b3abfb | 18:33 → 18:37 |
> | #553 | **cancelled** | b8ff17fb | 18:41 → 18:43 |
> | #554 | success | 2d672fdc | 18:43 → 18:47 |
> | #555 | success | 06c7d668 | 19:11 → 19:14 |
>
> 검증 자체는 **3~4분**이다. 첫 Ready부터 마지막 초록까지는 **41분**이 걸렸다.
> 사용자가 물었다 — *"왜 이렇게 배포가 길어지니?"* 답은 CI가 아니라 **나**였다.
> #552는 §18-G가 막을 결함이고, **#553·#555는 순전히 내가 검증 중에 커밋을 얹어서 생겼다.**

**왜 조항이 필요한가 — 값이 안 보였다.** §15가 이미 *"하네스 뒤 코드를 바꾸면 묶음이
깨진다"*고 적어 뒀다. 그런데 조항은 **커밋을 치는 순간에 아무 말도 하지 않는다.**
그리고 `concurrency: cancel-in-progress`가 켜져 있으므로, 「커밋 하나 더」의 값은
커밋 하나가 아니라 **돌고 있는 검증을 버리고 처음부터**다. 안 보이는 값은 계산되지 않는다.

**규칙.**

1. **릴리스 검증을 시작할 때 얼린다**(`npm run release:arm <후보>`). 얼어 있는 동안
   **새 이력을 만드는 것**(`commit`·`merge`·`rebase`·`cherry-pick`·`revert`)이 막힌다.
   **조사·읽기·후보 push는 자유다** — 막으면 사람이 장치를 꺼 버리고, 꺼진 장치는 없는
   장치다. 🔴 첫 실사용에서 `push`까지 막았다가 **릴리스 후보를 올리는 일 자체가 막혔다**
   (v2.08). 규율이 막으려는 것은 push가 아니라 **검증 뒤에 생긴 새 커밋**이고, 커밋이
   막혀 있는 동안 push가 나를 수 있는 것은 이미 검증된 이력뿐이다.
2. **다시 여는 것은 금지가 아니라 기록이다**(`npm run release:reopen -- "<이유>"`).
   빨간 게이트를 고치려고 다시 여는 것은 **정당하다.** 다만 이유를 적고, 그 순간
   묶음은 「다시 열렸다」로 **세어진다**. 이유 없는 예외를 막고 세는 것은 이 저장소가
   이미 쓰는 형태다(§7의 `NO_OP_REQUIRED`).
3. **급하지 않은 변경은 배포 확인 뒤에 따로 올린다.** 후속과제·문서 정리가 여기 해당한다 —
   v2.07에서 CI를 두 번 더 돌린 것이 정확히 이 부류였다.
4. **완료 보고에 재개방 횟수를 적는다.** 「41분 걸렸다」는 정보가 없다.
   **「검증 1회 + 재개방 N회」**가 정보다(§18-C의 「직렬 N구간 + 병렬 M구간」과 같은 규율).
5. **묶음을 닫는 것은 배포 그린 확인 뒤다**(`npm run release:close`). 머지가 아니라 배포다
   (「완료의 정의」).

**이 조항이 기대는 세 층 (§7)**

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 조항 | 이 절 | `docs/CONSTITUTION.md` → 두 어댑터 |
| ② 구조 | 묶음의 경계를 **물건으로** 만든다 — 상태와 재개방 이유가 파일에 남는다 | `scripts/release-lock.mjs` |
| ③ 기계 | **PreToolUse(Bash) 훅이 얼어 있는 동안 커밋을 차단**하고, 막힐 때 그 값(취소·재시작)을 화면에 적는다 | `scripts/hook-release-freeze.mjs` · `check-hooks-wired` |

**정직한 한계**: 이 잠금은 **AI의 명령**만 막는다(PreToolUse 훅). 사람이 터미널에서 직접
치는 것은 보지 못한다. 그리고 잊고 넘어간 잠금이 다음 사람을 영원히 막지 않도록
**3시간이 지나면 스스로 풀린다** — 판정 불가는 통과시킨다는 다른 훅들과 같은 자세다.

### §18-I. 🔴 **날짜는 손으로 적는 값이라 조용히 낡는다 — 머지 전에 다시 잰다** (사용자 지시 2026-08-13)

> 사용자: *"날짜 관련 정보들 정합성 판단은 머지 전에 다시 한 번 체크해보게 헌법에 명시하는 건
> 어떨까? 그래야 날짜가 넘어가는 시점과 틀려졌을 때를 미연에 방지할 수 있을 것 같은데?"*

**왜 조항인가 — 재보니 막아 주는 층이 하나도 없었다.** 지시를 받고 먼저 실측했더니
**적어 둔 날짜를 오늘과 대조하는 게이트가 단 하나도 없었다.** 즉 날짜가 낡아도 CI는 초록이다.
안전해서가 아니라 **아무도 안 보고 있어서** 안 터지던 것이다.

그 값은 같은 날 치렀다. 세션 도중 날짜가 08-12 → 08-13으로 넘어갔고, 실수 원장에
`2026-08-12`를 적었다. **하네스의 게이트가 전부 초록**이었고 사람이 눈으로 발견했다.

🔴 **이 부류가 왜 특별히 잘 새는가**: 날짜는 **작업을 시작할 때의 사실**인데 **끝날 때 커밋**된다.
그 사이에 날이 바뀔 수 있고, 바뀌어도 **아무 신호가 없다.** 코드는 틀리면 컴파일이 깨지고
계약은 틀리면 게이트가 잡는데, 날짜는 **틀린 채로 완벽히 동작한다.**

### 규칙

1. **릴리스 묶음을 얼렸으면**(§18-H `release:arm`) **최신 CHANGELOG 항목의 날짜가 오늘이어야 한다.**
   그 항목의 날짜는 정의상 **머지·배포일**이기 때문이다(`src/app/changelog.ts`의 자기 계약).
2. **미래 날짜는 언제나 위반이다.** 릴리스 여부와 무관하게 늘 잰다 — 앞당겨 적은 날짜는
   오타이거나 아직 일어나지 않은 일을 일어났다고 적은 것이다(비타협 원칙 #4).
3. 🔴 **얼리지 않았을 때는 최신 항목 날짜를 재지 않는다.** §15의 축적 기간에는 최신 항목이
   「지난 릴리스」라 **과거인 것이 정상**이다. 여기서 재면 정상을 위반으로 잡고, 그런 게이트는
   사람이 무시하기 시작해 죽는다(§11 ③).
4. 🔴 **시간대 하루 차이는 위반이 아니다.** CI는 UTC이고 사용자는 KST(+9)다. KST 아침은 UTC로
   아직 전날이다. 그러므로 잡는 것은 「시간대 차이」가 아니라 **「이틀 이상 낡은 날짜」**다.

### 🔴 날짜는 **한 사례일 뿐이다** — 근본형은 「자동 옆의 수동」이다 (2026-08-13 확장)

날짜가 특별히 잘 새는 이유를 한 겹 더 파면 **날짜여서가 아니다.** *자동으로 갱신되는 값
바로 옆에 사람이 적는 값이 있으면 그 수동 값은 반드시 밀린다.* 버전은 릴리스마다 자동으로
오르는데 그 옆 날짜는 손으로 적히니, 갈라지는 것은 시간 문제였던 것이다.

그러므로 **자동과 수동이 같은 선언·같은 표·같은 객체에 섞여 있는 자리를 찾으면** 다음을 밟는다.

1. **먼저 파생을 시도한다.** 값을 한 번 고치는 것은 다음 판에서 또 밀리는 것을 막지 못한다 —
   **손으로 적는 자리 자체를 없애는 것**이 수정이다(§2의 「파생물은 스크립트로 재생성」).
2. **기대값 계산을 한 함수에 두고 생성기와 게이트가 그것을 함께 쓴다.** 게이트가 기대값을
   따로 계산하면 둘이 갈라지고, **갈라진 쪽은 조용해진다**(M-0060).
3. **파생 불가면 관계를 게이트로 잠근다** — 「A가 바뀌었으면 B도 바뀌어야 한다」. 그리고
   §4에 따라 **실제로 어긋났던 상태를 주입해** 빨간불을 본 뒤에만 그 게이트를 믿는다.
4. **형제를 전수로 센다.** 한 자리에서 이 형태를 찾았으면 같은 파일·같은 원장의 다른 수동
   필드를 훑는다 — **대개 혼자 있지 않다**(§7).

**왜 조항으로 올리나**: 이 저장소는 날짜에서 이미 값을 치렀는데, 그때 고친 것은 **날짜 한
종류**였다(`check-date-freshness`). 근본형을 적어 두지 않으면 다음 수동 필드에서 같은 사고가
난다 — 그게 §6이 말하는 *"버그를 단건으로 고치지 않고 근본형을 한 문장으로 추상화한다"*이다.

### 이 조항이 기대는 세 층 (§7)

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 조항 | 이 절 | `docs/CONSTITUTION.md` → 두 어댑터 |
| ② 구조 | 릴리스 잠금을 **앵커로** 쓴다 — 「지금이 릴리스인가」를 추측하지 않고 물건에서 읽는다 | `.release-lock.json`의 `armed` |
| ③ 기계 | `check-date-freshness` — 미래 날짜(항상) + 얼렸을 때 최신 항목이 오늘 것인가 | `scripts/check-date-freshness.mjs` |

🔴 **일반형에는 아직 ③이 없다.** 「자동 옆의 수동」을 기계가 전수로 찾으려면 무엇을 자동으로
칠지 정의해야 하는데, 그 정의가 아직 없다. 그래서 지금 이 확장은 **①(조항)과 착수 절차의
자문**으로만 서 있다 — 없는 게이트를 만들어 초록을 띄우면 그 초록의 뜻은 「지켰다」가 아니라
**「안 봤다」**이다(§19가 같은 이유로 게이트를 두지 않은 것과 같은 자세).

**왜 `origin/main`과 대조하지 않았나**: 「이번 묶음이 새 릴리스인가」는 기준 가지와 비교하면
알 수 있다. 그러나 그건 **얕은 체크아웃에서 없는 세계**이고, 정확히 그 형태로 한 번 데였다
(§18-G · M-0135). 잠금 파일은 **작업트리 안에 있어** 아무 세계도 가정하지 않는다.

**정직한 한계 — 두 가지를 못 본다.**

1. **그럴듯하게 틀린 날짜는 못 본다.** 어제 날짜로 적으면 허용 범위 안이다. 이 게이트가
   보증하는 것은 「날짜가 옳다」가 아니라 **「이틀 이상 낡은 채로 조용히 머지되는 것의 차단」**이다.
2. **얼리지 않고 머지하면 1항은 돌지 않는다.** 그건 이 게이트의 구멍이 아니라 §18-H를 안 지킨
   것이고, 그 자리는 `release:arm`이 맡는다. 층이 서로를 대신하지 않는다.

### 그대로 받지 않은 것 — 우리 조건이 다르다

- **「전체 검사는 CI에서, 로컬은 좁게」**: 원문은 CI가 더 싸다는 실측 위에 서 있다. 이 저장소는
  **Actions 한도 초과로 배포가 막힌 적이 있어**(§15) 로컬이 더 싼 자리일 수 있다. 그래서
  「기본은 CI」를 받지 않고 **§15의 릴리스 묶음**을 유지한다. 다만 **같은 커밋을 세 번 재지 않는다**는
  원문의 핵심은 §15가 이미 말한다.

### 이 조항이 기대는 세 층 (§7)

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 조항 | 이 절 | `docs/CONSTITUTION.md` → 두 어댑터 |
| ② 구조 | 파이프 대신 로그+`EXIT=$?`가 기본 관용구 | 검증 명령을 적는 모든 자리 |
| ③ 기계 | **PreToolUse(Bash) 훅이 파이프를 차단**하고, 독립 서버 표면은 정적·운영 대조가 앱 릴리스를 차단한다 | `scripts/hook-verify-exit.mjs` · `check-sync-release-contract` · `verify-sync-release-live` |

**정직한 한계**: 훅은 **파이프 형태**만 본다. 일반 코드 전부에서 「병렬로 할 수 있는 것을
줄 세웠는가」는 여전히 판단 영역이다. 다만 동기화 오케스트레이션은 `syncPlan.ts`의 실행 계획과
`check-sync-parallelism`이 push 3단계·pull 1단계·직렬 사유·join-all을 기계로 잠근다.

## CI 실행 정책 — 어떤 초록이 무엇을 뜻하는가 (§15 · 사용자 결정 2026-08-03, 2026-08-04 개정)

> **일정은 워크플로 파일이 정본이고, 헌법은 *의미*를 정한다.** 이 저장소의 규율은 늘 그
> 형태였다(§2-G SKIP≠PASS · §2-J 안 잰 것을 문제 없음이라 하지 마라 · §2-K 속도로 초록의
> 뜻을 깎지 마라). 언제 도는가는 바뀔 수 있지만, **초록이 무엇을 보증하는가**는 계약이다.

**왜 개정했나(실측)**: 변경 1건마다 harness가 여러 번 돌았고, 문서·작은 기능마다 곧바로
머지·배포하면 검사 비용과 배포 횟수만 늘어난다. 하네스는 편집 루프가 아니라 **릴리스 판정**이며,
머지·배포와 떨어뜨리면 그 초록이 낡는다. 이 저장소는 Actions 한도 초과로 배포가 막힌 적도 있다.

|---|---|---|---|
| ① | 작업·축적 중(**Draft PR**)에는 **빠른 차선만** 돈다 | `ci.yml`의 `fast-gates` job | 유지 |
| ② | 문서 단독 변경은 Ready·버전·build·harness·merge·deploy로 보내지 않고 기능 릴리스에 묶는다 | 사람·AI의 릴리스 판단 | 개정 |
| ③ | 기능 변경도 기본은 모으고, 긴급 사유가 있을 때만 단독 릴리스한다 | 위 「변경 축적과 릴리스 묶음」 | 신설 |
| ④ | **Ready 전환** 시 앱을 먼저 build하고 그 커밋에서 전체 Required를 잰다 | `harness` job의 `build → harness`, `live-render`의 `build → live` | 개정 |
| ⑤ | 새 커밋이 올라오면 **낡은 진행 중 검사는 자동 취소** | `concurrency: cancel-in-progress: true` | 유지 |
| ⑥ | 그 초록을 확인한 커밋만 머지하고 바로 배포한다 | `harness → merge → deploy` 한 묶음 | 신설 |
| ⑦ | main 배포에서 하네스를 다시 돌리지 않는다 | `deploy-pages`는 build·시크릿 검사·배포만 | 개정 |

### 🔴 각 초록의 뜻 — 여기가 이 조항의 본론이다

- **`fast-gates`의 초록은 「통과」가 아니다.** `npm run gates`가 스스로 *"재본 N개 통과 ·
  **M개는 아예 안 쟀습니다**"*라고 말하고 안 잰 이름을 나열한다(§2-K). **병합 근거가 될 수 없다.**
- **`harness`+`live-render`의 초록만이 병합 근거다.** 그리고 그것은 **그 커밋**에 대한 것이다 —
  이후 새 커밋이 올라오면 그 초록은 옛 커밋의 것이다(③이 취소하는 이유).
- **main의 초록은 `deploy-pages`가 준다.** main에서는 전체 하네스를 다시 재지 않고, PR 머리의
  build·harness·live-render 초록을 신뢰한다. 배포 job은 운영 변수로 산출물을 다시 만들고
  시크릿 검사 뒤 올린다. base 이동이나 운영 변수 차이로 PR 머리와 달라지는 좁은 창은 배포 후
  실기기가 첫 검출자다. 이 대가를 알고 중복 하네스를 없앤다.
- **「완료 = 배포 그린 확인」은 그대로다**(M-0031). 중복 제거는 확인 면제가 아니다.

### 🔴 이제는 기계가 막는다 — 그리고 그 사실을 **부딪혀서** 알았다

🔴 **`main`에 브랜치 보호가 켜져 있다**(실측 2026-08-12 `protected: true`).
이 절은 원래 *"보호가 없으니 기계적 보장도 없다"*(실측 2026-08-03 `protected: false`)로
적혀 있었다. **현실이 바뀌었고 문서는 그대로였다** — §17이 말하는 「문서 ↔ 코드」 모순의
전형이고, 이 저장소가 반복해서 당한 형태다(M-0006의 화석 주석).

**어떻게 알았나 — 물어봐서가 아니라 막혀서다.** 문서 단독 변경을 `fast-gates` 초록만 보고
머지하려다 GitHub이 거절했다:

```
405: 2 of 2 required status checks are in progress
```

즉 **Required 검사 두 개가 실제로 병합을 막는다.** 그 뒤 `list_branches`로 `protected: true`를
확인했다. 🔴 **관측이 먼저였고 확인이 나중이었다** — 「막아 주지 않는다」를 믿고 있었으므로
스스로 물어볼 생각을 못 했다. 규칙 문서는 *무엇이어야 하는가*를 말하지 *지금 무엇인가*를
말하지 않는다(§9 4단계 「세계를 본다」).

> **병합 규칙(사람·AI 공통)**: 릴리스하기로 결정한 뒤 앱을 build하고, **그 커밋에서**
> `harness`와 `live-render`가 둘 다 success인지 확인한 다음 머지하고 바로 배포한다.
> `fast-gates`만 초록인 상태, 아직 모으는 기능은 병합하지 않는다.
>
> 🔴 **이제 이 규칙은 권고가 아니라 강제다.** 어기려 해도 405로 막힌다.

**그래도 남는 정직한 한계 둘.**

1. **보호의 *내용*은 재지 않았다.** 아는 것은 「Required가 두 개이고 그것이 병합을 막는다」
   까지다. 어떤 check가 Required인지, force-push·관리자 우회가 허용되는지는 **확인하지
   않았다** — 모르는 것을 안다고 적지 않는다(§8).
2. 🔴 **`skipped`를 성공으로 세는 함정은 그대로 살아 있다.** GitHub은 `if:`로 건너뛴 Required
   check를 성공으로 취급할 수 있고, 이 저장소의 `harness`·`live-render`는 **Draft에서
   제외된다**(§15 ①). 그러면 **Draft로 두는 것만으로 검사를 우회**하게 된다 —
   §2-G(SKIP≠PASS)가 CI 층에서 재현되는 형태다. **이건 아직 안 재봤다.**

### 기계 층

`check-ci-policy`가 워크플로가 이 조항에서 조용히 벗어나는 것을 막는다: ①`ci.yml`이
main에서 돌지 않는가 ②전체 검사가 draft에서 제외되는가 ③`concurrency` 취소가 켜져 있는가
④Ready PR이 build→harness 순서인가 ⑤`deploy-pages`가 harness를 다시 돌리지 않고 build는
유지하는가. **정직한 한계**: 이 게이트는 *파일이 그렇게
적혀 있다*까지만 안다 — GitHub이 실제로 그 일정대로 도는지는 정적으로 볼 수 없다(§2-J ②).

## 완료의 정의 (Definition of Done)

> 🔴 **두 어댑터가 서로 다른 정의를 갖고 있었다**(2026-07-29에 발견). CLAUDE엔 화면·버튼
> 확인은 있고 **배포 확인이 없었고**, AGENTS엔 배포 그린은 있고 **§13이 없었다.**
> 그래서 *"Codex는 화면을 안 보고 완료라 하고, Claude는 배포 확인 없이 완료라 하는"* 길이
> 양쪽에 하나씩 열려 있었다 — **M-0046이 정확히 그 형태였다.** 아래가 합친 정의다.

```
릴리스 완료
  → 모아 둔 변경의 버전(changelog +0.01)·문서 확정
  → 🔒 `npm run release:arm <후보>` — 여기서부터 저장소를 얼린다(§18-H)
  → 앱 build
  → 전체 하네스 통과(일부 아님 · SKIP은 통과가 아니다)
  → 🔴 화면을 바꿨으면 열어서 보고, 버튼을 만들었으면 눌러 봄(§13)
  → PR 그린 → 병합 → **배포 성공 확인**
  → 사용자 흐름 확인 · Acceptance 승인
  → 🔓 `npm run release:close` — 재개방 횟수가 나온다
  → 정직한 보고(통과/스킵/미실행을 구분 · **검증 1회 + 재개방 N회**)
```

작업 브랜치에서 관련 검사까지만 끝낸 변경은 **「구현됨·릴리스 대기」**이지 「릴리스 완료」가 아니다.
릴리스할 때는 **일부가 아니라 전부** 통과해야 한다. 자동검사를 통과하지 않은 릴리스를 완료로 표시하지 않는다.

> 🔴 **「화면을 열어서 봄」을 건너뛰었으면 「라이브 렌더 미실행」이라고 적는다**(원칙 #4).
> 「검사 통과」와 「화면을 봤음」은 다른 말이다 — M-0046은 전자가 전부 초록인 채로 배포됐다.
> 그리고 **「화면을 봤음」과 「버튼이 돈다」도 다른 말이다.** M-0046·M-0048은 둘 다 버튼이
> 결함이었는데, 그때 라이브 검사는 버튼의 **라벨만 읽고 있었다**(§13 4항).

> **완료 = 병합이 아니라 배포 그린 확인.** merge 성공 ≠ 배포 성공(M-0031에서 빨간불이
> 두 번 쌓였다). 다만 이 샌드박스는 `*.github.io`를 막으므로 **「배포 확인함」과
> 「사이트에서 확인함」은 다른 말**이다 — 후자는 사용자 실기기 몫이다.

## 검증 명령 (두 도구 공통)

```bash
npm run brief <고칠 파일들>   # 착수 전 — 읽을 스킬 문서·형제 목록·그 영역의 과거 실수
npm run gen                   # 생성물 재생성 — **의존 순서대로 전부**(순서를 외우지 않는다)
npm run gates                 # 편집 루프 (약 6초 · 정적 + typecheck)
npm run build                 # 기능 화면 실측 또는 릴리스 후보 앱 재빌드(tsc --noEmit + vite build)
npm run harness               # 🔴 머지·배포할 때만 — build 다음 전체 검사
npm run live                  # 릴리스 후보 라이브 층(build 다음에)
```

- 🔴 **`npm run gates`는 「통과」가 아니다.** 판정문이 *"재본 N개 통과 · **M개는 아예 안
  쟀습니다**"*라고 말하고 안 잰 이름을 나열한다. 작업 중에는 관련 유닛·개별 게이트·타입검사를
  쓰고, 전체 하네스는 아래 릴리스 묶음에서만 돈다.
- `npm run live`는 `dist`가 소스보다 낡으면 **스스로 멈춘다**(exit 2). 낡은 번들을 재면
  검사가 공허해지기 때문이다 — 반드시 `npm run build` 다음에.
- **SKIP은 통과가 아니다.** 선택 게이트가 건너뛰었으면 그 실행은 그 층을 **재지 않은 것**이다.

### 변경 축적과 릴리스 묶음 (사용자 결정 2026-08-04)

- **문서 개정만 있는 작업**은 문서·필요한 생성물·관련 정적 검사까지만 진행한다. 앱 버전 증가,
  앱 재빌드, 전체 하네스, 머지, 배포를 단독으로 일으키지 않고 다음 기능 릴리스에 묶는다.
- **기능 변경도 기본은 축적**이다. 작업 중에는 관련 유닛·개별 게이트·타입검사와 필요한 화면
  실측으로 결함을 좁혀 잡되, 전체 하네스를 관성적으로 반복하지 않는다.
- **긴급 릴리스 예외**는 기다리는 비용이 더 큰 경우뿐이다: 사용자 데이터 유실·보안 노출,
  동기화/로그인/앱 실행 불가 같은 핵심 흐름 차단, 배포·서버 호환성 파손. 단순 문구·미관·편의
  개선은 긴급 사유가 아니다.
- **릴리스 순서는 하나의 원자적 묶음**이다:
  `버전·CHANGELOG 확정 → 앱 build → 전체 harness + live-render → 그 커밋 머지 → 배포 → 배포 그린 확인`.
  하네스만 미리 돌려 두거나, 하네스 뒤 코드를 바꾸거나, 머지만 하고 배포를 미루면 묶음이 깨진다.
