# CODING MISTAKES · Bugeon Journey (실수 원장)

> LESSONS §7·최우선10 #1: **실수는 고치는 것이 아니라 기록하는 것이다.** 체크포인트를 넘은(병합·배포·게이트 거짓통과) 또는 재발한 실수는 **수정과 같은 변경에서** 여기에 기록하고, 가능하면 게이트/hook로 기계화한다. 기록 없이 고친 실수는 다음 세션에 재발한다.

형식: `증상 / 원인 / 수정 / 예방(게이트)`. 추가 전용, 최신이 위.

## M-0044 · **코드가 없는 ADR을 가리켰다** — 근거를 적었다고 믿고 병합·배포까지 갔다
- 날짜: 2026-07-28 · 발견: 오디오 동기화 착수 중 문서 점검(§9 2단계) · 심각도: minor(근거 소멸)
- **증상**: `src/domain/place/externalMap.ts:97`이 *"각 URL 형식의 출처와 검증 상태는 `docs/DECISIONS.md`(ADR-0031)에 적었다"*고 말하는데 **ADR-0031이 존재하지 않았다.** v1.19로 병합·배포까지 나간 상태였다.
- **원인**: 지도 넷을 붙이면서 *"근거는 ADR에 적자"*고 **주석을 먼저 썼고**, 그 커밋에서 ADR을 쓰지 않았다. 주석은 의도를 적을 수 있지만 **의도는 검증되지 않는다.** 그리고 이 자리는 특히 나쁘다 — 얀덱스만 경도가 먼저라는 것, 카카오 경로가 쉼표로 나뉜다는 것, 어느 지도가 실기기에서 확인됐는지가 **전부 그 없는 문서에 있다고 적혀 있었다.** 다음 사람이 URL 형식을 의심하면 갈 곳이 없다.
- **왜 아무 게이트도 못 잡았나**: 문서 카운트(`check-doc-counts`)는 **숫자**를 대조하고 스킬 라우팅(`check-skill-routing`)은 **파일**을 대조한다. *"코드가 가리키는 문서 절이 실제로 있는가"*를 보는 층은 없었다. 조항(§1 SSOT)만 있고 기계 검사가 없던 자리다.
- **수정**: ADR-0031(바깥 지도 넷 · 제공자별 동의)을 실제로 작성했다. URL 형식 표에 **좌표 순서와 검증 상태(실기기/문서 기준)를 열로** 넣어, 다음 사람이 "이건 확인된 건가?"를 물을 수 있게 했다.
- **근본형**: **약속을 코드에 적고 지키지 않으면, 그 약속은 거짓 근거가 된다.** 「~에 적었다」는 완료형 주석은 그 문서를 **같은 커밋에** 쓰지 않으면 안 된다 — 나중에 쓰겠다는 것은 §7의 "다음 형제가 자동으로 따라오는가"에 아니오다.
- **예방**: 지금은 층이 없다. 후속 후보 — 게이트가 코드 주석의 `ADR-\d{4}` 참조를 뽑아 `docs/DECISIONS.md`의 제목과 대조한다(문서→코드 방향은 굳이 볼 필요 없다; 인용되지 않는 ADR은 정상이다). 만들면 **없는 번호를 주입해 RED**를 먼저 확인할 것(§11 ①).

## M-0043 · **뒷정리가 만든 오류를 실패로 읽었다** — 정상 재생 직후에만 「재생 불가」
- 날짜: 2026-07-28 · 발견: **사용자 실기기**(*"재생불가가 아닌데 재생불가라고 안내하네요"*) · 심각도: major(거짓 안내)
- **증상**: 녹음을 **끝까지 들으면** 칩이 「🔇 재생 불가」로 바뀐다. 재생은 멀쩡히 됐다. 사용자는 자기 녹음이 깨진 줄 안다.
- **원인**: 정리 함수가 **스스로 `error` 이벤트를 발화시킨다.** 미디어 요소의 `src`를 비우고 `load()`를 부르면 브라우저는 "실을 것이 없다"를 오류로 알린다. 그런데 그 오류 리스너가 아직 붙어 있었다:
  ```
  ①ended → ②정리(src=''+load()) → ③setIdle()로 라벨 정상 복귀
         → ④뒤늦게 error 발화 → ⑤라벨을 「재생 불가」로 덮어씀
  ```
  **정상 경로에서만** 나는 거짓말이라 더 나빴다 — 실패했을 때가 아니라 **성공했을 때** 실패라고 말했다.
- **수정**: 재생마다 `AbortController`로 이벤트를 묶고, `stopAudioPlayback()`이 **정리보다 먼저** `detach()`한다. 이중 방어로 `failed()`가 `playing?.audio !== audio`면 즉시 반환한다(이미 정리된 재생의 오류는 우리 것이 아니다). `src=''` 대신 `removeAttribute('src')` — 빈 문자열은 **문서 URL을 미디어로 실으려 드는** 또 다른 오류원이다.
- **근본형**: **뒷정리가 만드는 신호를 실패 신호로 읽지 마라.** 자원을 놓는 행위(구독 해지·연결 종료·버퍼 비우기)는 그 자체로 이벤트를 만든다. 리스너를 **정리보다 먼저** 떼지 않으면 그 이벤트가 "실패"로 둔갑한다. 같은 형태가 날 수 있는 자리: WebSocket close, AbortController로 취소한 fetch(=`AbortError`를 네트워크 실패로 세는 것), IntersectionObserver disconnect.
- **예방(게이트)**: `verify-editor-live.mjs`에 **끝까지 재생한 뒤** 라벨을 보는 검사 2건 추가(165). 이 부류는 **재생 중만 재면 영원히 안 잡힌다** — 검사가 "끝난 뒤"를 봐야 한다. 고치기 전 코드를 그대로 주입해 RED 확인(`{"text":"🔇재생 불가"}` 재현).
- **왜 자동층이 못 잡았나**: 유닛은 DOM 미디어 이벤트를 못 돌리고, 기존 라이브 검사는 **재생 중 상태만** 쟀다(폭·aria-pressed). 상태 전이의 **마지막 칸**을 아무도 안 봤다 — §10 ③(전달 결함)의 시간축 버전이다.

## M-0042 · **순간 실행취소가 사진만 되살렸다** — M-0007이 형제 한쪽에서 그대로 재발
- 날짜: 2026-07-27 · 발견: 위치 칩 작업 중 인접 코드 정독(§9 2단계) · 심각도: major(복구 경로 소멸)
- **증상**: 타임라인에서 순간을 지우고 「실행취소」를 누르면 **사진만 돌아오고 비용·소리는 tombstone으로 남았다.** 순간이 활성으로 돌아오므로 **휴지통에도 안 보여** 복구 경로가 사라진다.
- **원인**: `tripDetail.ts`가 `const { deletedMediaIds } = await softDeleteMomentLocalFirst(m.id)`로 **사진만 꺼내** `restoreMomentLocalFirst(m.id, deletedMediaIds)`로 넘겼다. 나머지 두 매개변수는 **선택적이고 기본값이 `[]`**라 누락을 조용히 삼켰다 — 컴파일도, 서비스 유닛도 전부 통과했다.
- **이것이 M-0007과 같은 결함인데 형제 한쪽만 안 고쳐진 것이다.** M-0007에서 여행 쪽은 `TripChildren` 묶음 타입으로 이 부류를 **컴파일 오류화**했다. 그 처방이 옳았다는 것은 그때 증명됐다(옛 호출 형태를 쓰던 테스트가 즉시 TS2554로 잡혔다). 그런데 **순간 쪽에는 적용하지 않았다** — §7이 요구하는 "형제 목록을 적고 전부에 적용하라"를 그때 하지 않은 것이다. 그리고 그 자리는 그 뒤로 **1년치 세션 동안 아무 게이트도 묻지 않았다.**
- **수정**: `MomentChildren { mediaIds; expenseIds; audioIds }`를 만들어 **삭제가 돌려주는 것과 복원이 받는 것을 같은 타입**으로 했다. 호출부는 `restore(id, children)`로 통째로 넘긴다 — 손으로 고를 기회 자체가 없다. 자식 종류가 늘면 컴파일러가 모든 호출부를 데려온다.
- **예방(게이트/검사)**: `tests/unit/audioSiblingDiscipline.test.ts`에 「실행취소는 딸린 것 전부를 데려온다」 무리 추가(사진·비용·소리 세 종류를 한 순간에 달아 놓고 삭제→복원을 실제로 돌린다). 옛 시그니처를 주입해 **3건 RED** 확인.
- **배운 것 — 타입으로 잠근 계약은 호출부까지 그 타입을 통과하게 해야 한다.** 서비스 계층 유닛은 전부 초록이었다. 검사의 시선이 **서비스에 있었고 화면에 없었다**(§10 ③과 같은 자리). 그리고 *선택적 매개변수 + 기본값*은 이 저장소에서 반복적으로 결함을 삼켜 왔다 — 자식 목록처럼 **빠지면 조용히 데이터가 안 돌아오는** 인자는 선택적으로 두지 않는다.

## M-0041 · **소리 칩이 형제보다 두 배 높았다** — `.chip`이 flex가 아니었다 (+ 소리에만 없던 실행취소)
- 날짜: 2026-07-27 · 발견: **사용자 실기기**(*"칩 디자인이 조잡하네요"*, *"이미 녹음된 걸 삭제할 땐 바로 삭제가 되네요"*) · 심각도: minor(시각)+major(복구 어포던스)
- **증상**: ① 소리 칩 안의 ✕가 **둘째 줄로 밀려나** 칩 높이가 51.3px — 형제(장소 칩) 29.3px의 **거의 두 배**였다. 칩 줄 전체가 어긋나 보였다. ② 녹음을 지우면 **실행취소 토스트가 안 떴다.** 사진에는 있었다.
- **원인**:
  - ①은 `.chip`이 `display:flex`가 아니어서다. 그 안의 두 버튼이 인라인으로 배치돼 폭이 좁으면 줄바꿈했고, `.chip-clear`의 `margin-left:auto`는 **flex가 아니면 아무 일도 하지 않는다.** 게다가 `.chip-clear`는 *줄(row)* 안에 서라고 만든 24px 원형이라 작은 알약 안에서 과했다 — **형제의 부품을 맥락이 다른 곳에 그대로 가져다 쓴 것**이 뿌리다.
  - ②는 M-0040과 **같은 형태의 잔재**다. 다섯 곳을 고치면서 서비스 계층 대칭은 맞췄는데 **화면 계층의 어포던스**를 세지 않았다. 사용자에게 "되돌릴 수 있다"는 사실은 휴지통에 있느냐가 아니라 **그 자리에서 말해주느냐**로 결정된다.
- **수정**: `.chip`을 `inline-flex` + `min-height:30px`로 못 박아 **모든 칩이 같은 높이로 태어나게** 했다(우연히 같기를 바라지 않는다). ✕는 칩 전용 `.chip-x`로 분리 — 보이는 크기는 줄이고 누름 영역은 칩 높이를 채워 24×30=720px²(예전 324px²의 두 배). 삭제에 사진과 같은 `showUndoToast`를 붙였다.
- **가장 중요한 배운 것 — 격리 테스트가 통과했는데 실제 화면에서는 실패했다.** 처음엔 `::after{inset:-11px}`로 40px 터치 목표를 만들었고 **떼어놓고 재니 네 방향 전부 통과**했다. 그런데 실제 카드 안에서는 아래쪽이 **사진 격자에 가려져** 실패했다. 그리고 그건 단순 미달이 아니라 **위험**이었다: 보이지 않는 *삭제* 목표가 사진 위에 얹히면 사진을 누르려던 손이 소리를 지운다. → 칩 **밖으로 넘치지 않는** 방식으로 바꿨다. **부품을 떼어내 재면 맥락이 만드는 결함을 못 본다.**
- **예방(게이트)**: `verify-editor-live.mjs`에 소리 칩 8건 추가(137 → 145). 마크업을 손으로 세우지 않고 **Dexie에 행을 넣어 앱이 스스로 그리게** 한다 — 내가 쓴 마크업을 재면 그건 나를 재는 것이지 앱을 재는 것이 아니다(M-0038의 「이름이 있는 것과 불리는 것은 다르다」). 배포됐던 상태(비-flex + `.chip-clear`)를 그대로 주입해 **5건 RED**를 확인했다(h=51.3 재현).
- **두 번 헛디딘 것도 적어 둔다**: ⓐ 픽스처를 0바이트 더미로 넣어 **재생 실패 경로만 재고 있었다** — 실제로 디코드되는 WAV를 만들어 고쳤다(픽스처가 틀리면 검사는 조용히 딴 것을 잰다). ⓑ 칩이 뷰포트 밖이라 `elementFromPoint`가 null을 돌려줬는데 그걸 "안 눌린다"로 읽어 **멀쩡한 것을 결함이라 불렀다** — `scrollIntoView` 후 재도록 고쳤다.

## M-0040 · **오디오가 형제의 규율을 하나도 안 받고 태어났다** — 게이트가 접미사에 기대고 있었다
- 날짜: 2026-07-27 · 발견: 병합 전 자기감사(사용자 지시 *"전반적으로 우리가 겪었던 문제들 다시 한 번 감사하고 병합여부 결정하자"*) · 심각도: major(병합 전 차단)
- **증상**: 오디오 노트는 기능으로 완성돼 있었다 — 녹음·재생·백업 왕복·유닛 22건 전부 통과. 그런데 형제(순간·사진·비용)가 이미 지키던 계약 **다섯 개가 동시에 비어 있었다**:
  ① 순간·여행을 지워도 **소리만 활성으로 남았다**(cascade 누락) ② 개별로 지운 소리가 **휴지통 어디에도 안 보였다** — 실행취소 토스트가 사라지면 복구 경로가 소멸(F5의 재발) ③ 여행을 **영구삭제해도 blob이 IndexedDB에 영원히 남았다**(여행 행이 사라져 어느 화면에서도 닿을 수 없으므로 사용자가 지울 방법도 없다) ④ 저장 용량 화면의 「합계」가 소리만큼 **작게** 나왔다 ⑤ 무결성 점검이 소리를 **안 보고 「0건」이라 말했다**.
- **원인(두 층)**:
  - *직접*: M-0033과 **같은 근본형** — 새로 만든 것은 형제의 계약을 알고 태어나지 않는다. 그때는 op 하나였고 이번엔 도메인 하나였을 뿐이다. `services/audio.ts`는 형제 목록을 훑어 여섯 줄을 맞췄는데(머리주석에 그 목록이 있다), **cascade·휴지통·영구삭제·용량·무결성 다섯은 그 목록에 없었다.**
  - *진짜*: **다섯이 동시에 빈 이유는 하나다.** `check-domain-symmetry`가 `\w*LocalFirst` 이름만 검사 대상으로 삼았다. `softDeleteAudio`/`restoreAudio`는 그 접미사를 안 써서 **검사 대상에 들어오지도 않았다.** 게이트가 통과했다는 사실이 아무것도 뜻하지 않았던 것이다. **접미사 규약에 기대는 검사는, 규약을 안 따르는 새 형제를 정확히 놓친다** — 그리고 새 형제야말로 검사가 가장 필요한 대상이다.
- **수정**: 다섯 곳을 형제와 같게 맞췄다(cascade는 `TripChildren.audioIds`로 **누락이 컴파일 오류**가 되게, 휴지통은 `TRASH_DOMAINS`·`CHILD_SOURCE` 등록부를 돌게, 영구삭제는 하드 삭제 + 되읽기 확인, 용량은 「소리」 줄로, 무결성은 `IntegritySnapshot.audio`를 **필수 필드**로). 로컬 전용이라 서버 왕복이 없는 것은 `LOCAL_ONLY_DOMAINS`로 분리하고 **왜 그것이 차별이 아닌지**를 코드에 적었다.

- **영향(정직 — 측정 후 정정)**: 처음엔 「같은 초 안에서 순서가 뒤집힌다」고 적었는데 **틀렸다.** PostgREST는 timestamptz를 **항상 `+00:00`**으로 주므로 자릿수가 맞고, `'+'`(0x2B) < `'.'` < 숫자라 **사전순이 시간순과 일치한다.** 실제 위험은 순서 뒤집힘이 아니라 **같은 순간을 다르다고 보는 것**이다(`'…00+00:00'.localeCompare('…00.000Z') !== 0`). 그러면 **동률일 때만 도는 규칙**이 건너뛰어진다 — LWW의 version 판정, 정렬의 안정성. M-0034의 진짜 피해(TIME_INVERSION 오탐·version 판정 생략)와 같은 형태다.
- **배울 것(추가)**: 이 정정 자체가 교훈이다. 「정렬이 흔들린다」를 **재보지 않고** 문서·changelog에 적었고, 그걸 검증한다고 쓴 유닛은 **주입에도 통과**했다(공허). 영향 범위를 주장할 때는 **그 주장을 깨는 입력을 실제로 만들어 봐라** — 못 만들면 주장이 틀린 것이다.

### ③ 읽기-수정-쓰기를 트랜잭션 밖에서 했다 — **M-0033과 같은 부류를, 그걸 기록한 세션에서**

- **수정**: `table.db.transaction('rw', …)`로 읽기와 쓰기를 한 커밋에 넣었다.
- **완화 요인**: `autoSync`가 `running` 프로미스로 `runSync`를 직렬화하고 `runSync`를 부르는 곳이 거기뿐이라 동기화끼리는 겹치지 않는다. 남는 창은 **복원과 겹칠 때**뿐이었다.
- **근본형**: §1-B가 이미 말한다 — *"이 함수가 `await`에서 멈춘 사이에 동기화가 돌면 지금 상태는 어떻게 보이는가?"* 읽기-수정-쓰기에는 **언제나** 이 질문이 걸린다.

## M-0035 · 동기화가 **방금 성공했는데 「판정 불가」** — 앱이 아는 것을 화면에 안 말했다
- 날짜: 2026-07-27 · 발견: **사용자 진단 요약**(v1.08 배포 직후) · 심각도: minor(오판정 · 총괄 판정을 끌어내림)
- **증상**: 진단 총괄 판정이 `unknown`인데 하위 지표는 **전부 `ok`**였다. 끄는 것은 하나: 「자동 동기화: 지금 **마지막 성공 19:45:03** / 정상 최근에 성공 — **unknown**」. 보고서 시각은 19:46:15 — **72초 전에 성공했는데 판정 불가**다.
- **원인**: 판정이 `st.phase === 'ok'`일 때만 `ok`였다. `lastOkAt`이 찍혀 있으면서 `ok`가 아닐 수 있는 갈래는 **`running`** 하나뿐이다(`failed`·`offline`·`signed-out`은 각자 문구가 있고 `idle`은 `lastOkAt`이 null). 즉 그 순간 주기 동기화가 **한 번 더 돌고 있었다.**
- **진짜 결함은 판정이 아니라 문장**: `running` 갈래가 「마지막 성공 …」으로만 보였다. 앱은 자기가 **동기화 중임을 알고 있었는데** 화면에 안 적었고, 그래서 **사용자가 판정 불가의 이유를 알 방법이 없었다**(§12 — 앱이 아는 것을 사람에게 대신 알아내게 한다).
- **근본형**: **지표의 판정 규칙이 그 지표가 묻는 질문과 어긋났다.** 이 지표가 묻는 것은 「자동 동기화가 조용히 실패하고 있는가」 하나인데, 판정은 「지금 상태가 정확히 `ok`인가」를 재고 있었다. 둘은 다른 질문이다.
- **수정**: 판정을 질문에 맞췄다 — `running` + 이번 세션 성공 이력 있음 → **`ok`**(마지막 결과가 성공이므로 "조용한 실패"가 아니다). `running` + 성공 이력 없음 → **`unknown`**(진짜로 모른다) + 해소 경로. 그리고 **어느 갈래든 상태를 문장에 적는다**(「지금 동기화 중 · 마지막 성공 19:45:03」). 판정·문장을 `domain/syncStatusVerdict.ts`의 **순수 함수**로 뽑았다.
- **예방**: `tests/unit/syncStatusVerdict.test.ts` 13건 — **level만이 아니라 문장도 잰다**(§10 ③). 옛 로직 주입 시 **3건 RED**. `check-fn-size` 래칫이 `syncProbe`를 144 → 133줄로 밀어 추출을 강제했다.
- **배울 것**: §8의 *"모르는 것을 정상으로 반올림하지 않는다"*는 **아는 것을 모른다고 하라**는 뜻이 아니다. 과도한 `unknown`도 결함이다 — 총괄 판정을 끌어내려 **정상 화면을 이상하게 보이게** 만들고, 사용자는 매번 안을 열어 하나씩 확인해야 한다. M-0034의 오탐(§11 ③)과 같은 부류다: 지표가 틀리면 사람이 그 지표를 안 보게 된다.
- **정직**: 사용자 화면에서 `running`이었다는 것은 **역산**이다(그 순간의 phase를 직접 관측하지 못했다). 다만 `lastOkAt`이 있으면서 `ok`가 아닌 갈래가 그것뿐이라 다른 가능성이 없다.

## M-0034 · 진단이 **멀쩡한 사진 9건을 문제라 했다** — 같은 순간을 두 표기로 적고 글자로 비교
- 날짜: 2026-07-27 · 발견: **사용자 실기기** *"이 문제 해결하자."*(앱 상태 확인: 「만든 시각이 고친 시각보다 늦음 — TIME_INVERSION ×9」) · 심각도: major(오탐 · 그리고 LWW에 잠복)
- **증상**: 진단이 사진 9건을 시간 역전으로 판정. 서버 실측 결과 그 9행은 `created_at = updated_at`으로 **완전히 같았다.** 데이터는 처음부터 멀쩡했다.
- **원인**: 같은 순간을 **두 표기**로 저장하고 있었다. 서버(PostgREST/JSON) `2026-07-26T17:29:48.34+00:00` — ms 끝 0 생략·오프셋 `+00:00`. 로컬(JS `toISOString()`) `2026-07-26T17:29:48.340Z`. 그런데 이 앱은 시각을 **문자열 대소로** 비교한다: `'0'`(0x30) > `'+'`(0x2B) → createdAt이 더 크다. 사진은 push 후 `updatedAt`만 서버 값으로 덮이므로 **정확히 그 9건만** 걸렸다.
- **더 위험했던 자리(화면에는 안 보였다)**: `mergeDecision`의 LWW가 같은 비교를 쓴다. 표기가 섞이면 같은 순간인데 한쪽이 크게 나오고 — **동률일 때만 도는 version 판정을 통째로 건너뛴다.** 더 높은 세대의 서버 행이 조용히 무시될 수 있었다.
- **근본형**: **밖에서 들어온 시각 문자열을 우리 표기로 바꾸지 않고 저장했다.** 경계에서 정규화하지 않으면, 그 값을 비교하는 **모든** 자리가 표기에 의존하게 된다.
- **수정**(§7 세 층): ①조항 — 표기의 SSOT를 `domain/time.ts`에(`isoInstant`·`isoInstantOrNull`·`withCanonicalStamps`·`compareInstants`). ②구조 — 브랜드 타입 `Instant`/`WithInstants<T>`로 서버 경계 함수의 반환형을 잠갔다. `createdAt: r.created_at`은 **컴파일 오류**(주입 확인: TS2322). 형제 4곳이 자동으로 따라온다. ③기계 — `check-instant-normalization` 게이트가 **타입이 못 잡는 구멍**을 본다(새 rowmap이 반환형을 아예 안 쓰는 경우 · 백업 복원 · LWW가 문자열 비교로 회귀). 진단은 `TIME_INVERSION`(순간으로 잰다)과 `BAD_TIME_FORMAT`(표기만 본다)으로 **나눴다**.
- **상태 의존 절반(§10 ②)**: 코드를 고쳐도 **이미 옛 표기로 박힌 행은 그대로다.** `normalizeStampsOnce()`가 동기화 앞에서 1회 정리한다 — 같은 순간·다른 표기라 version이 안 바뀌고 sync op을 만들지 않으며, 커서로 돌아 사진 blob을 메모리에 올리지 않는다. 그 정리가 안 돌았을 때를 볼 창이 `BAD_TIME_FORMAT` 지표다(정상 0건).
- **예방**: `tests/unit/instantFormat.test.ts` 28건. 주입 2건 RED 확인(옛 문자열 비교를 `mergeDecision`·`integrity`에 되돌리면 각각 잡힌다).
- **배울 것 ①**: **오탐도 결함이다**(§11 ③). 사용자가 진단을 무시하기 시작하면 그 지표는 죽고, 진짜 시간 역전이 왔을 때 아무도 안 본다. 오탐은 "빡빡한 게이트"가 아니라 **틀린 게이트**다.
- **배울 것 ②**: **왕복 유닛이 있었는데도 놓쳤다.** rowmap 유닛은 *우리가 만든 문자열*을 넣고 되읽었다 — **서버가 실제로 뭘 주는지는 아무도 안 넣어봤다.** 밖에서 오는 값을 검사할 때는 **실측한 실제 값**을 픽스처로 써라(이 파일의 `PG` 상수가 그것이다). M-0033과 같은 형태다: 조각마다 유닛이 있고 **이음매**에는 없었다.

## M-0033 · 그 수정이 **반쪽이었다** — 의사를 행과 다른 커밋에 넣어 창을 만들었다
- 날짜: 2026-07-26 · 발견: **사용자 실기기(같은 날 두 번째)** — 복원이 「복원됨 · 여행 1 · 순간 1 · 사진 10 · 비용 1 · 영구삭제했던 13건을 되살립니다」를 띄우고도 홈 화면은 **「첫 여행을 기록해보세요」** · 심각도: **critical(기억 손실 · 재발)**
- **증상**: M-0032를 고쳐 배포(v1.03)했는데 **같은 증상이 그대로 났다.** 서버 실측: 행 여전히 0, 원장 **24 → 11**(= 13건이 실제로 되돌려졌다). 즉 **되돌리기 자체는 성공했는데 행은 이미 없어진 뒤였다.**
- **원인**: v1.03이 `requestUnpurge`를 행 트랜잭션 **밖**에 두었다. 그 사이가 창이다:
  `커밋(행 있음 · 로컬 표식 없음 · 되돌리기 의사 **없음**)` → 여기서 동기화가 돌면 → `applyPurgedLedger`가 보호할 근거를 못 찾고 **방금 되살린 행을 지운다.**

- **두 번째 원인(이게 없었으면 회복됐다)**: 트리거 거부는 4xx라 `classifyError`가 **'permanent'**로 본다 → op이 `permanent_failed`가 되고 push는 그 상태를 **영원히 건너뛴다.** 그래서 나중에 원장을 푸는 데 성공해도 그 행은 **두 번 다시 올라가지 않는다.** 판정은 그 순간엔 옳았고, 틀린 것은 **영구로 굳힌 것**이다 — 거부 사유가 사라질 수 있는 종류였다.

- **수정**: ① `requestUnpurge`를 트랜잭션 **콜백의 반환값**으로 옮겼다 — 밖으로 빼면 반환 경로가 끊기므로 다음 사람이 무심코 되돌릴 수 없다(§7 2층, 구조적 강제). ② `pushUnpurges`가 되돌리기에 성공한 id의 `permanent_failed`/`retryable_failed` 전파 op을 **되살린다**(`revivePushOps`) — 사유가 사라진 것을 아는 곳이 거기뿐이므로 되살리는 책임도 거기 있다. `pushUnpurges`가 다른 push보다 먼저 돌므로 **같은 동기화 안에서** 바로 올라간다.
- **예방**: `tests/unit/restoreAtomicity.test.ts` — *"의사를 못 남기면 **행도 남지 않는다**"*. 이건 "의사가 남는가"가 아니라 **"행과 의사가 같이 커밋되는가"**를 재는 검사다. v1.03 배치를 주입해 **2건 RED** 확인(옛 배치에서는 행이 커밋된 채 남는다 = 사고의 그 상태). `revivePushOps` 제거 주입도 1건 RED.
- **배울 것**: **결함을 고칠 때 새로 만든 것에는 기존 규율이 자동으로 걸리지 않는다.** "op은 행과 한 커밋"이라는 규율이 문서에도 코드에도 있었는데, *새로 만든 op*이 그 규율의 바깥에서 태어났다. 새 op·새 테이블·새 큐 항목을 만들 때는 **형제가 지키는 규율 목록을 그대로 훑어라**(§7 착수 절차의 "형제 목록"이 정확히 이 일을 위한 것이다). 그리고 **고친 그 자리에서 다시 넘어지는 것이 가장 흔하다** — 같은 날 M-0032와 M-0033이 그랬다.

  2. push → 0012의 **BEFORE INSERT 트리거**가 서버 원장을 보고 거부한다.
  3. 사진 바이트는 행 upsert와 **별개로** 먼저 올라가 R2에 착지한다 → 고아 파일 10개.
  4. `runSync`가 원장을 pull → `applyPurgedLedger`가 **로컬 행까지 지운다.**
  5. 사용자에게는 아무 오류도 보이지 않는다.
- **근본형**: **§7 비대칭 — 규칙을 한쪽(로컬)에만 구현했다.** "사용자가 명시적으로 복원한 것은 영구삭제 의사보다 우선한다"를 로컬에는 구현하고 서버에는 구현하지 않았다. 더 나쁜 것은 **클라이언트에 원장을 지울 권한 자체가 없어**(0013이 DELETE를 의도적으로 withhold) 복원이 이길 방법이 **원리적으로** 없었다는 점이다. `check-migration-grants`는 *코드가 하는 연산*을 대조하는데, 이 경우 코드는 **아무 연산도 하지 않고 있었으므로** 대조할 것이 없었다 — **하지 않는 일은 게이트가 못 본다.**
- **두 번째 결함(더 위험)**: 진단이 R2에 남은 파일 10개를 「영구삭제 후 남은 사진 파일」로 분류하고 **[남은 사진 파일 정리] 버튼까지 내어 주고 있었다.** 그 10개는 잔재가 아니라 **복원된 사진의 마지막 바이트**였다. 버튼을 눌렀으면 앱이 사용자의 사진을 스스로 지웠다.
- **수정**: ① migration `0017` — `journey.unpurge_ids(uuid[])` **좁은 문** 하나. 테이블 DELETE는 여전히 안 준다(0013의 판단 유지). `SECURITY DEFINER`지만 `user_id = auth.uid()`로 자기 행만, 초대제 통과 필수, 명시한 id만. ② `unpurge` 큐 op 신설 — 복원이 **의사를 큐에 남기고**(오프라인·실패에도 살아남는다) `pushUnpurges`가 **runSync 맨 앞에서** 보낸 뒤 **원장을 되읽어** 실제로 빠졌는지 확인한다(성공 응답을 완료로 치지 않는다). ③ `applyPurgedLedger`가 되돌리기 대기 중인 id를 **건너뛴다**(④를 막는 층). ④ `classifyOrphanFiles`에 `restorePending` 인자 추가 — 되살리는 중인 파일은 `restoring`으로 갈라 **치우기 대상에서 뺀다.** ⑤ 진단에 **「복원했는데 서버가 막은 항목」** 지표 + `[복원한 항목 되살리기]` 액션.
- **예방(세 층)**:
  - **정적**: 없다 — 정직하게 적는다. 이 결함은 코드가 아니라 **데이터의 모양**에 달렸다(§10 ②).
  - **런타임(이게 게이트다)**: `StoreComparison.blockedByLedger` = *로컬에 행이 있는데 서버 원장이 막는 id*. **옛 판으로 이미 복원해 둔 사람을 데려올 유일한 층**이다.
  - **유닛**: `tests/unit/restoreUnpurge.test.ts` 12건 + `blockedByLedgerMetric`/`classifyOrphanFiles` 문장 검사 6건. 주입 검증으로 각각 3건 RED 확인(가드 제거 · 되읽기 신뢰 · 보호 해제).
- **배울 것**: 서버가 **거부한다**는 것은 정상 동작일 수도, 결함일 수도 있다. 가르는 기준은 *누가 그 요청을 만들었는가*다 — 사정 모르는 기기의 자동 재업로드는 좀비, **사용자가 파일을 골라 누른 복원은 새 의도**다. 차단 장치를 만들 때는 **"정당한 예외는 어느 문으로 들어오나"**를 같은 자리에서 답해야 한다. 답하지 않으면 그 문은 만들어지지 않고, 없는 문은 **조용히** 막는다.

## M-0030 · 「다 지웠는데 왜 용량이 남지?」 — **보이지 않는데 용량을 먹는 것**을 앱이 볼 수 없었다
- 날짜: 2026-07-26 · 발견: 사용자 실기기 *"버킷 용량은 왜 2.87?? 개체수도 10개로 잡히고? 이것도 설마 휴지통 이런데 간거 아님?"* · 심각도: major
- **증상**: 버킷 **최상위가 완전히 비었는데**(대시보드가 *"버킷이 준비되었습니다"*라고 표시) 크기는 2.87MB, 개체 수는 10개로 계속 나왔다. 앱은 「사진 파일 0개」라 했다. **세 화면이 서로 다른 이야기를 했다.**

  - `list`가 **미완료 멀티파트 개수**(`multipart.mine/outside/known`)를 함께 준다 → 지표 「올리다 만 사진 조각」 + 액션 [올리다 만 조각 정리].
  - `list`가 **내 폴더 총 바이트**를 준다 → 화면이 「사진 파일 3개(0.9MB)」라고 말해 대시보드와 대조 가능.
  - `capabilities`(version·ops·serverTime) → **옛 함수가 배포돼 있으면** 화면이 「낡음」이라고 말한다. 그전에는 `?? 0` 방어 코드 때문에 "0개"와 "모름"이 구분되지 않았다.
  - `deleteMany` — 한 번에 보내고 **함수가 목록을 다시 읽어** `stillThere`를 준다. "성공 응답"을 완료로 치지 않는다(M-0029의 근본 대응).
- **예방(게이트)**: `check-edge-fn-ops`(22번째) — `FN_OPS` 선언과 실제 `op ===` 분기가 **양방향으로** 일치해야 한다. 구현했는데 선언 안 함 / 선언만 하고 구현 안 함을 둘 다 잡는다. 셀프테스트 8건, 양방향 주입으로 RED 확인.
- **부수 확인**: `check-report-fields`가 `StoreComparison.bytes`를 **계산해 놓고 화면에 안 썼다**고 잡았다(M-0022 부류). 게이트가 실제로 일했다.

## M-0025 · **§10을 쓰고 바로 그 함정에 다시 빠졌다** — 휴지통이 로컬만 보게 만듦
- 날짜: 2026-07-26 · 발견: 사용자 실기기(휴지통 확장 배포 직후) *"0이 되지 않네요"* · 심각도: major

## M-0024 · 연산을 바꾸면서 **그 연산의 서버 권한**을 안 열었다 (M-0020의 재발)
- 날짜: 2026-07-26 · 발견: 사용자 실기기에서 [서버에서도 지우기]를 누른 뒤 서버 대조 · 심각도: **critical**
- **증상**: 화면은 `3건을 서버로 보냈어요`라고 했는데 서버는 **원장만 6 → 9로 늘고 행은 하나도 안 지워졌다.**
- **원인**: ADR-0030에서 영구삭제를 "tombstone 유지" → "행 하드 삭제"로 바꾸면서 **`authenticated`에게 DELETE 권한도, DELETE RLS 정책도 주지 않았다.** 네 테이블 모두 SELECT·INSERT·UPDATE뿐이었다. `pushPurges`는 원장 기록(INSERT)까지 성공하고 그 다음 `hardDelete`에서 막혔다.
- **근본형**: **"코드에서 하기로 한 일을 서버가 허락하는지 확인하지 않았다."** M-0020과 **같은 형태의 재발**이다 — 그때는 *새 테이블*의 GRANT를, 이번엔 *새 연산*의 GRANT를 빠뜨렸다. M-0020을 기록하고 게이트까지 만들었는데도 재발한 이유는 **그 게이트가 "테이블"만 봤기 때문**이다. 규율의 범위를 사고의 모양에 맞춰 좁게 잡았다.
- **왜 조용했나(두 겹)**:
  1. CLAUDE.md §0는 ADR-0030 때 "하드 삭제 예외"를 명시했는데 **DB만 옛 상태로 남았다** — 문서와 서버의 드리프트.
  2. **`runSync`는 개별 작업 실패를 예외로 던지지 않고 개수로 돌려준다.** `autoSync`가 그 개수를 안 보고 무조건 `phase: 'ok'`로 적었다. 바로 위 catch에 *"자동 동기화의 가장 큰 위험이 안 갔는데 갔다고 믿는 것"*이라고 적어 놓고도, **예외가 아닌 실패는 세지 않고 있었다.**
- **수정**: 마이그레이션 0015 — 네 테이블에 `grant delete` + 소유자·초대제 결합 DELETE 정책. `deleted_at is not null` 조건은 **일부러 넣지 않았다**(tombstone이 아닌 자식이 하나라도 있으면 read-back이 영원히 실패해 **빠져나올 수 없는 덫**이 된다 — 자료 보호층은 이미 세 겹이다). `autoSync`는 `r.failed > 0`이면 실패로 보고한다.
- **검증**: 앱과 같은 역할로 3종 — 소유자가 tombstone 여행 하드 삭제 **1행** ✅ / 허용목록 밖 0행 ✅ / 남의 계정 0행 ✅ (`BEGIN…ROLLBACK`).
- **예방(게이트를 연산 단위로 넓혔다)**: `deleteOpsAreGranted` — 코드에 `.delete()`가 있으면 그 테이블마다 DELETE GRANT와 DELETE 정책이 있는지 검사.
- **⚠️ 이 게이트가 처음엔 공허했다**: 느슨한 정규식(`grant …{0,120}… on journey.trips`)이 **문장 경계를 넘어** 다른 테이블의 grant를 물어, trips의 권한을 지워도 통과했다. **비공허 확인을 안 했으면 이 결함을 그대로 배포했을 것이다.** 문장 단위로 끊어 파싱하도록 고치고, "다른 테이블의 권한에 속지 않는가" 셀프테스트를 추가했다.

## M-0023 · 영구삭제 방식을 바꾸면서 **옛 방식으로 지운 것들을 데려오지 않았다**
- 날짜: 2026-07-26 · 발견: 사용자가 마지막 테스트를 하려고 휴지통을 열었는데 *"휴지통에 아무것도 없는데용?"* · 심각도: major(사용자 의도가 반영되지 않은 채 영구히 방치)
- **증상**: 휴지통은 `비어 있어요`인데 서버엔 삭제된 여행 `테스트`(07-25 14:09)가 순간 1 · 사진 1과 함께 tombstone으로 남아 있었다.
- **원인**: ADR-0027 **이전**의 `purgeTripPermanently`는 로컬 표식만 남기고 서버엔 아무것도 알리지 않았다(ADR-0025 — *"서버 행은 tombstone으로 남겨 둔다"*). 그 시절에 지운 항목은 **전파 op가 애초에 만들어진 적이 없어** 아무리 동기화해도 안 간다. 게다가 로컬 표식 때문에 pull이 그 id를 건너뛰어 **휴지통에도 안 보인다** — 어디서도 손댈 수 없는 상태.
- **근본형**: **"규칙을 바꾸면서 옛 규칙으로 만들어진 것들을 데려오지 않았다."** ADR-0027(전파 추가)과 ADR-0030(하드 삭제)은 *앞으로의 삭제*만 설계했다. **이미 옛 방식으로 지워진 것들에게는 아무 일도 일어나지 않는다**는 사실을 아무도 묻지 않았다. M-0006의 `requeueOrphanTombstones`가 정확히 같은 형태의 처방이었는데, 영구삭제 쪽엔 그 층을 안 만들었다.
- **왜 진단이 못 잡았나(더 아픈 부분)**: 「저장 상태」는 **활성 개수**를 클라우드↔이 기기로 대조한다. tombstone은 활성에 안 들어가므로 **대조에 걸리지 않는다.** 「서버에 남는 표식 11건」은 접힌 출처라 판정이 아니다 — 숫자는 화면에 있었는데 **아무도 그것을 판정하지 않았다.** §8이 말하는 "관측이 아니라 판정"의 실패다.
- **수정**: `StoreStatePort.tombstonedIds()` 신설 → `서버 tombstone ∩ 로컬 purgedIds`를 **「지웠는데 서버에 남은 항목」** 지표로(0이 정상, 아니면 `problem`). 복구는 `requeueUnpropagatedPurges()` — **의도를 다시 실어 보낼 뿐** 로컬은 건드리지 않는다(이미 사용자 뜻대로 지워져 있다). 판정 문장도 이걸 **가장 먼저** 말한다(사용자 의도가 반영되지 않은 상태라 제일 무겁다).
- **가장 위험한 오작동을 막은 지점**: 표식이 **없는** 서버 tombstone은 *다른 기기가 휴지통에 넣은 것*이다 — 그걸 영구삭제로 바꾸면 **남의 의도를 내가 뒤집는다.** 표식 있는 것만 큐에 넣는다.
- **예방**: 유닛 10건(찾기 3·복구 3·오작동 차단 2·멱등 2). **비공허 확인**: 표식 검사를 빼니 2건 RED. 헌장 `sync-offline-dev` §2-C 신설.

## M-0022 · **확인은 해놓고 그 결과를 사용자에게 말하지 않았다** — 되돌릴 수 없는 버튼 앞에서
- 날짜: 2026-07-26 · 발견: 사용자 실기기(이관 실행 화면) · 심각도: major(되돌릴 수 없는 행동의 근거가 화면에 없었다)
- **증상**: 이관을 실행하니 화면이 `8장 옮김.`이라고만 했다. 그건 **업로드 성공**을 뜻하지 "새 저장소에 실제로 있다"가 아니다. 그런데 사용자가 다음에 누를 버튼은 **[옮긴 뒤 옛 파일 정리] — 되돌릴 수 없다.**
- **원인**: `migrateMediaBytes`는 설계대로 되읽어 확인했고 `safeToRemove`에 담아 반환까지 했다. **그런데 `describeMigration`이 그 필드를 안 읽었다.** 검증을 *수행*하는 것과 그 결과를 *보여주는* 것을 별개 작업으로 취급했고, 뒤엣것을 빠뜨렸다.
- **근본형**: **"확인했으니 됐다"** — 확인의 목적은 *내가 아는 것*이 아니라 **사용자가 결정할 수 있게 하는 것**이다. 사용자가 볼 수 없는 확인은 없는 것과 같다. 특히 되돌릴 수 없는 행동 앞에서는 그 근거가 반드시 화면에 있어야 한다(원칙 #5 복구 가능성 우선 · §8 판정).
- **왜 유닛이 못 잡았나**: 유닛 15건이 전부 **`MigrateReport`의 숫자**를 검사했다. 숫자는 다 맞았다. **화면에 무엇이 나가는지를 검사한 것이 하나도 없었다** — 검사의 시선이 사용자가 아니라 자료구조에 있었다.
- **수정**: `describeMigration`이 확인 수를 반드시 말한다. 전부 확인 → `8장 모두 확인했어요` / 일부 → `3장 중 2장 확인했어요 — 확인된 것만 정리됩니다` / 없음 → `⚠️ 확인된 것이 없어요 — 옛 파일을 정리하지 마세요`.
- **함께 고친 것 2건(같은 화면에서 드러남)**:
  1. 「옛 저장소에 남은 사진 8개」가 이관 뒤에도 8이라 *"안 옮겨졌나?"*로 읽혔다. 개수만 세면 **아직 안 옮긴 것**과 **옮겼는데 원본이 남은 것**을 구분 못 한다 — 사용자가 할 일이 정반대다(옮기기 vs 정리). 두 집합을 다 붙잡아 설명을 진행 상황에 맞게 바꿨다.

- **예방**: 유닛 4건 — 전부 확인/일부 확인/확인 없음(경고)/정리 후에도 확인 수 유지. **비공허 확인**: 확인 문구를 지우니 4건 RED.

## M-0020 · 새 테이블에 **GRANT를 빠뜨리고**, 그 검증을 **superuser로** 해서 통과라고 보고했다
- 날짜: 2026-07-26 · 발견: **사용자 실기기 화면**(진단 「저장 상태」가 `! 문제 · 확인하지 못했어요 / 영구삭제 원장 조회 실패:`) · 심각도: **critical**
- **증상**: 콜론 뒤가 **비어 있었다.** 빈 오류 메시지가 단서였다 — PostgREST가 본문 없이 거절했다는 뜻이다.
- **원인 두 겹**:
  1. 마이그레이션 0012가 `journey.purged_ids`를 만들면서 **`grant … to authenticated`를 빠뜨렸다.** 형제 테이블 넷(trips/moments/media/expenses)에는 전부 SELECT·INSERT·UPDATE가 있었고 **새 테이블 하나만 조용히 빠졌다** — 이 저장소의 최빈 결함군 그대로다(§7).
  2. **RLS와 GRANT를 같은 층으로 오인했다.** GRANT는 *"이 역할이 이 테이블에 접근이나 할 수 있는가"*, RLS는 *"그중 어느 행을 볼 수 있는가"*다. 정책을 정성껏 썼으니 다 했다고 여겼는데, 문 자체가 잠겨 있었다.
- **실제 피해(진단 화면보다 훨씬 크다)**: `pushPurges`의 `ledgerAdd`도 같은 표에 쓴다 → **영구삭제가 서버에 반영되지 않았다.** v0.79의 핵심 기능이 배포된 채로 죽어 있었고, 사용자가 휴지통을 비워도 서버 자료가 남았을 것이다.
- **왜 내 "검증"이 통과했나 — 이게 진짜 교훈**: 0012 적용 뒤 나는 트리거 실효를 확인하고 *"라이브 DB에서 트리거가 원장 id 재삽입을 실제로 거부(0행)"*라고 보고했다. **그 SQL을 superuser로 돌렸다.** superuser는 GRANT도 RLS도 우회한다 — **앱이 쓰는 역할이 아니다.** 헌장 §4에는 `set_config('request.jwt.claims', …)`로 **남이 되어 보라**고 적혀 있었고, 그대로 했으면 즉시 잡혔다.
- **근본형**: **"검증을 대상의 실제 실행 조건이 아닌, 내가 편한 조건에서 했다."** 헤드리스가 모바일 `vh` 버그를 재현 못 하던 것과 같은 형태다 — 그때는 한계를 알고 계약 검사로 우회했는데, 여기서는 **한계를 인지조차 못 하고 성공을 통과로 읽었다.** "통과했다"의 기준은 결과가 아니라 **같은 역할·같은 조건이었는가**다.
- **수정**: 마이그레이션 0013 — `grant select, insert on journey.purged_ids to authenticated`(**UPDATE·DELETE는 일부러 주지 않는다** — 원장을 고치거나 지울 수 있으면 좀비 차단이 뚫린다) + 두 정책에 `is_allowed()` 결합(§2.2도 함께 빠져 있었다).
- **검증(이번엔 제대로)**: `set local role authenticated` + **실제 허용 이메일**로 5종 — 소유자 6건 조회 ✅ / 허용목록 밖 0건 ✅ / 남의 계정 0건 ✅ / 소유자 원장 기록 성공 ✅ / 남의 소유로 위조 삽입 거부 ✅. 전부 `BEGIN … ROLLBACK`(원장 6건 그대로, 흔적 0 확인).
  - **이 과정에서 오진도 한 번 했다**: 첫 시도에서 가짜 이메일(`owner@x`)을 썼더니 `is_allowed()`가 정상 작동해 0건이 나왔고, 나는 그걸 결함으로 읽을 뻔했다. 이메일은 손으로 적지 말고 `allowed_users`에서 **읽어서** 써야 한다.
- **예방(게이트 `check-migration-grants` — 18번째)**: 마이그레이션에서 `create table journey.X`를 찾아 ①`grant … to authenticated`가 어딘가에 있는가 ②그 테이블 정책에 `is_allowed()`가 결합됐는가를 검사. 제외는 `NO_GRANT_REQUIRED`에 **근거를 적어야** 한다(`allowed_users`는 앱이 직접 읽지 않고 SECURITY DEFINER 함수만 읽으므로 제외). **비공허 확인**: 0013의 GRANT 줄을 지우니 RED, `is_allowed()`를 지우니 RED — 둘 다 **오늘 사용자가 실제로 겪은 상태**를 그대로 재현한 것이다.
- **함께 명문화**: 헌장 §3에 GRANT 단계와 "GRANT≠RLS", §4 머리에 **"superuser로 확인한 것은 검증이 아니다"**를 굵게 넣었다.

## M-0018 · 보안 규칙을 **단건 연산만 상정해** 써 두고, 목록 연산에는 규칙이 없었다
- 날짜: 2026-07-26 · 발견: 목록 조회 기능을 만들기 전 §9 정독 중 · 심각도: minor(사고 전 발견 — 구멍만 있었고 코드는 아직 없었다)
- **증상**: `supabase-security-dev` §2.7의 R2 4중벽 중 세 번째가 *"객체 키를 서버가 생성"*이라고만 적혀 있었다. 이 문장은 **한 객체를 다루는 연산**(put/get/delete)만 상정한 것이다. 여러 객체를 훑는 연산에는 **규칙이 아예 없었다.**
- **왜 위험한가**: 단건 연산에서는 키를 서버가 만들어 남의 폴더를 못 가리킨다. 그런데 목록은 **prefix 하나로 버킷 전체가 열린다.** R2엔 RLS가 없으므로 그 한 줄이 마지막 벽이다. 규칙이 없는 채로 만들었다면 "클라이언트가 prefix를 보내면 편하겠네"가 자연스러운 구현이 됐을 것이다.
- **근본형**: **"규칙을 그때 있던 사례의 모양대로 쓴다."** 오버레이 잘림 사고 때 `ui-responsive-dev`에 `vh`/`dvh` 규칙이 **아예 없었던 것**과 같은 형태다 — 읽었어도 못 막았을 구멍이다. §9 2단계("정독 중 문서와 코드가 어긋나거나 규칙이 빠져 있으면 그것부터 고친다")가 존재하는 이유가 정확히 이것이고, 이번엔 **그 단계가 실제로 작동해서** 코드보다 먼저 잡혔다.
- **수정**: 헌장에 §2.8 신설 — prefix는 검증된 sub에서만 · 요청 본문의 prefix/delimiter/bucket은 **무시가 아니라 미파싱**(파싱해 두면 다음 사람이 쓰게 된다) · 목록 서명 URL을 브라우저에 주지 않는다 · 응답에 전체 키 대신 mediaId만 · 잘렸으면 잘렸다고 말한다.
- **예방(게이트)**: `check-verdict-symmetry`의 `listPrefixIsServerBuilt` — 네 조항을 소스에서 정적으로 검사. **비공허 확인**: 본문 prefix를 신뢰하도록 주입하니 2건 RED.
- **함께 고친 것**: 이 게이트의 성공 로그가 셀프테스트 수를 **`37`로 손으로 박아** 두고 있었다(그래서 4건을 추가해도 계속 37이라고 말했다). 개수를 손으로 세지 않는다는 규율을 게이트 자신이 어기고 있었던 것 — 배열 길이에서 파생하도록 바꿨다.
- **또 하나**: 옛 유닛 검사가 *"알 수 없는 op은 거부한다"*의 예시로 하필 `'list'`를 쓰고 있어, `list`가 실제 op이 되자 RED가 됐다. **검사가 잡아준 게 맞다** — 예시는 실제로 없는 이름이어야 한다(`'exfiltrate'`로 교체).

- 날짜: 2026-07-26 · 발견: 사용자 지적("의도를 가지고 삭제하는건데 서버에 왜 살려두나요?") · 심각도: major(설계)

- **원인**: ADR-0025와 ADR-0027이 서버 행 하드 삭제를 기각한 근거가 **글자 그대로 같았다** — *"그 사실을 모르는 다른 기기가 자기 사본을 다시 올려 좀비를 만든다."* 근거 자체는 사실이었다. 틀린 것은 **"좀비를 막는 방법은 행을 남기는 것뿐"이라는 숨은 가정**을 두 번 다 검증하지 않은 것이다. 서버가 재삽입을 거부하게 만들면(원장+트리거) 그 가정은 무너지고 자료를 살려둘 이유가 통째로 사라진다.
- **근본형**: **"이미 내린 결정의 근거를 재사용하면서 그 근거의 전제를 다시 묻지 않는다."** 두 번째 ADR은 첫 번째를 *인용*했지 *재검토*하지 않았다. 결정 재사용은 효율이지만, 같은 결론에 두 번 도달했다는 것은 오히려 **가정을 검증하지 않았다는 신호**로 읽어야 했다.
- **함께 드러난 것**: 사용자는 두 번 다 정확히 옳았고, 나는 두 번 다 "설계대로"로 닫으려 했다. M-0016도 똑같이 "오해로 닫을 뻔한 신고"를 파다가 나왔다. 사용자 신고를 설명으로 닫는 순간 조사가 멈춘다.
- **수정**: ADR-0030 — `journey.purged_ids` 원장(id만) + BEFORE INSERT 트리거로 재삽입을 **물리적으로** 차단하고, 서버 행은 하드 삭제한다. `purged_at` 컬럼(0011)은 제거. 전파는 pull이 아니라 원장이 담당(`applyPurgedLedger`).
- **전환에서 하마터면 낸 2차 결함**: 컬럼을 DB에서 드롭한 뒤 `storeState.ts`가 여전히 `.is('purged_at', null)`로 조회하고 있었다 — 배포됐으면 진단 화면이 400으로 죽는다. 손으로 고른 파일 목록이 아니라 **src 전체**를 훑는 게이트(`noDroppedPurgedAtColumn`)로 잡았다.
- **예방(게이트 3종, 전부 비공허 확인)**:
  - `purgeOrderContract` — 원장 기록·경로 조회가 **행 삭제보다 앞**에 오는가, read-back 3종이 있는가. 순서는 코드를 훑어봐선 뒤집힌 줄 모른다. *주입: 원장을 삭제 뒤로 → RED.*
  - `runSyncAppliesLedger` — `runSync`가 원장을 읽어 적용하는가. 빠지면 다른 기기가 영구삭제를 영영 못 배운다. *주입: 호출 제거 → RED.*
  - `noDroppedPurgedAtColumn` — 사라진 컬럼 참조가 src 어디에도 없는가. *주입: `storeState.ts`에 옛 조회 복원 → RED.*
- **문서에 남긴 규율**: CLAUDE.md §0의 "하드 삭제 없음"에 **예외를 명시**했다. 조항의 *목적*(좀비 차단)과 *수단*(행 유지)을 구분해 적지 않았던 것이 이 실수를 가능하게 했다.

## M-0016 · 영구삭제가 **로컬에 보이는 자식만** 치움 — 사진만 서버에 표식 없이 남았다
- 날짜: 2026-07-26 · 발견: 사용자 신고("서버에서는 아직도 사라지지 않는")를 서버 대조로 조사하다 · 심각도: major
- **증상**: 여행 `R2 테스트`를 영구삭제했더니 **여행·순간엔 `purged_at`이 찍혔는데 사진(`e12f7cc6`)만 null**이었다. 그 사진은 어느 기기에서도 영구삭제되지 않고 서버에 영영 남는다.
- **원인**: `purgeTripPermanently`가 자식을 **로컬 Dexie에서만** 찾는다(`d.localMedia.where('tripId')`). 그런데 tombstone된 사진은 그 기기에 **로컬 행이 아예 없을 수 있다** — `pullMedia`가 "로컬에 없는 tombstone은 만들지 않는다"는 **비파괴 규율**(불변식 #8)로 건너뛰기 때문이다. 두 규율이 각각은 옳은데 **맞물리는 지점에 구멍**이 생겼다.
- **근본형**: "로컬이 못 보는 것은 없는 것으로 친다." M-0006의 서버 기준 스윕이 같은 형태였다 — 그때는 *로컬에 없는 서버 고아*를 pull에서 잡았는데, **영구삭제 경로엔 그 층을 안 만들었다.**
- **수정**: `PurgeRemote.markFamily(tripId)` 신설 — 여행 purge를 push할 때 **서버 기준으로** `trip_id = X`인 자식 전부에 표식을 찍는다. 등록부(`PURGE_DOMAINS`)를 돌므로 새 도메인이 자동으로 따라온다. `unmarkedInFamily()`로 **read-back**해 0이 아니면 완료로 치지 않고 큐에 남긴다(조용히 넘기면 그 사진은 영영 남는다). 이미 찍힌 것은 `.is('purged_at', null)`로 시각을 덮지 않는다(최초 영구삭제 시각 보존).
- **이미 발생한 피해 복구**: 부모가 purged인데 자식이 안 찍힌 행에 표식을 소급 적용(행은 지우지 않음 — §0).
- **예방**: 유닛 3건 — 여행 purge가 `markFamily`를 부르는가 · read-back이 0이 아니면 실패로 남기는가 · 자식 op는 가족 쓸기를 하지 않는가(여행 단위 1회). **비공허 확인**: 가족 쓸기를 제거하니 3건 RED.
- **함께 배운 것(사용자 대면)**: 사용자는 "서버에 안 사라진다"고 신고했는데 그중 **대부분은 설계대로**(ADR-0027이 행을 일부러 남긴다)였고 앱이 그걸 설명하지 않았다(v0.76에서 수정). **진짜 결함은 그 신고를 조사하다 발견됐다** — 신고를 "오해"로 닫았으면 이걸 못 찾았다.

## M-0015 · 전파 기능을 만들어 놓고 **화면에서 부르지 않음** — 영구삭제가 큐에 앉아만 있었다
- 날짜: 2026-07-26 · 발견: 사용자 제안("자동동기화 기능이 있어야 될 거 같아요")을 검토하다 코드 확인 · 심각도: major

## M-0013 · 오버레이 규칙을 세 곳에 손으로 구현 — 가로 태블릿에서 모달 상하가 잘림

## M-0014 · 스킬 문서가 있는데 안 읽었고, 읽었어도 그 규칙이 문서에 없었다
- 날짜: 2026-07-26 · 발견: 사용자 제안("모든 코딩 시작 전 스킬문서부터 정독하고, 정독 과정에서 오류나 모순이 있으면 그것부터 정리하고 시작하면 되지 않을까요?") · 심각도: major(프로세스)

## M-0012 · 결함을 고치면서 **형제 목록을 손으로 골라** 절반만 고침 — 게이트도 같은 범위로 만들어 통과시킴
- 날짜: 2026-07-26 · 발견: **사용자 화면 캡처**(휴지통 영구삭제 설명에 별표 노출) · 심각도: major
- **증상**: `영구삭제는 되돌릴 수 없어요. **이 기기의 저장공간**을 비우는 것이며…` — 마크다운 강조가 **글자 그대로** 화면에 찍혔다. `dataManager`·`r2Setup`·`changelog`·`diagnosticsHub`·`fx` 등 여러 화면에 40건 가까이 있었다.
- **원인(이게 핵심이다)**: 직전 릴리스(M-0010)에서 **같은 결함을 하나 고쳤다** — `envReport.ts`의 저장소 경고 문구. 그리고 재발 방지 게이트까지 붙였다. 그런데 그 게이트의 대상 파일을 **손으로 6개 골랐다**(`TEXT_SURFACES` 배열). 그래서:
  - 형제 화면 전체가 검사 밖에 남았고,
  - **그 게이트를 만든 바로 그 릴리스의 변경 노트에 내가 새 `**`를 넣었는데도 통과했다.**
  같은 커밋에서 나는 CLAUDE.md §7에 *"형제 목록을 적는다. **손으로 세지 말고 등록부/디렉터리에서 뽑는다**"*라고 썼다. 조항을 쓰면서 그 조항을 어겼다 — 조항만으로는 안 지켜진다는 §7의 주장을 내가 스스로 실증한 셈이다.
- **더 깊은 원인**: 규칙을 **문자열 쪽**에 걸었다("이 파일들에서 `**` 쓰지 마라"). 문자열은 무한히 늘어나고 새 파일은 계속 생기므로, 그 방향의 규칙은 반드시 샌다. 규칙은 **경로가 좁은 쪽**(렌더러)에 걸어야 한다.
- **수정**: `ui/dom.ts`의 `el()`·`setNote()`가 통과하는 `applyText()`를 만들어 `**강조**`를 `<strong>`으로 렌더한다(innerHTML 없이 textContent 조각으로만 — 사용자 입력이 섞여도 마크업이 될 수 없다). 파싱은 순수 함수 `parseEmphasis()`로 분리해 DOM 없는 유닛이 모든 경계를 실제로 돌린다. 짝이 안 맞는 `**`는 **먹지 않고 평문으로 되돌린다**(사용자 글자를 삼키지 않는다).
- **예방(3층, 이번엔 범위를 기계가 정한다)**:
  1. **구조** — 강조 처리가 `el()` 안에 있어 누가 어디에 무슨 문자열을 쓰든 자동으로 따라온다. "다음 사람이 이 규칙을 몰라도 지켜지는가?" = 예.
  2. **정적** — `check-verdict-symmetry`를 고쳐 ① 손으로 고른 목록을 **없애고 `src/` 전체를 걷고**(61개 파일) ② 금지 대상을 문자열이 아니라 **우회 경로**(`textContent`에 강조 문자열 직접 대입)로 바꾸고 ③ 안전 렌더러가 온전한지(applyText 존재·`<strong>` 생성·innerHTML 없음·el()이 실제로 사용) 검사한다.
  3. **라이브** — `verify-editor-live`가 실제 브라우저에서 휴지통·변경 이력을 열어 **화면 텍스트에 `**`가 없고 `<strong>`이 실제로 있는지** 본다. 이 층이 최종 판정이다 — 정적은 "우회가 없다"까지, 유닛은 "파싱 규칙"까지만 본다.
- **비공허 검증**: `el()`이 `applyText`를 안 쓰게 되돌리자 정적 게이트 RED + 라이브 2건 FAIL, 그리고 라이브가 **사용자 캡처의 그 문장을 그대로 재현**했다.
- **부수 오탐 2건(기록)**: ① 게이트가 `dom.ts` 머리주석의 "innerHTML 금지"를 사용으로 오탐 → 주석 제거 후 검사. ② 내 변경 노트가 별표 두 개를 **예시로 리터럴 포함**해 라이브가 RED — 이건 결함이 아니라 문구 문제라 문구를 고쳤다(`check-doc-counts`에서 이미 겪은 "검사 대상의 문법을 문서가 리터럴로 포함하면 오탐"과 같은 형태).

- **증상**: 여행을 지워도 서버 `media` 행이 **활성으로 남고** R2 객체도 잔류. 휴지통에서 영구삭제한 여행이 **다음 동기화에 되살아남**.
- **원인 3형(같은 뿌리 — 로컬만 바꾸고 서버에 알리지 않음)**:
  1. `softDeleteTripLocalFirst`가 사진·비용을 tombstone하면서 **큐 op는 순간만** 만들었다. 주석에 이유가 화석으로 남아 있었다: *"미디어는 로컬 전용이라 op를 만들지 않는다"* — 그 전제는 사진·비용 동기화가 생기며 무너졌는데 **이 함수만 갱신되지 않았다.** 결정적으로 `moments.ts`의 순간 삭제는 **처음부터 올발랐다** → *같은 규율을 두 곳에 손으로 구현한 것*이 진짜 뿌리.
  2. `purgeTripPermanently`가 로컬 행을 **하드 삭제**했다. `mergeDecision`의 `if (!local) return 'take-server'`와 만나 다음 pull에서 부활. 동기화 전 영구삭제는 큐 op를 고아로 만들어 폐기시켜 **서버에 활성 행**이 남았다.
  3. 정합 복구를 **1회만** 실행하게 최적화한 결과 표식 이후 생긴 고아를 영영 놓쳤고, **로컬에 행 자체가 없는 경우**는 재큐잉이 원리적으로 닿지 못했다.
- **수정**: (1) `trips` 삭제·복원 양쪽에 media·expense op 추가 + `requeueOrphanTombstones` (2) **ADR-0025 A안** — 사전 조건(`PendingSyncError`) + `purgedIds` 표식, 네 pull이 건너뜀, 서버는 tombstone 유지 (3) **pull에서 서버와 대조**(로컬 tombstone + 서버 활성 = 도달 실패의 직접 증거, 비용 0) + **서버 기준 스윕**(로컬 없음 + 서버 활성 + 부모 영구삭제 → 되살리지 않고 정리) + `retryFailedOps`(막다른 `permanent_failed` 탈출구).
- **예방(게이트)**: `check-domain-symmetry`(신설) — ① `softDeleteX`가 있으면 `restoreX`도 있어야 함 ② **모든 `*LocalFirst`가 큐에 op를 넣어야 함**(정적). `tests/unit/cascadeOps.test.ts` 18개 — 자식 전 종류 op·고아 0 불변식·복원 대칭·서버 대조·스윕 경계·재시도(실행). **정적+실행 두 층이 함께**여야 한다: 정적은 "op를 넣는 코드가 있다"까지만 보고, "자식 종류를 빠짐없이 넣는지"는 실행이 잡는다.

## M-0004 · 시크릿 스캐너 게이트 거짓통과 (첫 매치만 검사 → service_role 우회)
- 날짜: 2026-07-22 · 발견: 적대적 저장소 검토(게이트 비공허성 검사, 재현 성공) · 심각도: critical

- **예방(게이트)**: 셀프테스트가 스크립트에 내장되어 매 실행마다 게이트 비공허성을 증명. 신규 게이트는 셀프테스트 내장을 기본으로 한다(`check-csp.mjs`도 동일 패턴).

## M-0005 · Dexie 인덱스에 null 필드(deletedAt) 선언 — tombstone 설계와 양립 불가
- 날짜: 2026-07-22 · 발견: 적대적 저장소 검토 · 심각도: major(스키마 v1 확산 전 발견)
- **증상**: `offline/db.ts`가 `deletedAt`(활성 행 = null)을 인덱스로 선언. IndexedDB는 null을 인덱스 키로 저장할 수 없어 활성 행 전부가 해당 인덱스에서 누락되고 `where('deletedAt').equals(null)`은 예외 — tombstone 전용 삭제 계약(ADR-0011)의 기반 인덱스가 처음부터 무효.
- **원인**: SQL 인덱스 직관을 IndexedDB에 그대로 적용(브라우저 현실 미검증 — M-0003과 같은 근본형).
- **수정**: `deletedAt`을 인덱스에서 제거(스키마 v1이 퍼지기 전). tombstone 필터는 `.filter()`, 인덱스가 필요해지면 Phase 1에서 센티널(`0 | ISO`) 마이그레이션.
- **예방(게이트)**: Dexie `stores()` 선언에 nullable 필드 인덱스 금지 — Phase 1 동기화 구현 시 `check-dexie-schema` 게이트로 기계화 예정.
