# 동영상 지원 설계안 (VIDEO_PROPOSAL)

> 상태: **제안 · 미승인.** 코드 변경 0건. 사용자 결정 대기.
> 작성: 2026-07-27 · 근거: 도메인 에이전트 4종 조사(media-pipeline · supabase · offline-sync · travel-experience-director) + 저장소 실측 대조.
> 이 문서는 **결정을 위한 자료**다. 승인되면 `docs/DECISIONS.md`에 ADR로 옮기고 이 문서는 그 근거로 남는다.

## 0. 한 장 요약

| 질문 | 답 |
|---|---|
| 기술적으로 가능한가 | **가능하다.** 단 "사진과 같은 방식"으로는 **불가능**하다 |
| SPEC이 뭐라고 하나 | `PROJECT_SPEC.md:43` — 영상은 **2차**. MVP가 아니다 |
| 그럼 무엇을 먼저 하나 | **오디오 노트.** `PROJECT_SPEC.md:37`(S-01)이 MVP로 이미 지정했는데 **미구현**이다 |
| 영상을 한다면 어떤 모양인가 | **A안(표식만)** 또는 **B안(로컬 전용 짧은 클립)**. 서버 업로드(C안)는 MVP 밖 |

**핵심 판단**: 영상이 사진 대비 추가로 회수하는 것은 **소리 · 움직임 · 말** 셋이다. 그중 **둘(소리·말)을 오디오 노트가 두 자릿수 배 낮은 비용으로 회수**한다. 그래서 권고는 "영상을 나중에 하자"가 아니라 **"오디오를 먼저 하자"**다.

## 1. 실측으로 확인한 파손 지점 (전부 코드 인용 대조 완료)

에이전트 보고를 그대로 싣지 않고 **직접 확인한 것만** 적는다.

### 1-A. 서버가 영상을 거부한다 — 그리고 더 나쁜 것

```ts
supabase/functions/media-sign/index.ts:189
  if (!/\.webp$/i.test(rest)) return null;      // .mp4 → bad_media_path 400

supabase/functions/media-sign/index.ts:333
  const base = last.replace(/\.webp$/i, '');    // 삭제 검증층이 확장자에 의존
```

🔴 **`safeRest`(정문)만 열고 `mediaIdOfKey`(검증층)를 안 고치면 「성공했다는 거짓말」이 배포된다.** 영상 키는 id 매핑에 안 잡히고, `deleteMany`는 그것을 「이미 없는 것」으로 처리한 뒤 되읽기에서도 못 보므로 **`verified: true`를 반환한다** — 「영구삭제 후 남은 사진 파일 정리」가 성공·확인됨을 보고하는데 바이트는 R2에 그대로 남는다.

M-0029는 **실패가 조용**했던 건이고, 이건 **성공이 거짓**이라 더 나쁘다. 두 함수는 **반드시 같은 커밋**이고, 확장자 목록을 각자 손으로 갖게 하면 그 자체가 §7 드리프트다 — **한 상수를 두 함수가 지나게** 한다.

### 1-B. 압축 파이프라인은 영상을 디코드조차 못 한다

```ts
src/media/compress.ts:24-46   createImageBitmap(source)   ← video/mp4 Blob이면 reject
src/services/media.ts:130     compressForStorage(...)     ← 무조건 호출 → 던지면 인테이크 전체 실패
```

`<video>`는 **DOM 엘리먼트라 Web Worker에서 만들 수 없다.** 즉 이 저장소의 "OffscreenCanvas + Worker" 모델은 영상 포스터 추출에 **원리적으로 적용 불가**하고, 메인 스레드 전용이 된다.

### 1-C. CSP가 영상 재생을 막는다 — §7 비대칭

```
index.html:17   img-src 'self' data: blob: …     ← 사진은 blob: 허용
                media-src 지시어 없음             ← default-src 'self'로 폴백 → <video src="blob:"> 차단
```

`scripts/check-csp.mjs`의 REQUIRED에도 `media-src`가 없어 **게이트가 이 누락을 알려주지 않는다.** 사진에서 옳다고 판단한 것이 형제에게 안 걸린 §7 전형이다.

### 1-D. 멀티파트 업로드가 없다 (청소만 있고 손이 없다)

```ts
index.ts:228  FN_OPS = ['probe','capabilities','list','put','get','delete','deleteMany','abortMultipart']
index.ts:58   EXPIRES_SEC = 300   // 5분
```

**조각을 치우는 빗자루(`abortMultipart`)는 있는데 조각을 만드는 손이 없다.** `presign`의 method 유니온도 `PUT|GET|DELETE`라 POST를 서명할 수 없다.

🔴 **결정적 손실 경로**: 100MB를 모바일 업링크로 올리면 5분에 닿는다 → R2가 **403** → `merge.ts:67`이 403을 `'permanent'`로 판정 → push는 `permanent_failed`를 **영원히 건너뛴다**. 사유(서명 만료)는 일시적인데 **판정이 영구로 굳는다.** M-0033이 경고한 바로 그 형태다.

**만료를 늘리는 것은 답이 아니다** — 유출 창을 넓히는 순수 손실이다. 답은 멀티파트 또는 **크기 상한**이다.

### 1-E. 백업이 정확히 필요할 때 실패한다

```ts
src/services/backup.ts:360-362  전 바이트를 entries 배열에 올린다
src/services/zip.ts:104-111     그 위에 다시 단일 버퍼로 복사     → 피크 ≈ 총량 × 2
src/services/zip.ts:58,73-75,82 크기·오프셋이 전부 setUint32     → 4GiB 초과 시 조용한 손상
src/services/zip.ts:95-96       엔트리 수 setUint16              → 65,535개 초과 시 손상
```

그리고 `diagnostics.ts:136`은 저장 여유가 80%를 넘으면 *"지금 백업으로 파일을 받아 두세요"*라고 안내한다.

> 🔴 **여유가 없을 때 하라고 안내하는 유일한 행동이, 여유가 없을 때 정확히 실패한다.**

ZIP은 무압축(store)이므로 영상은 **1바이트도 줄지 않는다**(`zip.ts:54`).

### 1-F. 지표가 거짓말을 시작한다

`storage.ts:40`이 3-blob 합을 `photoBytes`에 넣고 화면은 「🖼 사진」으로 표시한다(`dataManager.ts:61`). **사용자는 4K 영상 두 개 때문에 「사진」이 5GB라고 읽게 된다** — §8 정면 위반.

그리고 `r2.ts:39`의 `mediaIdFromPath`가 `.webp`만 인정하므로 영상 객체는 진단에서 **「설명할 수 없는 사진 파일」로 오탐**되고, 사용자가 [정리] 버튼을 누르면 **살아 있는 자기 영상을 지운다** — §0(원본 임의 삭제 금지)에 닿는 경로다.

## 3. 저장 전략 3안

세 안 모두 **포스터 프레임 + 메타는 사진과 동일 규율로 로컬 내구성 커밋**을 공통 전제로 한다. 이건 선택지가 아니라 **원칙 #1의 최소선**이다 — 포스터가 없으면 서버가 죽는 순간 소비 기기에서 *그 순간의 존재 자체*가 화면에서 사라지고, 사용자에겐 「기억이 없어진 것」과 구분되지 않는다.

| | **A안** 표식만 | **B안** 로컬 전용 클립 | **C안** 서버 동기화 |
|---|---|---|---|
| 영상 바이트 | 저장 안 함 | Dexie 로컬만 | R2 업로드 |
| 앱 내 재생 | ✕ (갤러리로 연다) | ○ 그 기기에서만 | ○ 모든 기기 |
| 로컬 quota | ○ 무해 | △ 상한 필요 | △ |
| 백업 ZIP | ○ 메타만 | △ 메타만(제외 명시) | ✕ 4GB 벽·OOM |
| 업로드 resume | 불필요 | 불필요 | **필수**(없으면 1-D 함정) |
| 서버 계약 변경 | 없음 | 없음 | 마이그레이션+함수+앱 3단 |
| 영상 바이트 계층 수 | 갤러리 only | ①+갤러리 | ②+갤러리 |
| MVP 적합 | ○ | △ | ✕ |

**두 에이전트가 독립적으로 A/B를 권고했고 C를 MVP 밖으로 밀었다.** 근거가 같다: C안은 §1-A·1-D·1-E를 **전부** 활성화시키는데, 얻는 것은 "다른 기기에서도 본다" 하나다.

### 백업에서 영상을 빼는 것이 원칙 #1과 충돌하는가

**조건부로 정당하다.** 선례가 있다 — `DISASTER_RECOVERY.md:69`가 원본 사진의 클라우드 사본 부재를 *"버그가 아니라 계약"*이라고 못박았다. 그러나 그 선례가 성립한 이유는 원본 사진이 **①③ 두 계층**에 남기 때문이다. 영상 바이트를 ③에서 빼고 ②에도 안 올리면 **① 하나만** 남고, ①은 DR 문서가 *"축출·사이트데이터 삭제·기기 분실"*로 죽는다고 명시한 계층이다.

**정당해지는 조건 셋 — 전부 충족해야 한다:**

1. **사용자 갤러리의 원본이 살아 있다**는 사실이 진짜 계층 하나로 셀 수 있다(§0: 앱은 원본을 건드리지 않는다). **단, 앱 안에서 트리밍·편집한 영상에는 이 논거가 성립하지 않는다** — 그건 앱이 유일 원천이다.
2. **메타는 반드시 백업에 담는다** — 어느 순간에 붙었는지·촬영시각·길이·크기·**바이트 해시**·원 파일명. 바이트를 빼도 *기억의 뼈대*는 ③에 남아야 복원 후 "이 영상을 다시 붙여 주세요"가 가능하다.
3. **앱이 그 제외를 소리 내어 말한다** — 백업 완료 화면에 「영상 3개(1.2GB)는 이 파일에 들어 있지 않습니다」를 판정 문장으로. 조용한 제외는 §12의 정확한 재현이다.

> 그리고 `check-backup-coverage`의 `EXCLUDE`에 넣으면 **안 된다.** 그 칸은 파생 캐시(`syncQueue`·`localFxRates`)의 자리다. 영상 바이트는 *"잃으면 기억이 사라지는가"*에 **예**이므로, 「선택적 포함(사용자가 고른다) + 기본은 메타만」이 맞는 모양이다.

## 4. 게이트가 못 잡는 자리 (§7 세 번째 질문)

**`LocalMedia`에 `videoBlob?: Blob`을 붙이면 `check-backup-coverage`는 GREEN이다.** 게이트가 **테이블 단위**로 보기 때문이다(`check-backup-coverage.mjs:33-38`) — 필드가 늘어도 테이블 목록은 그대로다. 그러면 영상이 **조용히 백업에서 빠진다.**

> 그래서 영상을 한다면 **`localVideos` 별도 테이블**이 안전하다. 게이트가 자동으로 걸린다.
> 필드로 붙일 거라면 게이트를 **필드 단위로 넓히고**, §11 ①에 따라 **주입 검증을 다시** 해야 한다.

같은 이유로 `SyncMeta`를 상속시키면 좀비 차단·LWW가 **자동 승계**된다(`merge.ts:20-50`은 `SyncMeta`만 참조) — §7 2층의 좋은 예다.

## 5. 권고

### 5-1. 지금 당장 (영상 기능 아님 — 결함 제거)

`accept='image/*'`는 **힌트일 뿐 강제가 아니다**(`tripDetail.ts:498`·`:763`). 사용자가 영상을 섞어 고르면 `media.ts:130`이 던져 **배치 전체가 실패**할 수 있다.

→ 인테이크 첫 관문에서 종류를 갈라 **「영상은 아직 지원하지 않아요 — 사진만 저장했어요(영상 2개 제외)」**처럼 **제외 사실과 건수를 말한다.** 조용한 실패보다 낫다(§12).

### 5-2. 그다음 — 오디오 노트 (SPEC이 이미 MVP로 지정, 미구현)

| | 오디오 노트 | 영상 |
|---|---|---|
| 회수 채널 | 소리 · 말 | 소리 · 말 · 움직임 |
| 파일 크기 | 수십~수백 KB | 수십~수백 MB |
| 트랜스코딩 | 불필요(`MediaRecorder`) | 수단 없음 |
| 격자 영향 | 없음(칩 줄에 `🔊 0:14`) | 격자 재설계 |
| CSP | `media-src` 필요(영상과 동일) | 동일 |

**영상 가치의 2/3를 두 자릿수 배 낮은 비용으로 얻는다.** 오디오를 내고 실사용을 관측한 뒤 영상을 판단하면, 그때는 훨씬 튼튼한 근거 위에서 논의할 수 있다. 거의 안 쓴다면 영상의 근거도 함께 무너진다.

### 5-3. 영상을 한다면 — A안 → B안 순서, C안은 선행 조건 충족 후

**B안 착수 시 필수 게이트(하나라도 빠지면 착수 금지):**

- 하드 상한: **길이 ≤ 60초 AND 크기 ≤ 100MB** — 초과 시 **명시적 거부**(침묵 절삭 금지, `MEDIA_PIPELINE.md:44`)
- 인테이크 **전** `navigator.storage.estimate()` 사전점검 + 분할 수용
- 지표 분리: 「사진」/「영상」 별도(`storage.ts:40`·`dataManager.ts:38`)
- **CSP에 `media-src 'self' blob:` 추가 + `check-csp.mjs` REQUIRED 동시 갱신**
- 백업 제외를 **이유와 함께 코드에 기록**(§7 — 안 적으면 다음 사람이 "고친다")
- 포스터 프레임은 **픽셀 read-back으로 검증**(검은 프레임이 조용히 통과하는 부류)
- 「이 영상은 이 기기에만 있습니다」를 **화면에 명시**(§12)

**C안 선행 조건 4개** — 이 넷 없이 켜면 §1-D 함정이 첫날 데이터를 삼킨다:

1. quota preflight + `quota_blocked` 분할 수용
2. `classifyError`에 **「서명 만료」 제3 결과** + `attempts` 기반 백오프 (지금은 `retryable|permanent` 둘뿐이라 403이 "권한 없음"과 "서명 만료" 양쪽에 쓰인다)
3. 멀티파트 create/part/complete op + **세션 id를 데이터로 기억**(§1-C의 일반형)
4. ZIP64 또는 "영상은 ZIP 밖 개별 파일" 형식

### 5-4. 영구 제외 (범위 경계)

> **"영상을 보관하고 다시 보는 것"까지가 이 앱이다. "영상을 만드는 것"은 이 앱이 아니다.**

|---|---|---|
| 영상 편집(트림 외)·필터·자막 | 영구 제외 | 만드는 도구다. OS 앱이 더 잘한다 |

### 5-5. UI 방향 (승인 시)

- **격자에 `<video>`를 넣지 않는다.** 영상은 "재생시간 숫자가 붙은 사진"이다. 이 한 줄이 자동재생·무음·발열·데이터·모션 접근성을 동시에 해결한다.
- 썸네일은 **첫 프레임이 아니라 중간 프레임**(첫 프레임은 흔들리거나 검다).
- 배지는 **`0:12` 하나만.** 재생 삼각형 오버레이는 반려 — 같은 사실을 두 장식으로 말하는 중복이고, 사진 위에 반투명 덩어리를 얹는다.
- 뷰어는 **`photoViewer`에 통합**하되 영상은 **사진 기능의 부분집합**(확대·회전·편집 비활성) + 하단 전용 스크럽 트랙. 상위집합이 아니다 — 그래야 제스처 어휘가 하나로 유지된다.
- 🔴 `close()`에 **오디오 정지**가 없으면 「닫아도 소리가 남는다」. 세 경로(✕·Esc·배경 탭)가 전부 같은 `close()`를 지나므로 **한 곳에만** 구현한다(§7 2층).

## 6. 정직한 경계 (비타협 원칙 #4)

**측정하지 않은 것 — "확인 불가"로 남긴다:**

- **영상 비트레이트·파일 크기**: 「1분 1080p ≈ 60~130MB」는 일반 지식이고 **이 저장소에서 측정한 값이 아니다.** 크기 상한(§5-3)을 정하려면 사용자 기기 실측이 먼저다.
- **R2 Class A/B 월 무료 요청 수**: 저장소 어디에도 없다. 숫자를 적으면 그건 기억이지 이 저장소의 사실이 아니다. → Cloudflare 문서 확인 후 `STORAGE_R2_PROPOSAL.md`에 SSOT로 넣는 것이 후속 작업.
- **MP4 `moov` 박스의 실제 위치**: 카메라가 스트리밍으로 쓰면 파일 **끝**에 온다. 실기기 파일을 슬라이스해 헥스로 보기 전엔 파싱 전략을 "된다"고 말할 수 없다.
- **`drawImage(video)`가 `tkhd` 회전 matrix를 반영하는지**: 브라우저별 실측 필요. 안 하면 v0.23(세로 사진 눕혀 표시)과 **동형 결함**이 재발한다.
- **브라우저별 IndexedDB 할당량·persist 승인률**: 실기기 `estimate()` 스냅샷이 유일한 근거원(§9 4단계).
- **동일 Blob을 3개 필드에 넣을 때 디스크 점유가 1부인지 3부인지**: 확인 불가.

**이 문서가 하지 않은 것**: 코드 변경 0건 · SQL 실행 0건 · 라이브 렌더 미실행 · 실서버 advisor 미조회. 위 판정은 전부 **저장소 파일을 읽어** 내린 것이다.
