# DISASTER_RECOVERY · Bugeon Journey

> 비상 상황에서 **사용자의 기억(여행·순간·사진·비용)을 어떻게 되살리는가**의 단일 절차서.
> 비타협 원칙 #1(기억을 잃지 않는다)과 #5(복구 가능성 우선)의 운영 매뉴얼이다.
> 계약의 상세는 `SYNC_PROTOCOL.md`(병합 규율)·`MEDIA_PIPELINE.md`(사진 계층)·`ARCHITECTURE.md`(포트)에 있고, 이 문서는 **"무엇이 죽었을 때 무엇으로 되살리나"**의 우선순위 지도다.

---

## 1. 데이터가 사는 3개 계층 (무엇이 어디에)

| 계층 | 무엇이 있나 | 소유·통제 | 죽는 사건 |
| --- | --- | --- | --- |
| **① 로컬(IndexedDB/Dexie)** | 전 데이터의 진실 사본 — 여행·순간·**원본 사진**·표시본·썸네일·비용 | 사용자 기기(앱이 통제) | 브라우저 축출·사이트데이터 삭제·기기 분실 (앱 통제 밖) |
| **② 클라우드(Supabase)** | 메타(여행·순간·비용) + **표시본 사진**(Storage journey-media) — 원본·GPS는 없음 | 서버(소유자 RLS) | 프로젝트 중단·과금 정지·리전 장애·계정 상실 |
| **③ 백업 파일(JSON 또는 ZIP)** | export 시점의 전 테이블 스냅샷 + 사진(자족). **단일 JSON**(사진 base64 내장) 또는 **여행별 폴더 ZIP**(사진을 실제 이미지 파일로) | 사용자가 보관(파일) | 사용자가 파일을 잃음 |

**핵심 성질(왜 우리가 튼튼한가)**:
- **원본 사진은 ①에만 있다** — 외부 호스트(예: Cloudinary) 의존이 없어 "외부 URL이 깨져 사진이 통째로 날아가는" 약한 고리가 구조적으로 없다(절약 모드·§0).
- **②는 교체 가능한 부품이다** — 포트(TripsRemote/MomentsRemote/MediaRemote/ExpensesRemote)로 격리되어, Supabase가 사라져도 ①은 독립적으로 살아 있고 다른 백엔드로 갈아끼울 수 있다.
- **③은 자족적이다** — 사진을 파일 안에 품어(JSON=base64 내장, ZIP=실제 이미지 파일) 깨진 링크가 없다. 어떤 기기에서든 완전 복원. **두 형식은 공통 코어(`exportCollectRows`/`importMergeRows`)를 공유**하므로 완전성·병합 안전성이 동일하고, `check-backup-coverage` 게이트가 형식과 무관하게 전 테이블 커버를 강제한다. ZIP은 여행별 폴더로 나뉘어 파일 탐색기에서 바로 보기·**개별 여행 복원**이 되고, 고아 행은 `_orphans/`로 유실 없이 담긴다.

## 2. 복구 우선순위 (무엇이 죽었나 → 무엇으로 되살리나)

> 규칙: **복원은 "교체"가 아니라 "병합"**이다. 모든 경로는 `mergeDecision`(version 기반 tombstone 우위 + 빈-데이터 가드)만 거친다. 어떤 경로도 로컬을 통째로 덮어쓰지 않는다(좀비·유실 동시 차단).

### 시나리오 A — 기기 하나가 죽음(②는 살아 있음) · **가장 흔함**
- **되살리는 곳**: ② 클라우드.
- **절차**: 새 기기에서 로그인 → `runSync` pull → 여행·순간·비용 메타 + 표시본 사진 복원.
- **한계(정직)**: **원본 사진은 ②에 없다** — 새 기기엔 표시본만 온다(소비 기기는 `originalBlob=표시본 폴백`). 원본이 필요하면 **원본이 있던 기기의 ③ 백업**이 유일한 원천. → *권고: 원본 보존이 중요하면 주기적 JSON 백업(사진 포함)을 별도 매체에 보관.*

### 시나리오 B — 클라우드가 죽음(기기 ①은 살아 있음)
- **되살리는 곳**: 아무것도 할 필요 없음 — ①이 진실 사본이다. 앱은 오프라인 우선이라 **정상 동작**한다.
- **절차**: 즉시 ③ JSON 백업을 받아 안전하게 보관(기기까지 잃는 이중 사고 대비). 서버 복구/교체 후 `runSync` push로 재상승.
- **주의**: 빈-클라우드 가드가 "서버가 빈 배열을 줘도 로컬을 지우지 않음"을 보장 → 죽은/빈 서버가 로컬 기억을 지우지 못한다.

### 시나리오 C — 기기와 클라우드가 동시에 죽음
- **되살리는 곳**: ③ JSON 백업.
- **절차**: 아무 기기에서 앱 설치 → 데이터 관리 → 복원(import) → 사진 포함 전 데이터 병합 복원.
- **전제**: 사용자가 ③을 갖고 있어야 한다. → *이 문서의 유일한 사용자 행동 의존점. 앱은 백업 유도를 UI에 상시 노출.*

### 시나리오 D — 셋 다 없음(최악)
- **부분 재건**: 저장소만 살아 있다면 `supabase/migrations/*`로 **스키마는** 재건 가능(빈 껍데기). 하지만 **사용자 기억(행 데이터)은 ①②③ 중 하나 없이는 복원 불가.**
- **교훈**: 그래서 ③(주기 백업)이 마지막 방어선이다. 이 문서의 모든 권고가 "③을 만들고 지켜라"로 수렴한다.

## 3. 기계적 보증 (사람이 잊어도 지켜지는 것)

복구 절차가 "문서 속 약속"에 그치지 않도록 CI 게이트로 강제한다(`scripts/harness.mjs`):

- **check-backup-coverage** — 모든 사용자 데이터 Dexie 테이블(localTrips·localMoments·localMedia·localExpenses)이 `exportBackup`·`importBackup` **양쪽**에서 참조되는지 저장소만으로 대조. 새 테이블을 추가하고 백업 반영을 잊으면 **빌드가 즉시 RED**. (파생 큐 `syncQueue`만 명시 제외.) → *시나리오 C·D의 최후 방어선인 ③이 "새 데이터를 빠뜨리지 않음"을 기계적으로 보장.*
- **check-schema-parity** — 클라 rowmap 필드 ⊆ 서버 마이그레이션 컬럼. ②로의 push가 조용히 깨지지 않게(드리프트 차단).
- **merge 유닛(version 기반 tombstone 우위)** — 오래된 ③ 백업을 복원해도 삭제한 데이터가 되살아나지 않음(좀비 차단). 서버측도 `prevent_zombie_resurrection` 트리거로 동일 규칙.
- **복원 왕복 드릴(`tests/unit/backupRoundtrip`)** — "백업이 쓴 것 == 복원이 읽는 것"을 매 빌드에서 검증한다. JSON·ZIP 두 형식 모두 export→import 후 전 행·사진 바이트·tombstone·고아·좌표가 그대로인지 대조(비공허 포함). 복원이 "가정"이 아니라 "검증"이 됨(DR 기준 #7).
- **백업 암호화(`services/backupCrypto`)** — 선택적 암호구절로 백업 전체를 AES-GCM-256 봉투(PBKDF2 210k)로 감쌀 수 있다. 키는 저장하지 않으며(사용자만 보유·분실 시 복원 불가), 파일이 새어도 암호 없이는 평문을 얻지 못한다(DR 기준 #5).
- **DR 감사관(`.claude/agents/disaster-recovery-guardian`)** — 백업/복원/스키마 변경 전·정기 감사를 읽기전용으로 수행(문서만 보고 PASS 금지). 우리의 "정직한 완료" 규율과 동일 결.

게이트들은 **비공허 자체검사**를 내장한다(가짜 결함 주입 시 RED 확인) — 셀렉터 불일치로 조용히 통과하지 않는다.

## 4. 알려진 갭 (정직한 미완)

- **원본 사진의 클라우드 사본 없음**: 설계된 절충(절약 모드·§0). 원본은 ①과 ③에만 산다. 다기기에서 원본까지 필요하면 ③ 백업이 유일 원천 — 이건 버그가 아니라 계약이며, 사용자에게 백업을 권고하는 것으로 완화한다.
- ~~**Storage 고아 스윕 미구현**~~ → **해결(v0.37)**: 사진 tombstone 시 소유 기기가 표시본 Storage 객체를 최선노력으로 정리한다(`pushPendingMedia` + 마이그 0010 소유자 폴더격리 DELETE 정책, DEL-CONTRACT 이행). 유실 위험 0(tombstone은 이미 durable, 실패 시 잉여만 남음). *잔여*: 이 기능 이전에 삭제된 옛 고아 객체의 일괄 스윕은 후속.
- **외부 타임스탬프(TSA) 미도입**: 연구노트 해시체인은 앱 내 무결성만 보장(외부 시각 증명은 별도 논의).
- **③ 백업은 사용자 행동 의존**(설계상 경계): 자동 원격 백업·오프사이트 미러는 범위 밖(비공개 기본·§3) — DR 감사관 기준 ②③(무장된 스케줄·신선도)는 우리 앱에선 **"백업의 주인 = 최종 사용자"**라 일부러 자동화하지 않는다. 앱은 유도·암호화·완전성 보증까지 하고, 파일을 실제로 만들고 지키는 것은 사용자 책임이다. 백업 암호화(v0.37)로 개인정보 노출 위험은 완화됐다.

---

## 5. 한 줄 요약

> **①(로컬)이 진실, ②(클라우드)는 교체 가능한 다기기 동기화 부품, ③(JSON 백업)이 최후의 방어선.**
> 원본 사진은 ①③에만 살아 있으므로, **주기적 사진 포함 백업(③)이 유일하게 사용자가 해야 할 일**이다. 나머지는 게이트와 병합 규율이 지킨다.
