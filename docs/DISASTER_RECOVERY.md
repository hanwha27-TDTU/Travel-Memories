# DISASTER_RECOVERY · Bugeon Journey

> 비상 상황에서 **사용자의 기억(여행·순간·사진·비용·장소·소리·영상)을 어떻게 되살리는가**의 단일 절차서.
> 비타협 원칙 #1(기억을 잃지 않는다)과 #5(복구 가능성 우선)의 운영 매뉴얼이다.
> 계약의 상세는 `SYNC_PROTOCOL.md`(병합 규율)·`MEDIA_PIPELINE.md`(사진 계층)·`ARCHITECTURE.md`(포트)에 있고, 이 문서는 **"무엇이 죽었을 때 무엇으로 되살리나"**의 우선순위 지도다.

## 1. 데이터가 사는 3개 계층 (무엇이 어디에)

| 계층 | 무엇이 있나 | 소유·통제 | 죽는 사건 |
| --- | --- | --- | --- |
| **① 로컬(IndexedDB/Dexie)** | 전 데이터의 진실 사본 — 여행·순간·사진·비용·장소·소리·영상. 외부 원본과 검증 후 회수된 임시 원본은 앱이 다시 만들 수 없음 | 사용자 기기(앱이 통제) | 브라우저 축출·사이트데이터 삭제·기기 분실 (앱 통제 밖) |
| **② 클라우드(Supabase + R2)** | 7개 도메인 메타 + 사진 표시본·소리·영상 파생본/포스터 바이트. 외부 원본 사진·영상은 없음 | 서버(소유자 RLS) | 프로젝트 중단·과금 정지·리전 장애·계정 상실 |
| **③ 백업 파일(기본 ZIP, 호환 JSON/암호화 봉투)** | export 시점의 7개 사용자 도메인·tombstone + 앱이 보유한 사진·소리·영상 본문/포스터. 기본 이름 `YYYYMMDD_HHMM_Bugeon-Journey.zip` | 사용자가 고른 파일 위치 | 사용자가 파일을 잃음 |

**핵심 성질(왜 우리가 튼튼한가)**:
- **외부 원본은 앱이 통제하지 않는다** — 사진·영상은 앱이 실제 보유하는 파생본과 아직 회수하지 않은 임시 원본까지만 ①③에 담을 수 있다. 앱이 검증 후 정리했거나 사용자가 외부에서 지운 원본은 백업이 새로 만들 수 없다.
- **②는 교체 가능한 부품이다** — 포트(TripsRemote/MomentsRemote/MediaRemote/ExpensesRemote)로 격리되어, Supabase가 사라져도 ①은 독립적으로 살아 있고 다른 백엔드로 갈아끼울 수 있다.
- **③은 앱 보유분 기준 자족적이다** — 사진·소리·영상 바이트를 파일 안에 품어(JSON=base64, ZIP=실제 파일) 외부 URL에 기대지 않는다. **두 형식은 공통 코어(`exportCollectRows`/`importMergeRows`)를 공유**하므로 완전성·병합 안전성이 동일하고, `check-backup-coverage`가 전 테이블 커버를 강제한다. ZIP은 여행별 폴더와 `_orphans/`를 가지며 참조된 바이트 하나라도 빠지면 손상으로 거절한다.
- **저장 완료는 되읽기로 판정한다** — Android 셸의 기본 백업은 MediaStore `Download/Bugeon Journey`에 직접 저장하고, 사용자가 다른 폴더를 명시한 경우에만 SAF 시스템 저장 창을 연다. 두 경로 모두 URI에 청크 쓰기 후 길이+SHA-256을 다시 읽는다. 지원 브라우저도 저장 파일을 다시 비교한다. anchor fallback은 보통 Download 폴더로 다운로드를 요청할 뿐이라 앱은 완료로 기록하지 않는다.
- **ZIP 구조도 정확집합으로 판정한다** — CRC와 중앙/로컬 헤더, 중복 경로, manifest가 선언한 여행 bundle·`places.json`·현재 형식의 도메인 목록을 모두 대조한다. 이 기기에 이미 실물 바이트가 없는 행은 메타만 담긴 개수를 경고하고 완전백업 신선도로 기록하지 않는다.

## 2. 복구 우선순위 (무엇이 죽었나 → 무엇으로 되살리나)

> 규칙: **복원은 "교체"가 아니라 "병합"**이다. 모든 경로는 `mergeDecision`(version 기반 tombstone 우위 + 빈-데이터 가드)만 거친다. 어떤 경로도 로컬을 통째로 덮어쓰지 않는다(좀비·유실 동시 차단).

### 시나리오 A — 기기 하나가 죽음(②는 살아 있음) · **가장 흔함**
- **되살리는 곳**: ② 클라우드.
- **절차**: 새 기기에서 로그인 → `runSync` pull → 여행·순간·비용 메타 + 표시본 사진 복원.
- **한계(정직)**: 외부 원본 사진·영상은 ②에 없다. 원본이 필요하면 앱이 아직 임시 원본을 가진 기기에서 **임시 원본 포함 ZIP**을 만들거나 외부 원본을 별도 보관해야 한다.

### 시나리오 B — 클라우드가 죽음(기기 ①은 살아 있음)
- **되살리는 곳**: 아무것도 할 필요 없음 — ①이 진실 사본이다. 앱은 오프라인 우선이라 **정상 동작**한다.
- **절차**: 즉시 ③ 전체 ZIP 백업을 받아 안전하게 보관(기기까지 잃는 이중 사고 대비). 서버 복구/교체 후 `runSync` push로 재상승.
- **주의**: 빈-클라우드 가드가 "서버가 빈 배열을 줘도 로컬을 지우지 않음"을 보장 → 죽은/빈 서버가 로컬 기억을 지우지 못한다.

### 시나리오 C — 기기와 클라우드가 동시에 죽음
- **되살리는 곳**: ③ 전체 ZIP 백업(옛 JSON도 호환 복원).
- **절차**: 아무 기기에서 앱 설치 → 데이터 관리 → 복원(import) → 사진 포함 전 데이터 병합 복원.
- **전제**: 사용자가 ③을 갖고 있어야 한다. → *이 문서의 유일한 사용자 행동 의존점. 앱은 백업 유도를 UI에 상시 노출.*

### 🔴 시나리오 B·D 공통 — **새 Supabase 프로젝트로 재건할 때 초대목록부터 확인한다**(T-033 · ADR-0073)

`supabase/migrations/0002_journey_invite_only.sql`은 소유자 이메일을 **문자열로 시드**한다
(`hanwha27@gmail.com`). 지금 운영 프로젝트에서 그 줄은 **이미 돌았고 영원히 무해하다**
(`on conflict do nothing` · 실측 2026-07-23 시드 · 현재 1행). 그러나 **새 프로젝트에 migration을
처음부터 다시 적용하는 복구**에서는 그 값이 실제 접근 권한을 정한다.

- **소유자 계정이 그대로면**: 아무것도 안 해도 된다. 시드가 곧 정답이다 — 이게 값을
  환경변수로 빼지 않은 이유이기도 하다(변수가 비면 **아무도 초대되지 않은 채 조용히** 선다).
- 🔴 **소유자 계정이 바뀌었다면**: 재건 직후 `journey.allowed_users`에 **새 이메일을 먼저 넣는다.**
  안 넣으면 로그인은 되는데 **자기 행조차 한 건도 안 보인다** — RLS는 조용히 0건을 주지,
  「당신은 초대되지 않았습니다」라고 말해 주지 않는다.
  ```sql
  insert into journey.allowed_users (email, note) values ('새이메일@example.com', 'owner')
    on conflict (email) do nothing;
  select email from journey.allowed_users;   -- 🔴 되읽어 확인한다(성공 응답은 완료가 아니다)
  ```
- **복원(import) 전에 한다.** 초대 없이 복원하면 로컬로는 들어가지만 서버로 한 행도 못 올라가고,
  그 실패가 동기화 대기열에 쌓인 채로 원인을 찾게 된다.
- **앱은 이 상태를 「거절」로 단정하지 않는다**: 못 물어봤을 때는 세션을 유지하고 기록을 계속
  쓸 수 있게 둔다(`accessVerdict()` · `SECURITY.md`). 그래서 **로컬 기억은 이 사고로 잃지 않는다.**

### 시나리오 D — 셋 다 없음(최악)
- **부분 재건**: 저장소만 살아 있다면 `supabase/migrations/*`로 **스키마는** 재건 가능(빈 껍데기). 하지만 **사용자 기억(행 데이터)은 ①②③ 중 하나 없이는 복원 불가.**
- **교훈**: 그래서 ③(주기 백업)이 마지막 방어선이다. 이 문서의 모든 권고가 "③을 만들고 지켜라"로 수렴한다.

## 3. 기계적 보증 (사람이 잊어도 지켜지는 것)

복구 절차가 "문서 속 약속"에 그치지 않도록 CI 게이트로 강제한다(`scripts/harness.mjs`):

- **check-backup-coverage** — 모든 사용자 데이터 Dexie 테이블(**7개**: localTrips·localMoments·localMedia·localExpenses·localAudio·localPlaces·**localVideos**)이 export/import **양쪽**에서 참조되는지 대조한다. 새 테이블을 추가하고 백업 반영을 잊으면 빌드가 RED다. 제외는 재취득 가능한 파생·상태뿐이며 근거가 필요하다. 필드 누락은 비공허 왕복 픽스처가 보완한다.
- **check-schema-parity** — 클라 rowmap 필드 ⊆ 서버 마이그레이션 컬럼. ②로의 push가 조용히 깨지지 않게(드리프트 차단).
- **merge 유닛(version 기반 tombstone 우위)** — 오래된 ③ 백업을 복원해도 삭제한 데이터가 되살아나지 않음(좀비 차단). 서버측도 `prevent_zombie_resurrection` 트리거로 동일 규칙.
- **복원 왕복 드릴(`tests/unit/backupRoundtrip`)** — JSON·ZIP 모두 전 행과 사진·소리·영상 본문/포스터 바이트, tombstone·고아·좌표를 비공허하게 대조한다. ZIP에서 참조 파일을 하나 제거하면 반드시 RED다.
- **실제 파일 왕복(`tests/unit/backupFileRoundTrip` + 진단)** — 고유 trip·moment·video ZIP을 실제 파일 선택 경계로 되받아 전체 파일 해시와 영상 본문·포스터 해시를 검사하고 production 병합→Dexie read-back→의도적 abort를 지난다. 시험 뒤 entity·queue·purged 잔재는 0건이어야 한다.
- **운영 영상 서버 왕복(진단 「영상 서버 왕복」)** — 사용자 파일이 아닌 합성 WebM을 고유 trip·moment·video로 원자 저장해 운영 DB와 R2 영상/포스터 SHA-256·재생, 다른 기기식 pull, tombstone 바이트 보존, restore, permanent delete의 행 부재+원장 존재+두 객체 404, exact cleanup까지 확인한다. canonical 세대가 바뀌면 통과하지 않고 추가 자동 쓰기를 멈춘다.
- **백업 암호화(`services/backupCrypto`)** — 선택적 암호구절로 백업 전체를 AES-GCM-256 봉투(PBKDF2 210k)로 감쌀 수 있다. 키는 저장하지 않으며(사용자만 보유·분실 시 복원 불가), 파일이 새어도 암호 없이는 평문을 얻지 못한다(DR 기준 #5).
- **복원 입력 경계** — 일반 브라우저는 1GiB, Android 앱은 최대 32MiB를 선택 파일의 `arrayBuffer()`를 만들기 전에 거절한다. Android renderer/native 메모리 값은 32MiB를 올리지 않고 더 낮추는 데만 쓴다(ADR-0068). JSON·ZIP manifest의 `backupVersion`이 현재 판보다 새로우면 앱 업데이트를 요구하고, 여섯 사용자 도메인의 각 행은 `id·createdAt·updatedAt·version·deletedAt` 공통 메타를 검증한 뒤에만 Dexie 병합으로 간다. 옛 v1 백업의 `audio·places` 누락은 빈 배열로 하위호환한다.
- **DR 감사관(`.claude/agents/disaster-recovery-guardian`)** — 백업/복원/스키마 변경 전·정기 감사를 읽기전용으로 수행(문서만 보고 PASS 금지). 우리의 "정직한 완료" 규율과 동일 결. **최근 실행 결과: HOLD** — 커버리지·독립성·외부바이너리·정직한 경계는 통과, 남은 HOLD 근거는 "실제 사용자 백업의 존재·신선도는 저장소 밖 사실이라 소유자 확인 필요"(설계상 경계). 교정 반영: 아래 신선도 관측화·평문 경고·실기기 복원 드릴.
- **실기기 복원 드릴(`tests/unit/restoreDrill`)** — `importMergeRows`를 실제 Dexie(fake-indexeddb)로 구워 db 접근층까지 검증(저장·되읽기·blob 바이트 왕복·빈가드·LWW·tombstone 우위). 순수 직렬화 드릴에 더해 "실 DB에도 그대로 되살아남"을 증명.
- **백업 신선도 관측화(`services/backupMeta`)** — 데이터 관리에 "마지막 백업: N일 전"을 표시하고 오래됨/없음을 부드럽게 권고. 신선도가 "가정"이 아니라 "관측 가능"이 됨(감사관 #3 근거 완화).
- **평문 경고** — 암호 없이 내보낼 때 "이 파일은 암호화되지 않음(사진·GPS·메모 평문)"을 한 번 확인(감사관 교정 — 기본 평문 PII 노출 축소).

게이트들은 **비공허 자체검사**를 내장한다(가짜 결함 주입 시 RED 확인) — 셀렉터 불일치로 조용히 통과하지 않는다.

## 4. 알려진 갭 (정직한 미완)

- **원본 사진의 클라우드 사본 없음**: 설계된 절충(절약 모드·§0). 원본은 ①과 ③에만 산다. 다기기에서 원본까지 필요하면 ③ 백업이 유일 원천 — 이건 버그가 아니라 계약이며, 사용자에게 백업을 권고하는 것으로 완화한다.
- ~~**Storage 고아 스윕 미구현**~~ → **해결(v0.37)**: 사진 tombstone 시 소유 기기가 표시본 Storage 객체를 최선노력으로 정리한다(`pushPendingMedia` + 마이그 0010 소유자 폴더격리 DELETE 정책, DEL-CONTRACT 이행). 유실 위험 0(tombstone은 이미 durable, 실패 시 잉여만 남음). *잔여*: 이 기능 이전에 삭제된 옛 고아 객체의 일괄 스윕은 후속.
- **외부 타임스탬프(TSA) 미도입**: 연구노트 해시체인은 앱 내 무결성만 보장(외부 시각 증명은 별도 논의).
- **③ 백업은 사용자 행동 의존**(설계상 경계): 자동 원격 백업·오프사이트 미러는 범위 밖(비공개 기본·§3) — DR 감사관 기준 ②③(무장된 스케줄·신선도)는 우리 앱에선 **"백업의 주인 = 최종 사용자"**라 일부러 자동화하지 않는다. 앱은 유도·암호화·완전성 보증까지 하고, 파일을 실제로 만들고 지키는 것은 사용자 책임이다. 백업 암호화(v0.37)로 개인정보 노출 위험은 완화됐다.

## 5. 한 줄 요약

> **①(로컬)이 진실, ②(클라우드)는 교체 가능한 다기기 동기화 부품, ③(전체 ZIP 백업)이 최후의 방어선.**
> 주기적으로 암호화된 전체 ZIP을 사용자가 고른 별도 위치에 보관한다. 외부 원본 사진·영상은 앱 백업과 별도로 지킨다.
