**Phase 9k(2026-07-26)**: **이관 완주 + 옛 저장소 경로 제거**(v0.85·v0.86). **경과**: 사용자가 실기기에서 [옛 저장소 사진 옮기기]를 눌렀고 화면이 `8장 옮김.`이라고만 말했다 — **그 순간 도구의 정직성 구멍이 드러났다**(M-0022): `migrateMediaBytes`는 설계대로 되읽어 확인하고 `safeToRemove`에 담아 반환까지 했는데 **`describeMigration`이 그 필드를 안 읽었다.** 검증을 *수행*하는 것과 결과를 *보여주는* 것을 별개로 취급했고 뒤엣것을 빠뜨렸다. 사용자는 **되돌릴 수 없는 [옛 파일 정리]를 누를 근거를 화면에서 볼 수 없는 상태**였다. 근본형: *"확인했으니 됐다"* — 확인의 목적은 내가 아는 것이 아니라 **사용자가 결정할 수 있게 하는 것**이다. **유닛 15건이 왜 못 잡았나**: 전부 `MigrateReport`의 숫자를 검사했고 숫자는 다 맞았다. **화면에 무엇이 나가는지 검사한 것이 하나도 없었다** — 검사의 시선이 사용자가 아니라 자료구조에 있었다. v0.85에서 확인 수를 반드시 말하게 고치고(전부/일부/없음 경고), 같은 화면에서 드러난 2건도 함께 고쳤다(「옛 저장소에 남은 사진」이 개수만 세어 *아직 안 옮김*과 *옮겼는데 원본이 남음*을 구분 못 하던 것 / 판정은 사진을 가리키는데 밑 설명은 기기 얘기이던 것). **완주**: 사용자가 v0.85로 재실행 → `8장은 이미 옮겨져 있었어요. 새 저장소에서 8장 모두 확인했어요.` → [옮긴 뒤 옛 파일 정리] → `옛 파일 8개 정리`. **서버 실측으로 확정**: 옛 저장소 객체 **0개**, 그런데 화면의 「사진 파일」은 **여전히 10개** → **R2에 10장이 다 있다**(활성 사진 10장과 정확히 일치). 이것이 R2 목록·업로드·삭제 전 경로의 실동작 증명이다. **v0.86 — 경로 제거**: `mediaRemote`의 Supabase 바이트 분기, `mediaStoreKind()`/`VITE_MEDIA_STORE`(코드·워크플로 양쪽), `supabaseBlobStore`·`supabaseMediaIds`·`MEDIA_BUCKET`, `mediaMigrate.ts`와 그 테스트, 진단의 이관 지표·버튼을 모두 제거. **판단 근거**: 바이트가 R2에만 남는 순간 `VITE_MEDIA_STORE` 되돌리기는 **이미 죽은** 탈출구다 — 살아 있지도 않은 탈출구를 남겨두면 다음 사람을 속인다. 스테일 빌드가 옛 버킷에 쓰는 가상 위험은 **「파일이 없는 사진 기록」 지표가 그 *결과*를 이미 잡으므로** 탐지를 잃지 않는다. **검증**: harness 18게이트 · 유닛 335 · verify-editor-live 95/95 · build 그린. **남은 것**: Supabase `journey-media` 버킷은 **비어 있지만 아직 존재한다** — 사용자가 콘솔에서 지우면 구조적으로 쓰기가 불가능해진다(권장, 사용자 결정 대기). v0.86.

**Phase 9j(2026-07-26)**: **저장소 이관 도구** — "옮긴다"는 연산은 없다(v0.84). **제안(사용자)**: *"어차피 앞으로는 supabase에 사진을 저장하지 않을 거니까 일단 내가 직접 다 삭제하고 supabase 이미지 저장 경로를 아예 제거해버리면 어떨까?"* 방향은 옳았다. **그런데 확인해 보니 살아 있는 사진 10장 중 8장의 서버 사본이 옛 저장소에만 있었다**(R2엔 2장뿐, 휴지통·고아 0). 먼저 지웠다면 그 8장의 서버 백업이 사라진다 — 원칙 #1과 정면 충돌이고, 「파일 없는 기록」이 3 → 11이 됐을 것이다. **그래서 순서를 뒤집었다**: 복사 → 되읽어 확인 → **확인된 것만** 삭제. **§9 2단계가 또 작동했다**: `sync-offline-dev`에 **저장소 이관 규칙이 아예 없었다**(바이트를 한 저장소에서 다른 저장소로 옮기는 상황을 헌장이 상정한 적이 없다) → §2-B를 먼저 신설하고 착수. **설계의 핵심**: ①업로드 200으로 원본을 지우지 않는다(200은 "받았다"이지 "있다"가 아니다) ②한 장씩 `복사→삭제`로 돌지 않는다 — 중간에 끊기면 **양쪽 어디에도 없는 사진**이 생긴다. 전부 복사한 뒤 새 저장소를 **다시 훑어** 실제로 있는 id만 삭제 대상으로 삼는다 ③한 장이 실패해도 멈추지 않고, **그 장의 원본은 살아남는다** ④멱등(사용자는 실패하면 다시 누른다) ⑤복사와 삭제를 **버튼 두 개**로 분리(영구삭제와 같은 2단계 규율). **구현**: `services/mediaMigrate.ts`(포트 뒤로 저장소 두 곳 격리 — 어느 백엔드인지 몰라도 된다) + `supabaseBlobStore()`(R2가 켜진 상태에서 **옛 저장소를 읽을 방법이 없었다** — 환경변수를 안 보는 어댑터를 따로 뒀다) + 진단에 지표 「옛 저장소에 남은 사진」(**'문제'가 아니라 '할 일'** — 사진은 멀쩡하고 옮기기만 하면 된다) + 액션 2종. **검증**: 유닛 15건, **비공허**: 업로드 직후 삭제하도록 주입 → 3건 RED / 확인 실패해도 지우도록 주입 → 1건 RED. harness **18게이트**(`check-skill-routing`이 새 파일의 라우팅 누락을 즉시 잡아 줌) · 유닛 350 · verify-editor-live 95/95 · build 그린. **다음**: 이관 완료(옛 저장소 0개) 확인 후에야 Supabase 경로 코드를 제거한다 — 바이트가 R2에만 남는 순간 `VITE_MEDIA_STORE` 되돌리기는 **이미 죽은** 탈출구이므로 그때는 없애는 게 맞다. v0.84.

**Phase 9i(2026-07-26)**: **사용자 실기기 화면이 critical 결함을 잡았다** — 새 테이블 GRANT 누락(v0.82 · M-0020). **경위**: 사용자와 단계별 확인을 시작해 1단계(진단 「저장 상태」 열기)를 요청했더니 화면이 `! 문제 · 확인하지 못했어요 / 영구삭제 원장 조회 실패:` — **콜론 뒤가 비어 있었다.** 빈 오류 메시지가 단서였다(PostgREST가 본문 없이 거절). **원인 두 겹**: ①마이그레이션 0012가 `journey.purged_ids`를 만들며 **`grant … to authenticated`를 빠뜨렸다**(형제 테이블 넷엔 전부 있었고 새 것 하나만 빠짐 — 최빈 결함군 그대로) ②**RLS와 GRANT를 같은 층으로 오인했다**(GRANT=이 역할이 테이블에 접근이나 하는가 / RLS=그중 어느 행인가). **실제 피해는 화면보다 크다**: `pushPurges`의 `ledgerAdd`가 같은 표에 쓰므로 **영구삭제가 서버에 반영되지 않았다** — v0.79의 핵심 기능이 배포된 채 죽어 있었다. **왜 내 "검증"이 통과했나(진짜 교훈)**: 0012 적용 뒤 트리거 실효를 확인하고 "라이브 DB에서 거부 0행"이라 보고했는데 그 SQL을 **superuser로** 돌렸다. superuser는 GRANT도 RLS도 우회한다 — **앱이 쓰는 역할이 아니다.** 헌장 §4에 `set_config('request.jwt.claims', …)`로 남이 되어 보라고 **이미 적혀 있었다.** 근본형: *"검증을 대상의 실제 실행 조건이 아니라 내가 편한 조건에서 했다."* 헤드리스가 모바일 `vh`를 재현 못 하던 것과 같은 형태인데, 그때는 한계를 알고 우회했고 **이번엔 한계를 인지조차 못 하고 성공을 통과로 읽었다.** **수정**: 마이그레이션 0013 — GRANT(select·insert만; **update·delete는 일부러 없다** — 원장을 고치거나 지우면 좀비 차단이 뚫린다) + 두 정책에 `is_allowed()` 결합(§2.2도 함께 빠져 있었다). **이번엔 제대로 검증**: `set local role authenticated` + **실제 허용 이메일**로 5종 — 소유자 6건 ✅ / 허용목록 밖 0건 ✅ / 남의 계정 0건 ✅ / 원장 기록 성공 ✅ / 위조 삽입 거부 ✅, 전부 `BEGIN…ROLLBACK`(원장 6건 그대로·흔적 0 확인). 그 과정에서 **오진도 한 번** 했다 — 가짜 이메일을 써서 `is_allowed()`가 정상 작동한 것을 결함으로 읽을 뻔했다(이메일은 `allowed_users`에서 읽어서 쓴다). **기계화**: `check-migration-grants`(**18번째 게이트**) — `create table journey.X`마다 GRANT와 `is_allowed()` 결합을 검사, 제외는 `NO_GRANT_REQUIRED`에 근거 필수. **비공허**: 0013의 GRANT 줄 제거 / `is_allowed()` 제거 → 둘 다 RED(**오늘 사용자가 실제로 겪은 상태의 재현**). 헌장 §3·§4·§5에 명문화. **정직**: v0.79~v0.81 사이에 영구삭제를 하셨다면 **서버에 반영되지 않았을 수 있다** — 다음 동기화에서 큐에 남아 있던 작업이 자동으로 재시도된다. v0.82.

**Phase 9h(2026-07-26)**: **앱이 서버 사진 파일을 스스로 판정한다**(v0.80 · M-0018). **지시(사용자)**: 커넥터를 켠 뒤 R2 객체 목록 도구가 없다는 걸 확인하고 *"그 목록 조회 기능 추가해주세요"*. **왜**: 지금까지 "R2에 고아 파일이 남았나"를 확인하는 유일한 방법이 **사용자가 Cloudflare 콘솔을 열어 캡처해 주는 것**이었다 — §8("진단 도구는 관측이 아니라 판정을 한다")에 정면으로 어긋난다. 앱이 스스로 말할 수 있는 일을 사람이 대신했다. **§9 2단계가 실제로 작동했다(M-0018)**: 코드를 쓰기 전 정독 중에 `supabase-security-dev` §2.7의 R2 4중벽이 **단건 연산(put/get/delete)만 상정해** 쓰여 있고 **목록 연산엔 규칙이 아예 없다**는 것을 발견했다. 단건은 키를 서버가 만들어 남의 폴더를 못 가리키지만 **목록은 prefix 하나로 버킷 전체가 열린다.** 규칙 없이 만들었다면 "클라이언트가 prefix를 보내면 편하겠네"가 자연스러운 구현이 됐을 것이다 — 오버레이 잘림 때 `vh`/`dvh` 규칙이 없었던 것과 **같은 근본형**(규칙을 그때 있던 사례의 모양대로 쓴다). 헌장에 §2.8을 먼저 신설한 뒤 착수했다. **구현**: `media-sign`에 `list` op — prefix는 **검증된 sub에서만**, 요청 본문의 prefix/delimiter/bucket은 **무시가 아니라 미파싱**(파싱해 두면 다음 사람이 쓴다), 목록 서명 URL은 **브라우저로 나가지 않는다**(함수가 호출하고 파싱된 결과만 준다 — 삭제와 같은 이유), 응답엔 전체 키 대신 **mediaId만**(폴더=uid를 다시 담지 않는다), 페이지 상한 10×1000에 걸리면 **`truncated`로 반드시 말한다**. `presign`을 버킷 단위(key='')로 일반화하고 `extraQuery`를 **서명에 포함**시켜 중간에서 prefix를 바꿔치기할 수 없게 했다. **판정층**: `auditMediaFiles()`(순수) — 두 방향을 **한 숫자로 합치지 않는다**: `orphans`(파일만 남음 — 용량만 먹음)와 `missing`(기록만 남음 — **다른 기기가 그 사진을 못 받는다**, 훨씬 무겁다). 목록이 잘렸으면 `missing`을 비우고 `unknown`으로 낸다(모르는 것을 문제로 반올림하지 않는다). **기계화**: `listPrefixIsServerBuilt` 게이트 신설(네 조항 정적 검사) — 본문 prefix 신뢰를 주입하니 2건 RED. **함께 고친 것**: 이 게이트의 성공 로그가 셀프테스트 수를 **`37`로 손으로 박아** 두고 있었다(4건을 추가해도 계속 37이라 말했다) — 게이트 자신이 "개수를 손으로 세지 않는다"를 어기고 있었다. 배열 길이에서 파생하도록 수정. 옛 유닛이 *"알 수 없는 op"*의 예시로 하필 `'list'`를 써서 RED가 난 것도 **검사가 옳게 잡아준 것**이다(`'exfiltrate'`로 교체). **배포**: `media-sign` v2 ACTIVE(verify_jwt 유지) — 12KB를 손으로 옮겼으므로 **`get_edge_function`으로 되읽어 대조**했다(코드 전부 동일, 차이는 의도적으로 추가한 불변식 #5 주석뿐 → 저장소도 같게 맞춤). **검증**: harness 17게이트 · 유닛 325(신규 21+2) · verify-editor-live 95/95 · build 그린. **정직**: **R2가 이 목록 서명을 실제로 받아들이는지는 이 환경에서 증명 불가**(샌드박스가 R2를 차단한다). 서명 정합은 검증 사다리 3번과 같은 성격이라 **실기기에서 진단 화면을 열어야 확정된다.** 토큰에 Object Read 권한이 없으면 `r2_list_failed`로 나온다. v0.80.

**Phase 9g(2026-07-26)**: **영구삭제가 서버 자료를 실제로 지운다**(v0.79 · ADR-0030 · M-0017). **지시(사용자)**: *"의도를 가지고 삭제하는건데 서버에 왜 살려두나요? 자료를..한 번 클릭으로 영구삭제는 막아야겠지만 2번 이상 클릭으로 삭제한거라면 영원히 복구가 안되도록 기록줄까지도 삭제시켜야 되는게 맞는거 아닌가요? … 오히려 서버에서 삭제가 안된게 더 큰 문제야."* **무엇이 틀렸었나**: ADR-0025와 0027이 서버 행 하드 삭제를 기각한 근거가 **글자 그대로 같았다** — *"사정 모르는 다른 기기가 사본을 다시 올려 좀비를 만든다."* 근거는 사실이었지만 **숨은 가정**("좀비를 막는 길은 행을 남기는 것뿐")을 두 번 다 검증하지 않았다. 서버가 재삽입을 **거부**하게 만들면 그 가정이 무너지고 자료를 살려둘 이유가 통째로 사라진다. 같은 결론에 두 번 도달한 것이 오히려 검증하지 않았다는 신호였다(M-0017 근본형: **결정의 근거를 재사용하며 그 전제를 다시 묻지 않는다**). **채택**: 마이그레이션 0012 — `journey.purged_ids` 원장(**id·소유자·시각만**, RLS는 select+insert만 두고 update/delete 정책을 **일부러 두지 않는다**) + 4개 테이블 **BEFORE INSERT 트리거**(원장에 있는 id는 조용히 거부 — 예외를 던지면 그 기기의 나머지 동기화까지 멈추는데 다른 기억은 죄가 없다) + 행은 **하드 삭제**, `purged_at` 컬럼(0011) 제거. 전파는 pull이 아니라 **원장**이 한다(`runSync` → `ledgerAll()` → `applyPurgedLedger()`) — 서버 행이 없으니 pull은 영구삭제를 볼 수 없다. 종류를 모르므로 네 테이블을 모두 훑고 표식은 `'unknown'`(거짓 종류를 지어내지 않는다). **§0 개정**: "하드 삭제 없음"에 예외를 명시 — 조항의 *목적*(좀비 차단)과 *수단*(행 유지)을 구분해 적지 않았던 것이 이 실수를 가능하게 했다. **순서가 곧 안전**: ①지우기 전에 묻는다(자식 id·사진 경로) ②**원장을 먼저 적는다** ③행을 지운다 ④되읽어 확인 ⑤바이트 삭제. **전환 중 하마터면 낸 2차 결함**: 컬럼을 DB에서 드롭했는데 `storeState.ts`가 여전히 `.is('purged_at', null)`로 조회 중이었다(배포됐으면 진단 화면이 400으로 죽는다) — 손으로 고른 목록이 아니라 **src 전체**를 훑는 게이트로 잡았다. **기계화**: 게이트 3종 신설 — `purgeOrderContract`(원장·경로 조회가 삭제보다 앞인가 + read-back 3종) · `runSyncAppliesLedger` · `noDroppedPurgedAtColumn`. **비공허 확인**: 원장을 삭제 뒤로 이동 / 옛 컬럼 조회 복원 / `runSync`에서 원장 적용 제거 — 셋 다 RED. **서버 실증**: 라이브 DB에서 트리거가 원장 id 재삽입을 실제로 거부(0행)하고 **원장에 없는 id는 정상 삽입**됨을 확인(검사 행은 즉시 정리). 정책 2종(INSERT·SELECT)·트리거 4개·옛 컬럼 0개. **함께 확인한 것(사용자의 두 번째 지적)**: "사진이 올라가는 건 오직 수동 업로드 때만" — **이미 그렇다.** 서버로 가는 것은 큐 op가 있을 때뿐이고 큐 op는 사용자 행동(`*LocalFirst`)으로만 생긴다. 유일한 구멍이던 "밀린 오프라인 편집을 가진 기기"를 이제 트리거가 물리적으로 막는다. **검증**: harness **17게이트** · 유닛 304 · verify-editor-live **95/95** · build 그린. **정직**: 마이그레이션은 라이브 DB에 적용했고 기존 데이터도 이관(원장 6건)했으나, **실제 2기기 전파(다른 기기에서 사라지는지)는 이 환경에서 재현 불가 — 사용자 확인이 필요하다.** v0.79.
