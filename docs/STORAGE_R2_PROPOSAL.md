# 기술변경 제안서 · 사진 바이트 저장소를 Cloudflare R2로 이관

> 상태: **제안(설계) — 승인 전. 코드·인프라 미착수.**
> 대상: 사진 **바이트**(표시본·썸네일)의 저장 위치. 메타데이터·인증·동기화 프로토콜은 **바꾸지 않는다**.
> 맥락: 메디컬 앱이 합류해 **한 지붕 여러 가족**이 되며, 앱 간 **물리적 분리**가 요구된다.
> 승인 시 ADR-0024로 승격하고 `ARCHITECTURE.md`·`SECURITY.md`·`DISASTER_RECOVERY.md`·`MEDIA_PIPELINE.md`에 반영한다.

---

## 0. 착수 전 5W1H (CLAUDE.md §0)

- **왜(Why)** — 북극성에 직접 기여하진 않지만 **기억의 지속 가능성**을 지킨다. 여러 앱이 Supabase 무료 한도(Storage 1GB·egress 5GB)를 **공유**해 서로 잠식하는 구조라, 사진이 늘면 가장 먼저 터지는 자원이다(ADR-0020이 이미 "사진이 Storage를 먼저 소진"이라 경고). 앱별 저장소를 물리적으로 갈라 **한 앱의 사진 증가가 다른 앱의 기억을 위협하지 못하게** 한다.
- **무엇을(What)** — 바꾸는 것: `MediaRemote`의 바이트 3연산(`uploadDisplay`/`download`/`remove`)의 백엔드. **안 바꾸는 것**: 로컬 원본(§0 불변), `journey.media` 메타 테이블·RLS·좀비 트리거, 동기화 병합 규율, 백업 형식(JSON/ZIP은 로컬 blob에서 생성 — R2 무관), 절약 모드 계약(원본 여전히 클라우드 미저장).
- **어디서(Where)** — SSOT: 포트 정의 `src/services/sync.ts:132`(`MediaRemote`), 경로 규약 `src/domain/media/rowmap.ts:82`(`mediaStoragePath`), 버킷 정책 `supabase/migrations/0007·0010`. 이 문서가 이관 결정의 SSOT이며 승인 시 ADR로 승격.
- **언제(When)** — 전환 기간에 **바이트가 두 곳에 나뉘어 존재**한다(구:Supabase / 신:R2). 읽기 경로가 이 시기를 견뎌야 하며(§5 폴백), 이관 완료 후 옛 객체 스윕까지가 한 사이클이다.
- **누가(Who)** — 데이터 소유자는 최종 사용자, 접근 범위는 `auth.uid()` 단위. **R2엔 RLS가 없다** → 그 책임이 DB에서 **Worker로 이동**한다(§3 — 이 제안의 최대 위험 표면). 검토 역할: security-privacy(필수), reviewer-release, disaster-recovery-guardian.
- **어떻게(How)** — 포트 뒤 어댑터 교체 + 재큐잉 유틸. 검증은 유닛(경로·서명·폴백) + Worker 통합검사 + 실기기 왕복. 되돌리기: 어댑터를 Supabase로 되돌리면 즉시 복구(옛 객체를 스윕 전까지 보존하므로 §7).

## 1. 왜 지금인가 (메디컬 합류가 바꾼 계산)

이전 판단은 "egress가 아직 안 아프니 보류"였다. **메디컬 합류로 전제가 바뀌었다.**

| | 현재(Supabase 공유) | 제안(R2 앱별 버킷) |
|---|---|---|
| 저장 한도 | 여행+회계+메디컬이 **1GB를 나눠 씀** | 앱마다 **각자 10GB**(무료 한도) |
| egress | 셋이 **5GB/월을 나눠 씀** | **무료(0원)** — R2의 핵심 이점 |
| 한 앱이 폭주하면 | **다른 앱이 같이 죽는다** | 격리 — 남의 앱 무영향 |
| 백업 복원 | 프로젝트 단위 → **한 앱 복원이 다른 앱을 롤백**(ADR-0020 명시 위험) | 바이트는 앱별 버킷이라 **교차 롤백 없음** |

마지막 행이 특히 중요하다: ADR-0020이 이미 기록한 "한 앱 복원 = 다른 앱도 롤백" 위험이 **메디컬(민감 의료 데이터)이 합류하면 수용 불가 수준**이 된다. 사진 바이트를 갈라내면 최소한 바이트 차원의 교차 위험은 사라진다.

**이관 비용은 지금이 가장 싸다** — 프로덕션 사진 수가 극소이고, 로컬에 원본 사본이 전부 있어(§5) 서버 간 복사 스크립트 자체가 불필요하다.

## 2. 물리적 분리 설계 — "한 지붕, 각자 벽"

요구: *스키마를 물리적으로 분리, 2가족 이상.* R2엔 스키마가 없으므로 **버킷**이 그 단위다.

```
Cloudflare 계정 (한 지붕)
├── R2 버킷: journey-media      ← 여행 앱 전용
├── R2 버킷: medical-media      ← 메디컬 앱 전용
└── R2 버킷: <다음 앱>-media     ← 확장 시 추가
        ▲                    ▲
        │ 바인딩(1:1)         │ 바인딩(1:1)
┌───────┴───────┐   ┌────────┴────────┐
│ Worker:       │   │ Worker:         │
│ journey-media │   │ medical-media   │
│ (여행 JWT 검증)│   │ (메디컬 JWT 검증) │
└───────────────┘   └─────────────────┘
```

### 핵심: **바인딩이 벽이다** (RLS보다 강한 보장)

Supabase RLS는 "정책"이다 — 정책을 잘못 쓰면 새어나간다(그래서 우리는 공격검사를 돌린다). R2 + Worker 구성에서는 다르다:

> **여행 앱 Worker에는 medical-media 버킷 바인딩이 아예 없다.** 코드에 치명적 버그가 나도, 심지어 공격자가 Worker 코드를 임의 실행해도, **존재하지 않는 바인딩으로는 남의 앱 바이트에 도달할 수 없다.** 정책 위반이 아니라 **물리적 불가능**이다.

이것이 "물리적으로 분리"에 대한 가장 정직한 이행이다. 대안과 비교:

| 방식 | 분리 강도 | 판정 |
|---|---|---|
| 한 버킷 + 앱별 prefix(`journey/…`) | 논리적(코드 실수로 교차 가능) | **기각** — 요구사항 불충족 |
| 앱별 버킷 + **공용** Worker | 버킷은 분리되나 Worker가 두 바인딩을 다 쥠 → 라우팅 버그가 교차 유발 | **기각** — 벽이 코드에 의존 |
| **앱별 버킷 + 앱별 Worker** | 바인딩 부재 = 물리적 불가능 | **채택** |
| 앱별 **Cloudflare 계정** | 최강이나 운영·과금 분산 부담 | 후속 옵션(민감도 상승 시) |

메디컬은 **별도 Supabase 프로젝트**(`rjhbfgbfhwdhtdzcdvtu`)라 JWT 발급자도 다르다 → Worker를 앱별로 두는 편이 **인증 경계와 저장 경계가 일치**해 더 단순하다. 한 Worker가 두 발급자를 구분하려 애쓸 이유가 없다.

## 3. 최대 위험 표면 — R2엔 RLS가 없다

현재 Supabase Storage가 **DB에서** 해주던 일:

```sql
-- 0007_journey_media_storage.sql
bucket_id='journey-media'
and (storage.foldername(name))[1] = auth.uid()::text   -- ① 소유자 폴더 격리
and journey.is_allowed()                               -- ② 초대제 허용목록
```

R2는 이걸 모른다. **Worker가 전부 대신해야 하며, 하나라도 빠지면 개인 사진이 공개된다.** Worker가 반드시 수행할 검사:

1. **JWT 서명 검증** — *디코드가 아니라 검증*. 디코드만 하면 누구나 `sub`를 위조해 남의 폴더를 읽는다. **이 이관에서 가장 치명적인 단일 실패점.**
2. **경로 접두어 = uid 강제** — 요청 키의 첫 폴더가 검증된 `sub`와 일치해야 함. `..`·절대경로·인코딩 우회 정규화 후 비교.
3. **초대제 허용목록**(§3.2 — 정직한 갭 있음)
4. **메서드별 권한** — GET/PUT/DELETE 각각 위 3개를 통과해야 함.

### 3.1 JWT 검증 방식

| 방식 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **비대칭(JWKS)** — Supabase 비대칭 서명 키 + 공개 JWKS 엔드포인트를 Worker가 fetch·캐시 | Worker에 **비밀이 없다**. 키 회전 자동 대응 | Supabase 프로젝트에 비대칭 키 활성 필요 | **1순위 권장** |
| 대칭(HS256 공유 시크릿) | 설정 단순 | **JWT 시크릿이 Worker에 상주** — 유출 시 임의 사용자 위조 가능. §0 "비밀키 최소화"와 상충 | 차선(비대칭 불가 시만) |

> **정직**: 이 환경(샌드박스)에서 Supabase 대시보드의 비대칭 키 활성 여부를 확인할 수 없다. 착수 시 사용자가 확인해야 하는 항목(§8 체크리스트 A-2).

### 3.2 초대제(`is_allowed`)의 정직한 갭

현재 허용목록의 SSOT는 **DB 테이블** `journey.allowed_users`다. Worker가 이를 아는 방법:

- **(a) Worker가 사용자 JWT로 Supabase RPC `is_allowed()` 호출** — SSOT 유지(§7 준수), uid별 단기 캐시로 비용 완화. **권장.**
- (b) Worker 환경변수에 허용목록 복제 — **손편집 중복 = 결함**(§7 위반). 기각.
- (c) 커스텀 JWT 클레임(Auth Hook으로 `is_allowed`를 토큰에 주입) — 가장 빠르나 Auth Hook 인프라 추가. 후속 최적화 후보.

**(a)를 채택하되 정직하게 남기는 갭**: 캐시 TTL 동안(예: 5분) 허용목록에서 방금 제거된 사용자가 자기 폴더에 계속 접근할 수 있다. **남의 데이터는 여전히 불가**(경로 격리는 캐시와 무관) — 노출이 아니라 **회수 지연**이다. 메타데이터는 DB RLS가 즉시 차단하므로 실질 영향은 "고아 바이트 업로드" 수준. 수용 가능하되 문서화 필요.

### 3.3 바이트 전달 방식

| 방식 | 동작 | 판정 |
|---|---|---|
| **Worker 프록시**(R2 바인딩으로 스트리밍) | 모든 바이트가 Worker를 통과. 매 요청 인증 강제. **S3 액세스 키가 아예 존재하지 않음**(네이티브 바인딩) | **채택** |
| 사전서명(presigned) URL | Worker는 서명만 발급, 바이트는 브라우저↔R2 직결 | 차선 — S3 자격증명 필요 + 서명 URL이 로그·히스토리에 남는 유출면 + CSP 호스트 추가 |
| 공개 버킷 + 추측 불가 키 | — | **절대 기각** — 개인자료 기본 비공개(§3) 정면 위반 |

프록시 채택 근거: ①**자격증명 자체가 없음**(바인딩은 키가 아님) ②CSP에 호스트 **하나만** 추가 ③표시본이 ≤10MB라 Worker 요청 본문 한도에 여유 ④개인 앱 트래픽은 Workers 무료 한도(10만 req/일)에 크게 못 미침.

## 4. 바꾸지 않는 것 (경계를 좁게 유지)

이관의 안전성은 **손대지 않는 범위**에서 나온다:

- **`journey.media` 테이블·RLS·좀비 트리거·복합 FK** — 그대로. 메타는 계속 Supabase Postgres.
- **`storage_path` 값 형식** — `{uid}/{id}.webp` 그대로 R2 키로 재사용. **DB 마이그레이션 불필요**(§5).
- **`check-schema-parity`** — 컬럼 안 바뀌므로 무영향.
- **동기화 병합 규율**(LWW·tombstone 우위·빈-클라우드 가드) — 무영향.
- **백업(JSON/ZIP)** — 로컬 blob에서 생성하므로 R2와 무관. `check-backup-coverage` 무영향.
- **로컬 원본**(§0) — 절대 불변. 여전히 클라우드 미업로드(절약 모드 계약 유지).
- **DR 3계층 구조** — ②의 구현체만 Supabase→R2로 바뀔 뿐 계층 성질은 동일. `DISASTER_RECOVERY.md` §1 표의 "②" 행만 갱신.

## 5. 이관 방법 — 서버 간 복사 없음

**핵심 통찰**: `LocalMedia`는 `originalBlob`/`displayBlob`/`thumbBlob`을 **항상 로컬에 보존**한다(`src/offline/db.ts:41`, §0 원칙). 즉 **모든 사진의 완전한 사본이 이미 사용자 기기에 있다.** 따라서 Supabase→R2 서버 간 복사 스크립트가 **아예 필요 없다.**

### 5.1 재큐잉 유틸 (신규 코드의 거의 전부)

`pushPendingMedia`(`sync.ts:421`)는 `syncQueue`에 남은 항목만 처리하고, 업로드 성공 시 큐에서 삭제한다(`sync.ts:461`). 그래서 이미 올라간 사진은 **다시 올릴 트리거가 없다.** 필요한 것은 단 하나:

```
requeueAllMedia(): 활성(deletedAt=null) localMedia 전 행에 대해
                   syncQueue에 'media' op를 새로 넣는다.
```

그러면 **이미 검증된 `pushPendingMedia` 경로가 그대로** 새 어댑터(R2)로 바이트를 밀어 올린다. 새 동기화 로직 없음. UI는 데이터 관리에 "사진 저장소 재업로드" 버튼 하나.

### 5.2 전환 기간 읽기 폴백 (DB 마이그레이션 회피)

전환 중엔 바이트가 두 곳에 나뉜다. **컬럼 추가 대신 읽기 경로 폴백**:

```
download(path):  R2 시도 → 404면 Supabase Storage 시도 → 성공분은 로컬에 보관
```

- 마이그레이션 0건, 스키마 파리티 무영향, **자가 치유**(읽는 족족 로컬에 남음)
- 재업로드 완료 후 다음 버전에서 폴백 제거

### 5.3 순서 (되돌리기 가능하게)

1. R2 어댑터 + Worker 배포, **읽기는 폴백 포함** → 이 시점에 되돌리면 무손실
2. `requeueAllMedia()` 실행 → 모든 바이트가 R2로 상승
3. 실기기에서 read-back 검증(§8 B) — 200이 아니라 **같은 바이트**를 되읽어 확인
4. 검증 통과 후에만 Supabase 옛 객체 스윕(DEL-CONTRACT)
5. 다음 버전에서 폴백 코드 제거

**3번 이전에는 옛 객체를 절대 지우지 않는다** — 되돌릴 곳을 남긴다(§5 복구 가능성 우선).

## 6. 게이트 의무 (같은 커밋에서 처리해야 하는 것)

우리 문서가 이미 요구하는 사항 — 잊으면 빌드가 RED이거나, 더 나쁘게는 조용히 통과한다:

- **`check-csp`** — Worker 호스트를 `connect-src`(+ 필요 시 `img-src`)에 추가하고 **`scripts/check-csp.mjs`의 `REQUIRED`도 같은 커밋에서 갱신**(ADR-0023이 명시한 규율). 갱신 안 하면 게이트가 새 의존을 보증하지 못한다.
- **`check-secret-leak`** — SECURITY.md가 못박은 의무: *"새 제공자 키 도입 시 형태 패턴을 같은 커밋에서 추가한다."* Cloudflare API 토큰 형태 패턴을 `PATTERNS`에 추가(현재 Supabase·Google·PEM만 있음). **Worker 시크릿이 저장소에 새는 것을 형태로 차단.**
- **신규 게이트 후보 `check-storage-isolation`** — Worker 설정(wrangler)에서 **각 Worker가 자기 버킷 바인딩만** 갖는지 저장소만으로 대조. §2의 "바인딩이 벽" 보장이 사람의 주의력이 아니라 **기계**로 지켜지게 한다. 비공허 자체검사: 교차 바인딩 주입 시 RED.
- **Worker 인증 유닛검사** — 서명 위조 JWT·만료 JWT·`sub` 불일치 경로·`..` 경로 우회를 **전부 거부**하는지. 알려진 실패 주입으로 비공허 확인(§4).

## 7. 정직한 갭·비용

- **Worker 코드가 새 신뢰 경계다** — 지금은 Supabase가 검증된 RLS로 해주던 일을 우리 코드가 한다. 버그 = 개인 사진 노출. 그래서 §6의 인증 유닛검사가 선택이 아니라 필수다. **security-privacy 에이전트 감사를 완료조건에 포함.**
- **가용성 의존이 하나 늘어난다** — Worker가 죽으면 사진 동기화가 멈춘다(단, **로컬 우선이라 앱은 정상 동작**하고 기억 유실은 없다 — DR 시나리오 B와 동일 성질).
- **초대제 회수 지연** ≤ 캐시 TTL(§3.2) — 노출 아님, 회수 지연.
- **인프라는 사용자 몫** — 이 세션에서 Cloudflare 계정 생성·버킷·토큰 발급을 대신할 수 없다(§8 A).
- **샌드박스 미검증** — `*.supabase.co`가 차단된 환경이라 실 네트워크 왕복은 **실기기 확인 몫**(기존 동기화와 동일한 정직한 경계).
- **비용**: 개인 규모에선 R2·Workers 무료 한도 내. 다만 이건 *현재 규모 기준*이며 한도 초과 시 과금됨 — 사용량 관측을 후속 과제로 남긴다.

## 8. 착수 전 체크리스트

**A. 사용자가 해야 할 것(외부 계정 — 제가 못 함)**
1. Cloudflare 계정 + R2 활성화, 버킷 2개 생성: `journey-media`, `medical-media`
2. Supabase에서 **비대칭 JWT 서명 키(JWKS)** 사용 가능 여부 확인 → §3.1 방식 확정
3. Workers 배포 권한(wrangler 로그인). **API 토큰을 저장소·채팅에 붙여넣지 마세요** — Worker 시크릿으로만 설정

**B. 완료의 정의(DoD)**
구현 → 유닛(경로·JWT 거부 케이스·폴백) → Worker 통합 → `harness` 11게이트 + 신규 격리 게이트 → security-privacy 감사 → **실기기 read-back**(같은 바이트 확인) → DR 감사관 재판정 → 문서 갱신(ADR-0024·ARCHITECTURE·SECURITY·DR·MEDIA_PIPELINE) → 옛 객체 스윕.
