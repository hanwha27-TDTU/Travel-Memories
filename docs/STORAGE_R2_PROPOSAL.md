# 기술변경 제안서 · 사진 바이트 저장소를 Cloudflare R2로 이관 (개정 2판)

> 상태: **적용 완료(2026-07-25) — 실증됨.** 버킷·CORS·토큰·시크릿 4개·`media-sign` 배포·`VITE_MEDIA_STORE=r2`까지 전부 반영되어 **새 사진은 R2로 저장된다**.
> **사진 보존 정책은 2026-08-04 ADR-0046으로 변경됨**: 사용자 외부 파일은 여전히 건드리지 않지만 앱 내부 `originalBlob`은 R2 WebP 바이트 검증 전 스테이징이며, 검증 뒤 정리한다. 아래의 영구 로컬 원본 표현은 이관 당시 역사다.
> **실측 증거**: 앱에서 사진 저장 → R2에 `{uid}/{mediaId}.webp` (image/webp, 53.99 kB, 저장 클래스 표준) 객체 생성 확인. DB `storage_path`와 R2 객체 키가 **완전히 일치**(키 파리티 실증). 함수 호출 전부 200, 삭제 서명도 200.
> **미확인**: 사다리 4번(새 기기에서 읽기 presign). 다른 기기로 열 때 자연히 증명된다.
> **혼재 상태 주의**: 07-25 이전 사진의 바이트는 여전히 Supabase Storage에 있다. 옛 객체 스윕은 4번 통과 후에만 검토한다.
> **개정 이유**: Medical-Note 앱이 2026-07-25에 동일 이관을 **처음부터 끝까지 실제로 수행**하고 인수인계 문서
> (`R2 이미지 저장소 — 여행앱 인수인계`)와 검증된 함수 소스(`media-sign-index.ts`)를 넘겨줬다.
> **1판(Cloudflare Worker + 바인딩)은 폐기하고, 실증된 구조(Supabase Edge Function presign)를 채택한다.**
> 아래 §7에 **1판에서 내가 틀렸던 것**을 명시했다.
> 승인 시 ADR-0024로 승격하고 `ARCHITECTURE.md`·`SECURITY.md`·`DISASTER_RECOVERY.md`·`MEDIA_PIPELINE.md`에 반영한다.

## 0. 착수 전 5W1H (CLAUDE.md §0)

- **왜(Why)** — 여러 앱이 Supabase 무료 한도를 공유해 서로 잠식하고, **백업 복원이 프로젝트 단위**라 한 앱 복원이 다른 앱을 롤백시킨다(ADR-0020 기록 위험). 메디컬 합류로 이 위험이 수용 불가 수준이 됐다.
- **무엇을(What)** — 바꾸는 것: 사진 **바이트**의 저장 위치와 그 접근 경로. 당시 안 바꾼 것: 로컬 원본 정책(후에 ADR-0046으로 변경), `journey.media` 메타 테이블·RLS·좀비 트리거, 동기화 병합 규율, 백업 형식.
- **어디서(Where)** — 포트 `MediaRemote`(`src/services/sync.ts:132`), 경로 규약 `mediaStoragePath`(`src/domain/media/rowmap.ts:82`). 이 문서가 이관 결정의 SSOT.
- **언제(When)** — 전환 기간에 바이트가 두 곳에 나뉜다(§5 폴백). 이관 완료 → read-back 검증 → 그 후에만 옛 객체 스윕.
- **누가(Who)** — 데이터 소유자는 최종 사용자. **R2엔 RLS가 없다** → 접근 통제가 DB에서 **토큰 스코프 + Edge Function**으로 이동한다(§3).
- **어떻게(How)** — 포트 뒤 어댑터 교체 + 재큐잉. 검증은 §6 사다리. 되돌리기: 어댑터를 Supabase Storage로 되돌리면 즉시 복구(옛 객체를 스윕 전까지 보존).

## 1. 채택 구조 (Medical-Note 실증)

```
[브라우저(여행앱)]
   │ ① POST /functions/v1/media-sign  {"op":"presign", kind, contentType, bytes}
   │     Authorization: Bearer <Supabase anon key>
   ▼
[Supabase Edge Function: media-sign]   ← R2 자격증명은 여기에만
   │ ② SigV4로 5분짜리 presigned PUT URL 생성 (객체 키는 서버가 만든다)
   ▼
[브라우저] ── ③ PUT (바이트 직접) ──▶ [Cloudflare R2 버킷: travel-log-media]
   │
   └─ ④ 키/URL만 메타에 저장 (바이트는 Supabase를 통과하지 않음)
```

**핵심 성질**

| 성질 | 왜 중요한가 |
|---|---|
| 바이트가 Edge Function을 통과하지 않음 | 요청 크기 제한에 안 걸리고, 나중에 영상도 같은 통로 |
| **객체 키를 서버가 생성** | 클라이언트가 보낸 key/bucket은 무시 — 경로 조작·타 버킷 접근 불가 |
| 서명 URL 수명 300초 | 유출돼도 창이 좁다 |
| 삭제도 서버측 서명 | 브라우저에 삭제 권한을 주지 않는다 |

## 2. 물리적 분리 — "한 지붕 N가족"

요구: *스키마를 물리적으로 분리, 2가족 이상.*

```
Cloudflare 계정 (한 지붕)
├── R2 버킷: medical-media      ← 메디컬 전용 토큰만 열 수 있음
└── R2 버킷: travel-log-media   ← 여행 전용 토큰만 열 수 있음
        ▲
        │ R2_* 시크릿 5개
[Supabase Edge Function: media-sign]  ← 앱의 Supabase 프로젝트에 개별 배포
```

### 핵심: **토큰 스코프가 벽이다**

> 여행앱 함수의 토큰은 **`travel-log-media` 버킷 하나만** 허용된다. 코드에 치명적 버그가 나도,
> 심지어 함수가 임의 실행돼도, **Cloudflare 토큰 스코프상 메디컬 버킷에 도달할 수 없다.**
> 정책 위반이 아니라 **물리적 불가능**이다.

**기각한 대안(인수인계 문서 §1.1 — 같은 실수 반복 금지)**

| 방식 | 판정 |
|---|---|
| `tenant` 파라미터를 받는 **공유 함수 1개** | **기각** — tenant→토큰 맵이 한 곳에 모여, 그 함수가 뚫리면 전 세입자 버킷이 함께 열린다 |
| 프록시 업로드(브라우저 → 함수 → R2) | **기각** — 바이트가 함수를 통과해 요청 크기 제한에 묶이고, 영상 추가 시 재설계 필요 |
| **배포 인스턴스 1개 = 버킷 1개** | **채택** — 이 설계의 전부 |

## 3. 접근 통제 — RLS가 없는 곳에서 무엇이 지켜주나

현재 Supabase Storage가 해주던 일과의 대응:

| Supabase Storage(현재) | R2 + Edge Function(제안) |
|---|---|
| JWT 검증 | **Supabase Edge Function이 네이티브로 처리**(anon Bearer) |
| `(storage.foldername(name))[1]=auth.uid()` 폴더 격리 | 키를 **서버가 생성** → 클라이언트가 경로를 못 고른다 |
| `journey.is_allowed()` 초대제 | 함수 호출 자체가 Supabase 인증을 거침(§8 미결 참조) |
| 버킷 비공개 | **⚠ `r2.dev` 공개 URL은 인증 없이 열람 가능 — §8 최대 미결 쟁점** |

> **1판 대비 가장 큰 개선**: 1판은 Cloudflare Worker가 **Supabase JWT 서명을 직접 검증**해야 했고, 나는 그것을
> "이 이관의 가장 치명적인 단일 실패점"이라고 적었다. Edge Function 방식은 **그 위험을 통째로 없앤다** —
> 우리가 인증 코드를 짜지 않는다.

## 4. 바꾸지 않는 것

- `journey.media` 테이블·RLS·좀비 트리거·복합 FK — 그대로(메타는 계속 Supabase Postgres)
- 동기화 병합 규율(LWW·tombstone 우위·빈-클라우드 가드) — 무영향
- 백업(JSON/ZIP) — 로컬 blob에서 생성하므로 R2와 무관
- 사용자 외부 원본 파일 — 앱이 변경·삭제하지 않음. 앱 내부 원본 복사본 정책은 ADR-0046으로 대체됨
- 썸네일을 클라이언트가 만드는 것 — **우리는 이미 그렇게 한다**(`thumbBlob`). R2엔 CDN 변환이 없으므로 이 성질이 잘 맞는다.

**바뀌는 것**: 없음(설계 시점 예상과 달랐다). 인수인계 §5.4는 R2 키를 별도로 저장하라고 했고 나도 `storage_path`를 R2 키 형식(`image/2026/07/<uuid>.webp`)으로 **전환하거나 컬럼을 추가해야 한다 → 마이그레이션 필요**라고 적었다. **이 서술은 구현에서 뒤집혔다** — 함수가 검증된 `sub`로 키를 만들게 하니 기존 규약 `{uid}/{id}.webp`가 그대로 R2 키가 된다. 따라서 **마이그레이션 0, `check-schema-parity` 무변경**이며, 저장된 경로를 건드리지 않는 쪽이 원칙 #1에 안전하다. 2026-07-25 실측에서 DB `storage_path`와 R2 객체 키가 완전히 일치함을 확인했다.

## 5. 이관 방법 — 서버 간 복사 없음 (1판과 동일, 유효)

이관 당시 `LocalMedia`가 세 blob을 로컬에 보존했으므로 Supabase→R2 서버 간 복사 스크립트가 불필요했다. 현재는 ADR-0046에 따라 R2 WebP 검증 뒤 `originalBlob`을 정리하지만 `displayBlob` 캐시는 유지한다.

1. R2 어댑터 + `media-sign` 배포, **읽기는 폴백 포함**(R2 → 404면 Supabase Storage) → 이 시점에 되돌리면 무손실
2. `requeueAllMedia()` — 활성 `localMedia` 전 행에 큐 op를 새로 넣어 이미 검증된 `pushPendingMedia` 경로가 R2로 밀어 올리게 한다
3. **실기기 read-back 검증**(§6 사다리 3~4번)
4. 통과 후에만 Supabase 옛 객체 스윕(DEL-CONTRACT)
5. 다음 버전에서 폴백 제거

**3번 이전에는 옛 객체를 절대 지우지 않는다.**

## 6. 검증 사다리 (인수인계 §6 — 앞 단계가 뒤를 보장하지 않는다)

| # | 검증 | 증명하는 것 | **증명 못 하는 것** |
|---|---|---|---|
| 1 | 대시보드 함수 Test `{"op":"probe"}` → 200 | 시크릿이 함수에 도달 | **앱 경로**(Test는 `Role postgres`로 호출) |
| 2 | 앱의 **연결 확인** 버튼 | anon Bearer 경로로 함수 호출 성공 | R2로의 실제 업로드(**CORS**) |
| 3 | **앱에서 사진 업로드** | presign → 브라우저→R2 직접 PUT → 썸네일 → 표시 | — (**결정적 검증**) |
| 4 | **새 기기(또는 시크릿 창)에서 그 사진 보기** | 읽기 presign(`op:get`) + 키 파리티 | — (정책 B에서만 필요) |

> **1번이 200이어도 앱에서는 실패할 수 있다.** CORS 문제는 **3번에서만** 드러난다. Medical-Note가 정확히 여기서 걸렸다.
> 이 사다리를 우리 릴리스 체크리스트에 그대로 넣는다 — **자동화로 대체할 수 없는 사람 단계**다.
>
> **2026-07-25 실측**: 1·2·3번 통과(3번 = R2에 image/webp 53.99 kB 객체 생성 확인). **4번은 미확인** — 새 기기에서 열 때 증명된다.

| # | 1판 서술 | 실제 | 영향 |
|---|---|---|---|
| 1 | "앱마다 **각자 10GB**(무료 한도)" | ❌ **무료 한도는 계정 전체 합산이다.** 여행앱과 메디컬이 같은 10GB를 나눠 쓴다 | **이관 근거 하나가 약해진다.** 이 격리는 **접근 권한의 격리이지 쿼터의 격리가 아니다.** 남는 근거: egress 무료 · 백업 복원 교차 롤백 해소 · Supabase Storage 1GB 압박 해소 |

## 8. ~~최대 미결 쟁점~~ → **결정됨: B(읽기도 서명)** ✅

> **2026-07-25 사용자 결정 "B로 가자" → ADR-0024.** 버킷은 비공개로 두고 읽기도 5분 presigned GET.
> 따라서 **공개 개발 URL을 켜지 않고 `R2_PUBLIC_BASE`도 등록하지 않는다**(시크릿 4개).
> B의 대가가 우리 앱에서 작은 이유: 화면은 언제나 **로컬 blob**으로 그린다(`tripDetail.ts`의
> `thumbBlob`/`displayBlob`) → 읽기 서명은 *새 기기가 그 사진을 처음 받을 때 사진당 1회*뿐이다.
> Medical-Note는 URL로 직접 표시하는 구조라 A가 합리적이었다 — 구조가 다르니 결론도 달라진다.
> 아래는 결정 근거로서 원문을 보존한다.

**~~이것이 승인 전에 반드시 결정해야 할 단 하나의 문제다.~~**

- 인수인계 구조는 R2 **공개 개발 URL**(`https://pub-xxxx.r2.dev/<key>`)을 쓴다 → **URL을 아는 사람은 인증 없이 열람**할 수 있다(키가 UUID라 추측은 사실상 불가능하지만, 유출되면 열린다).
- 그런데 우리 앱의 **비타협 원칙 #3**은 *"개인자료는 기본 비공개 — 여행·사진·GPS·동행인·비용·회고 모두 비공개가 기본"*이다. 현재 Supabase `journey-media` 버킷은 **비공개 + 소유자 RLS**다.
- Medical-Note는 이 절충을 수용했다("개인 식별 정보가 담긴 사진은 올리지 않는다"는 원칙으로 완화). **그러나 우리 앱은 정의상 개인 사진이 주인공이다** — 같은 완화가 성립하지 않는다.

**선택지**

| 안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 공개 URL 수용** | 인수인계 그대로 | 가장 단순·실증됨. 이미지 표시가 빠름(CDN 직결) | **원칙 #3 완화**. URL 유출 시 열람 가능 |
| **B. 읽기도 presign** | `op:"getUrl"`을 추가해 GET도 5분 서명 | **비공개 유지** — 원칙 #3 그대로 | 함수 호출이 늘고(이미지마다), URL 캐시가 어려워 표시 성능 저하. 함수 수정 필요(앱 독립성 약간 손상) |
| **C. 커스텀 도메인 + Cloudflare Access** | 도메인 앞에 인증 | 강함 | 도메인·설정 복잡도 증가 |

**내 권고: B**(읽기 presign)를 기본으로 하되, 성능이 문제되면 A로 완화하는 것을 **사용자가 명시적으로 결정**한다.
근거: 우리 앱에서 사진은 **기억 그 자체**이고 GPS가 붙은 개인 자료다. "URL을 모르면 안전"은 보안이 아니라 은닉이며, 백업 파일·기기 공유·브라우저 이력 등으로 URL은 생각보다 잘 샌다. 다만 **B는 실증되지 않은 경로**라(메디컬은 A로 운영 중) 우리가 처음 밟는 위험이 있다 — 이 점을 정직하게 남긴다. **[2026-07-25 갱신]** B의 **쓰기**(presigned PUT)·**삭제**는 실증됐다. **읽기**(presigned GET)는 아직 한 번도 실행되지 않았다 — 사다리 4번이 그것을 증명한다.

## 9. 착수 체크리스트

**A. 사용자가 해야 할 것(외부 콘솔 — 제가 못 함)**
1. R2 버킷 `travel-log-media` 생성 — **위치 자동 · 저장 클래스 표준**(Infrequent Access 금지)
2. 🔒 **공개 개발 URL은 켜지 않는다**(정책 B). "공개 액세스: 사용 안 함" 상태 확인만 하고 지나간다 → `R2_PUBLIC_BASE` 없음
3. **CORS 정책** — `AllowedOrigins`에 앱 origin을 **주소창에서 직접 복사**(GitHub Pages는 대문자→소문자 변환), `AllowedMethods: PUT/GET/HEAD`(**정책 B는 GET도 브라우저→R2 직행이라 GET 누락 시 "업로드는 되는데 새 기기에서 안 보임"이 된다**), `AllowedHeaders: content-type`
4. 🚨 **「버킷 잠금 규칙」 절대 켜지 말 것** — 기본값이 ON·무기한이라 저장하면 객체 영구 삭제 불가
5. **계정 API 토큰**(사용자 토큰 아님) — 권한 `개체 읽기 및 쓰기`, **특정 버킷 하나만**, IP 필터링 **비움**
6. 🔴 발급 결과에서 **"토큰 값"이 아니라 `Access Key ID`/`Secret Access Key`**를 쓴다. **이 화면은 캡처 금지**
7. Supabase Secrets **4개** 등록(`/functions/secrets` URL 직행) — `R2_PUBLIC_BASE` 제외
8. `media-sign` 함수 배포 — **우리 저장소의 `supabase/functions/media-sign/index.ts`**(메디컬 소스가 아니다: 읽기 서명 `op:"get"` 추가, 공개 URL 미사용, 객체 키를 검증된 `sub`로 생성)
9. 앱 빌드 환경변수 `VITE_MEDIA_STORE=r2` (이걸 켜기 전까지 기존 경로 그대로)

**B. 완료의 정의(DoD)**
구현 → 유닛 → `harness` 전체 그린 → security-privacy 감사 → **§6 사다리 1~4 전부**(특히 3번 실기기 업로드) → DR 감사관 재판정 → 문서 갱신 → 옛 객체 스윕.

## 10. 기계로 잠글 것 (인수인계 §10 권장 채택)

Medical-Note가 사고 후 도입한 패턴을 우리도 따른다:
- **함수 원장(JSON)**: 함수별 "누가 호출 · 어떤 시크릿을 읽음 · verify_jwt posture · 폐기 정리 상태" 선언
- **게이트**: 원장 ⇄ 함수 소스의 `Deno.env.get()` 집합 ⇄ 앱의 `/functions/v1/<name>` 호출 ⇄ 설정 문서를 양방향 대조
- 외부 콘솔 상태는 저장소에서 볼 수 없으므로 **FAIL이 아니라 경고**로 매 실행 출력(영구 빨간불 방지)

**정직**: 이 게이트는 **정합만** 잠근다. "외부 콘솔이 실제로 그렇게 설정됐는가"는 원리적으로 기계가 못 본다 → §6 사다리 3번(사람이 실제로 올려본다)은 릴리스 체크리스트에 명시 단계로 남긴다.

> **폐기 정리 교훈(인수인계 §9)**: Medical-Note는 저장소에서 Cloudinary 소스를 지웠는데 **Supabase 배포 실물과 시크릿 3개가 한 달 넘게 살아 있었다.** 저장소와 인프라는 따로 논다 — 이관 후 옛 함수·고아 시크릿 삭제를 체크리스트에 넣는다.

## 11. 한 줄 요약
